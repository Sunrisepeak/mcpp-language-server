# 架构

[English](../90-architecture.md) | **简体中文**

先给一张简图，再说明设计文档在哪。

## 大致结构

```
编辑器 / Agent / CI
        |  LSP、MCP 或命令行
   orchestrator ......... 每个根目录一个工作区：模型、计划、文档、状态
        |
   project .............. 工程怎么构建？mcpp、CMake、compile_commands.json，或者扫描源码
   toolchain ............ 这个编译器怎么处理模块？（探测后缓存）
        |
   normalize ............ 一份引擎计划：每个引擎都能接受的参数
        |
   engines .............. mcppls 自己的模块引擎，旁边是 clangd
```

- **模块描述只被规范化一次。** 不管用的是哪种构建系统，它都会变成一份 S1 文档（[specs/](../specs/)），下游的一切只读这一份。
- **两个引擎服务同一个工作区。** mcppls 自己的引擎从它自有的语法索引出发，回答模块级别的请求；其余的由 clangd 回答，靠 mcppls 为它写的数据库驱动。
- **服务端启动的外部程序不能拖住服务端。** 构建工具、编译器探测、CMake 和 git 全部经由同一个运行器执行，该运行器给每次运行分配独立的进程单元、限制读取量，并记录下发生了什么。
- **每个请求给 clangd 都有预算，并在预算内作答。** 补全和签名帮助 1 秒，悬停 2 秒，跳转到定义 10 秒。超过之后 mcppls 用手上有的东西作答——补全给出文件里离光标最近的词，作为不完整的列表，让编辑器再问；模块准备期间的悬停给出一行说明——并取消发给 clangd 的请求。报告按方法统计由哪个引擎作答（`requests.<method>.answeredBy`）。
- **clangd 答得慢时，用它之前的答案先顶上。** 补全、悬停、签名帮助和跳转会按位置、类型和名字保存 clangd 的答案。clangd 慢于 `mcppls.answer.budget`（450 ms）时先给出保存的答案，你继续输入时由 clangd 自己的答案替换；列表里除了 mcppls 存疑的那一项带个小小的 `·`，看不出任何区别。跳转只在它落到的文件没变时这样做。Agent 和命令行会被告知哪些答案不是 clangd 自己的，也可以选择等它（见 [Agent 与 CI](40-agents.md)）。正确性始终以 clangd 为准。
- **颜色立即出现并跟随文本。** 一个文件的语义 token 需要 clangd 对整个文件的语法树，补全不需要。服务端为每个打开的文件保存 clangd 上一次给出的 token，随每次编辑移动它们（被编辑触及的 token 等待 clangd），并立即以它们作答；clangd 的答案与之不同时随后发出 `workspace/semanticTokens/refresh`。已保存文本的 token 存放在磁盘上，键为文本、编译命令、mcppls 与 clangd 的版本以及该文件读取的模块接口，因此同一文本再次打开时，在 clangd 读完第一行之前就已上色。持有上一次答案的客户端只收到变化部分（`full/delta`），范围请求从整份答案中裁出。不支持 refresh 的客户端照旧等待 clangd。
- **后台工作只在空闲时做。** 为 clangd 的索引构建实现单元时一次只做一个，而且要在 10 秒内没有输入、没有打开文件、也没有请求之后；clangd 因构建描述变化需要的重启，要等输入停顿 3 秒之后（最多 60 秒）。崩溃或 clangd 不再应答仍然立即重启。有打开的文件在等模块准备时，准备工作用掉除一个之外的全部 worker，否则用一半。
- **无法恢复的情况立即记录下来。** 服务端无法自行恢复时，会写出一个已脱敏的诊断包（`<cache>/bundles/auto-<code>-<time>.zip`，从不上传），并挂在对应的状态 issue 上，编辑器就能据此提供一份填好内容的报告。
- **构建出的模块不会越积越多。** 每个单元保留它最新两条命令的 BMI；更旧的在 clangd 启动时于后台删除。
- **服务端知道自己运行在哪种沙箱里。** 在 PRoot（termux）下，它按那种沙箱的应答方式启动程序；报告里显示为 `server.sandbox`。
- **服务端本身不发起任何网络调用。** 它启动的外部程序默认离线运行；模型相关功能需要主动开启，并放在单独的进程里。

## 规范

值得复用的部分都写成了带标识符和可追溯性的规范，版本号与产品本身分开管理：S1 构建数据库、S2 发现、S3 LSP 扩展、S4 语义工具包、S5 语义查询。见 [specs/README.md](../specs/README.md)。
