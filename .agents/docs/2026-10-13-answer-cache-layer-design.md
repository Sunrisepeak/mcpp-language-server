# 多级缓存应答层：补全、签名、悬停、跳转（2026-10-13）

目标：项目准备好之后，**任何项目、任何文件，交互请求都在 0.5 s 内响应**；之后到达的权威结果**无感地**替换先给出的结果。冷启动和第一次加载可以慢，但**同类请求见过一次，之后就一定在 0.5 s 内响应**。

不同使用面的侧重不同：
- **编辑器用户**：以无感为核心，不暴露底层机制；
- **agent（MCP 工具）和 CLI**：每个结果都明确标注来源与确定性；
- **日志**：每一次应答都带来源标记，方便调试。

本文先说明 0.0.14 的应答路径和它在大型模块项目上的缺口，再给出分层与职责。然后依次是：应答层的通用框架；补全、签名帮助、悬停、跳转、引用各自的策略；各使用面的可见性规则；引擎侧的配合；指标与测试；设置、风险、计划，以及多视角自审。

## 0. 结论

1. **分两层，各管一件事。**
   - **mcppls-clangd 只管正确**：给定一个文档快照，给出权威答案。可以慢，但不猜。
   - **mcppls 管快、交互和可见性**：多级缓存、请求去重、后台续跑、结果合成、无感刷新、持久化，以及各使用面的标注。这一层只依赖标准 LSP 请求，与核心引擎是谁无关。
2. **大部分答案与文件无关，可以跨文件、跨会话缓存。**
   - `std::` 的成员、`ordered_json` 的成员、`std::vector` 的悬停、`spdlog::info` 的定义位置，在可见集合相同的文件里都一样；
   - 只有局部变量和 `this` 的成员是文件私有的。
3. **一套通用框架，按请求类型配不同的策略。**
   - 通用部分：三级键（K1 位置、K2 语义、K3 名字）、可见集合指纹、代际、多级存储、引擎代理、合成器。
   - 补全和签名帮助：可以给不确定的结果，再原地更新。
   - 悬停：可以给不确定的结果，下次悬停时更新。
   - 跳转：只给确定的结果，或者经过文本校验后能精确定位的结果，否则等引擎。跳错位置的代价比列表里多一项大得多。
4. **截止时间 0.45 s。** 到时权威结果没来，就用缓存合成一个结果。引擎请求**不取消**，跑完后写回缓存。
5. **可见性按使用面区分。**
   - 编辑器：不主动重弹列表，不确定的项默认只带一个很浅的 `·`，确定的项不加任何标记；
   - agent：默认等权威结果（和 `cxx_diagnostics` 的 `fresh` 一致），用了缓存时，在结果里给出来源、确定性、代际和缓存年龄；
   - CLI 和 report：输出命中统计和来源分布；
   - 日志：每次应答都有一行统一格式的来源记录。
6. **引擎侧三个补丁（E1、E2、E4），加一项 mcppls 侧的用法调整（E5）**，补丁都写成能提交上游的形式；E3 经核实不做（第 7 节）。预计把大型模块项目上一次补全的权威结果从 3.1–3.5 s 降到约 2 s，悬停从秒级降到毫秒级，具体以测量为准。
8. **模块项目怎样组织代码更快**（包装模块、头文件收敛、不混用），单独成文：`docs/25-module-projects.md`。
7. **不改 mcpp。** 所需的信息（模块图、文件变化、编译命令）mcppls 都已经有了。

## 1. 现状

### 1.1 0.0.14 的应答路径（`src/orchestrator/workspace.cpp`、`completion.cpp`、`routing.cpp`）

| 机制 | 做什么 | 范围 |
|---|---|---|
| R-7 预算（`answer_budget`） | 补全和签名帮助 1000 ms，悬停 2000 ms，跳转类 10000 ms；到时引擎没答，就用 mcppls 自己的结果作答 | 每个请求 |
| UP-25 `EnginePace` | 某个文件最近的引擎答案都稍晚于 1 s 时，补全预算放宽，最多到 2.5 s；远超上限的答案不计入 | 每个文件 |
| C-2 `LateCompletion` / `LateAnswer` | 补全预算到了，引擎请求继续跑（最多 10 s）；同一个词后续的请求等它，或者直接用它（5 s 内） | 每个文档一条 |
| A1 `WordAnswer` | 引擎的完整答案按词保留 30 s；同一个词里继续打字、词外文本没变时直接复用 | 每个文档一条 |
| 补全兜底 `document_words` | 文件里前缀相同的单词，加关键字；在 `.`、`->`、`::` 之后**什么都不给** | — |
| 悬停兜底（`explain_if_preparing`） | 说明模块还在准备 | — |
| agent 工具（`cxx_symbol`、`cxx_references` 等） | 经由同一个会话向引擎查询，有工具级的截止时间；`cxx_diagnostics` 有 `fresh` 参数（默认等待新结果） | 每次调用 |

这些机制都**只认"同一个文档里的同一个词"，而且只保留几秒到几十秒**。悬停和跳转完全没有缓存。

### 1.2 缺口：大型模块项目

测量对象是 Windows 上一个大型模块项目，有 25 个前置模块的实现单元，用 CI windows runner（2 核 4 线程）测量：

- **补全**：引擎答一次要 **3.1–3.5 s**，超过 `EnginePace` 的上限，每次都在 1 s 处回退。回退在 `.` 之后是空列表，所以三轮测量里这个文件的成员补全都是 **0/8**。这 3.1–3.5 s 由三部分组成：
  - 模块输入校验：0.67–1.0 s
  - 编译 + Sema：2.2–2.3 s
  - 结果整理：0.25–0.27 s
- **悬停**：在 2 s 处回退，答案不对。直接用引擎时，在同一个文件上悬停要 7–11 s，这个数字与重建一次 AST 的时间相当：打开的文件比常驻 AST 的数量多。
- **跳转**：一个跨模块的定义 4.5–9.5 s，结果不对。
- 同一项目里只依赖 4 个模块的小文件，补全 0.4–0.7 s。问题集中在依赖多、BMI 大的文件上，而这类文件正是项目里最常编辑的。

## 2. 目标与非目标

**目标**
- G1：稳定之后（项目模型就绪、引擎完成首轮准备），**补全、签名帮助、悬停的响应 p99 ≤ 500 ms**，不论文件多重。跳转：缓存确定时 ≤ 500 ms，否则在引擎的时间内给出正确结果。
- G2：同类请求见过一次后，必然命中缓存。"同类"包括同一位置、同一作用域或类型、同一符号，跨文件、跨会话都算。
- G3：编辑器里，权威结果到达后**无感**替换：不重弹列表，不打乱顺序，不跳光标。
- G4：缓存结果的错误项有界，并且可以度量（第 9 节）。
- G5：agent 和 CLI 拿到的每一个结果，都能知道它的来源和确定性；日志可以按来源检索。
- G6：只用标准 LSP 加 mcppls 已有的自定义通知，所有编辑器都可用；VS Code 体验最好。

**非目标**
- 不在 mcppls 里做语义分析：类型和符号身份只来自标准请求（`typeDefinition`、`definition`）和文本大纲。
- 不改 mcpp，也不改构建数据库格式。
- 冷启动和第一次加载的时间不在本文范围（见 `2026-10-12-windows-performance-plan.md`）。
- 语义高亮、文档符号、诊断不纳入缓存：语义高亮和诊断本来就跟着 AST 走，文档符号和工作区符号已经由 native 层回答。

## 3. 分层与职责

```
┌──────────────────── mcppls：快、交互、可见性 ────────────────────┐
│ 应答层（新，orchestrator/answer）                                 │
│   上下文提取 → 键与指纹 → 多级缓存 → 合成器 → 按请求类型的策略    │
│   引擎代理：去重、不随客户端取消、后台续跑、交互优先、并发上限    │
│   可见性：编辑器无感 / agent 与 CLI 标注 / 日志标记              │
│   刷新：isIncomplete 原地更新；仅一种情况主动拉一次              │
│   预取：空闲时在文件已有的触发点上提问                            │
│   持久化：工作区缓存 + 全局缓存；按代际失效；防污染              │
│ 代际服务（新，汇总已有的信息）：文件监听 + 模块图 + BMI 重建     │
└─────────┬──────────────────────────────────────▲─────────────────┘
          │ 标准 LSP：completion、completionItem/resolve、signatureHelp、
          │ hover、definition、declaration、typeDefinition、implementation
          │ + 输入核对的有效期（E1）+ 交互槽位（E4）+ 常驻 AST 数量（E5）
┌─────────▼──────────────────────────────────────┴─────────────────┐
│ mcppls-clangd：只管正确                                          │
│   给定快照，给出权威答案；不返回不确定的结果                     │
│   正确性前提下的效率补丁 E1、E2、E4，都能提交上游                │
└──────────────────────────────────────────────────────────────────┘
```

**层间约定**

- C1 **引擎不猜**：返回的一定是它在那个快照上算出的结果。
- C2 **mcppls 不改写权威结果**：原样返回，只额外记录它对应的文档版本、代际和键。
- C3 **代际只有一个来源，就是 mcppls**：文件监听、模块图、BMI 重建都在 mcppls 汇总；引擎的输入校验信任 mcppls 的提示（E1）。
- C4 **引擎可以替换**：应答层只用标准请求。引擎不支持某个请求时（比如 `typeDefinition`），对应的学习能力关掉，其余照常工作。
- C5 **每个应答都知道自己是从哪里来的**：应答层内部所有结果都带一个来源记录（见 4.11）。各使用面只决定把它显示到什么程度，不决定有没有。

## 4. 通用框架

### 4.1 上下文提取（同步，目标 < 5 ms）

只读文档文本，借助已有的 native 词法与模块扫描：

| 字段 | 例子 | 用于 |
|---|---|---|
| 位置类型 | 成员访问（`.`、`->`）、限定名（`::`）、无限定、调用实参中、import 行、预处理行 | 选择键与策略 |
| 光标处的标识符，以及它前面的接收者或限定符 | `dump`；`fileOverview`；`std::views`；`fs` | K1、K3 |
| 所在声明 | 外层函数、类、命名空间的名字与起始行 | K1 |
| 已输入的前缀 | `push_b` | 补全过滤 |
| 命名空间别名、`using` | `namespace fs = std::filesystem;` | 规范化 K3 |
| 局部上下文哈希 | 所在声明体内、光标以前的文本 | 判断 K1 是否确定（4.3） |

import 行和空格触发沿用现有逻辑（F9、F15），不经过这一层。

### 4.2 三级键

- **K1 位置键**：(文档，所在声明，位置类型，标识符或接收者、限定符的文字)。最精确，文件私有。"打了又删""同一处反复补全""同一处反复悬停"命中的就是这一级。A1 和 C-2 按词的单条记录保留在它前面，作为同一个词里继续打字的最快路径；K1 补上它们够不到的情况：每个文档可以保留很多条，有效期按代际判断，不再固定为 5–30 s。
- **K2 语义键**：(符号或类型的规范名，定义位置，可见集合指纹)。**跨文件共享。**
  - 限定名：规范化之后直接得到，例如 `fs::path` → `std::filesystem::path`。
  - 成员访问、标识符：符号身份靠**学习**。权威结果回来后，在后台对接收者发 `typeDefinition`，对悬停或跳转的标识符发 `definition`。有常驻 AST 时这些都很便宜。学到的结果记成"(文档，文字，所在声明) → (规范名，定义位置)"。之后同一个符号在任何文件出现，都能映射到 K2。推不出来时（模板依赖、宏）只用 K1。
- **K3 名字键**：(规范化的限定名，工具链与标准库指纹)。用于 K2 还推不出来的时候，比如 `std::`、`std::views::`、`std::vector`。**跨项目共享**，存在全局缓存里。

### 4.3 确定性：指纹与代际

每个缓存条目在被使用时，都要判断它是**确定**还是**不确定**。

**可见集合指纹**：影响可见性的编译参数（标准、`-D`、目标、标准库），加上文件 import 的模块闭包，再加上 preamble 部分（`#include` 与 GMF）的内容哈希。
- 完全一致：指纹相符。
- 不一致但提供该作用域或符号的模块、头文件相同：**兼容**，只能作为不确定的结果使用。
- 其他情况：不使用。

**代际**：每个模块单元、每个文件都有一个整数代际，由 mcppls 在下面三种情况下加一：
- 文件内容变化（编辑器的修改、保存，或者磁盘上的变化）；
- 依赖的模块重建；
- 项目模型更新。

每个条目记下写入时相关模块和文件的代际向量。

**判定**：
- K2、K3：指纹相符，而且提供者的代际一致 → **确定**；否则 → **不确定**。
- K1：除上面两条外，还要求局部上下文哈希一致（光标所在声明里、光标之前的文本没变）→ 确定。否则不确定，并且补全时并入 `document_words` 里的局部单词，补上新出现的局部变量。

### 4.4 存储

| 层 | 内容 | 容量与淘汰 |
|---|---|---|
| 内存 | 全部键的条目 | 按条目数和字节数做 LRU；每个文档的 K1 条目有单独上限 |
| 工作区磁盘缓存 | K1（最近的文档）、K2、学到的符号映射 | 放在工作区的 mcppls 缓存目录，计入 C-8 的缓存预算，`mcppls cache` 统计并清理 |
| 全局磁盘缓存 | K3 | 按工具链加标准库指纹分区，有总量上限 |

- 条目只存显示与插入需要的字段（第 5 节逐类说明）。补全项的文档注释不存，交给 `resolve`。
- 文件格式带版本号，版本不认识就整块丢弃。写入是原子的（先写临时文件再改名）。
- 工作区不受信任时，不写磁盘，只用内存。

### 4.5 引擎代理

- **去重**：同一个 K1 加同一个请求类型，在飞的引擎请求只保留一个。同一个词里继续打字产生的补全请求、在同一处反复悬停，都由缓存回答。这同时降低了引擎的排队。
- **不随客户端取消**：客户端发 `$/cancelRequest` 时，引擎请求继续跑完，结果写进缓存。引擎在收到请求时已经拿到了当时的文本快照，所以之后的编辑不影响这个结果对它那个键的有效性。
- **上限**：
  - 后台续跑同时最多 2 个，超出时最旧的那个真正取消；
  - 单个最长 30 s（C-2 的迟到答案仍是 10 s）；
  - 有交互请求在等时，后台续跑和预取都让路。
- **与现有机制的关系**：
  - A1（按词的完整答案）和 C-2（同一个词等同一个迟到答案）保留，排在应答层前面：同一个词里继续打字，它们比查表更快，也已有完整的测试；应答层处理它们够不到的情况（换了一行、换了文件、打了又删、取消后再问）；
  - `EnginePace` 保留它对 1 s 预算的自适应；有保存的答案时，预算换成应答层的预算。

### 4.6 合成器

1. 收到请求后立即查缓存，并把请求交给引擎代理（去重之后可能并不新发）。
2. 到了截止时间（默认 0.45 s；跳转见 5.4）：
   - 权威结果到了：原样返回，回写缓存；
   - 没到：按 K1 > K2 > K3 > native 取第一个可用的结果，按第 5 节对应请求类型的规则处理后返回；
   - 都没有：返回 native 的结果（补全给单词和关键字，悬停给"准备中"的说明），或者按策略继续等。

### 4.7 用最新文本修正

成员或声明"刚变"时，定义它的文件刚被编辑或保存过，mcppls 手里有最新文本。新增一个**轻量声明大纲**：只做词法级解析，得出 `class`/`struct` 体内的成员名，以及命名空间里声明的名字和行号，拿不准就不出结果。

当某个条目的提供者代际变了：
- **补全**：大纲里新出现的成员补进列表；大纲里已经没有的成员排到最后。两者都算不确定。
- **悬停**：大纲里这个名字已经不在了，就不用这条缓存。
- **跳转**：用大纲在目标文件里重新找到这个名字的声明，只找到一处时才用（5.4）。

同时把相关条目标为过期，安排空闲时刷新。遇到宏、条件编译、模板特化，或者大纲解析失败时，不做修正，只保留不确定标记。

### 4.8 预取

只在空闲时做：2 s 内没有输入，而且没有交互请求在处理。一次一个，用户一打字就暂停。
- **重放文件里已有的触发点**：每个 `x.`、`x->`、`ns::` 后面都是合法的补全位置；光标附近的标识符可以预先悬停和取定义。按离光标的远近排序。
- **打开文件时**：按历史命中次数，预取这个工作区最常用的作用域和符号。
- **代际变化后**：对标为过期、而且最近用过的条目，重新提问一次。
- **CPU 上限**：预取占用的引擎时间不超过空闲时间的一定比例；后台索引在跑时，预取让路。

### 4.9 失效与清理

- 代际不一致的条目不删除，降级成不确定（4.3）。
- 每个条目有一个"最长不确定期"，超过之后不再返回，只等刷新。
- 文档关闭时，它的 K1 条目留在磁盘上，内存里的会被淘汰。

### 4.10 防污染

引擎在状态不好时给出的答案不写入缓存：
- 这个文件的模块加载失败，或者引擎状态是 degraded、doomed（沿用现有的 status 与 issue）；
- 答案为空（空答案只说明"现在答不出"）；
- 请求的快照已经落后当前代际不止一代，而且结果和已有的确定条目冲突。

后台续跑答案的快照如果与当前不同，也只写入它自己那个快照对应的键，并按自己的代际向量记账，不覆盖更新的条目。

### 4.11 来源记录

应答层内部的每一个结果，都带一条来源记录：

```
source     engine | cache:K1 | cache:K2 | cache:K3 | outline | native
certainty  authoritative | certain | uncertain
generation 条目写入时的代际向量摘要，与当前的差异
age        条目年龄（ms）
latency    这次应答的耗时；引擎是否仍在后台计算
```

各使用面怎么用这条记录，见第 6 节。

## 5. 各请求的策略

### 5.1 补全（`textDocument/completion`、`completionItem/resolve`）

- **存储**：`label`、`kind`、`detail`、`labelDetails`、`sortText`、`filterText`、`insertText` 或 `textEdit` 的新文本、`data`。
- **返回缓存结果时**：
  - 用前缀做模糊过滤（规则与编辑器一致），保留原来的 `sortText`，并入关键字（F15）；
  - 用 `retarget` 把每一项的 `textEdit` 范围对准当前光标；
  - 标 `isIncomplete: true`。
- **用户看不见的安全措施**：不确定的项不预选（`preselect: false`），也不设 `commitCharacters`；按大纲判断已经删掉的项排到最后。
- **`resolve`**：缓存项的文档注释，在 `resolve` 时向引擎取，用存下来的 `data`。引擎没有及时回答，就用上一次的注释，没有就不显示。
- **刷新**：见 6.1。

### 5.2 签名帮助（`textDocument/signatureHelp`）

- **K1**：(文档，所在声明，被调用者的文字)；**K2**：(被调用函数的规范名，定义位置，指纹)。
- **存储**：所有签名，以及 `activeSignature`。`activeParameter` 不存，按当前实参位置在文本上现算。
- 不确定的结果照样返回。编辑器在用户输入逗号或括号时会重新请求，到时就是权威结果，原地更新。

### 5.3 悬停（`textDocument/hover`）

- **K1**：(文档，所在声明，标识符，接收者或限定符)；**K2**：(符号规范名，定义位置，指纹)，由 `definition` 学到；**K3**：限定名，比如 `std::vector`。
- **存储**：markdown 内容。`range` 不存，按当前标识符的位置现算。
- 截止时间到时，有可用的缓存就返回。不确定的悬停在编辑器里不加标记（6.1）；下次悬停到这里时，就已经是新结果了。
- 涉及模板实参的悬停，比如 `std::vector<int>` 在不同位置显示的实参不同：只使用 K1，或者在 K2 内容里只保留与实参无关的部分（声明、文档），实参相关的那一段等权威结果。具体规则在实现时依据引擎输出的格式确定。

### 5.4 跳转（`definition`、`declaration`、`typeDefinition`、`implementation`）

跳错位置的代价高，所以策略更保守：

- **确定**：K1 或 K2 命中，而且目标文件自记录以来代际没变 → 立即返回（≤ 500 ms）。
- **目标文件变过**：用声明大纲在目标文件里找同名声明。
  - 只找到一处 → 返回新位置，算不确定；
  - 找到多处，或者一处都没有 → 不用缓存，等引擎。
- 其他情况都等引擎，沿用现有的 10 s 预算。
- `implementation` 可能有多个目标，只在完全确定时才用缓存。

### 5.5 引用与调用关系（`references`、agent 的 `cxx_references`）

- **本轮不缓存。** 结果大、分布在很多文件里，任何一个相关文件变了就是不确定，而查找引用本来就不是按键级别的交互。
- agent 的 `cxx_references` 先通过悬停、跳转定位符号，这两步走应答层，结果的 `provenance` 照常标注（6.2）；引用列表本身总是引擎的。
- 以后要缓存时，键是 (符号规范名，定义位置，`includeDeclaration`、方向)，编辑器里的"查找引用"仍不使用不确定的缓存。

### 5.6 不纳入的请求

语义高亮、诊断、文档高亮、文档符号、工作区符号、格式化、重命名：或者跟着 AST 走，或者已经由 native 层回答，或者必须完全正确（重命名、格式化）。

## 6. 各使用面的可见性

| 使用面 | 截止策略 | 来源的可见性 |
|---|---|---|
| 编辑器（LSP） | 0.45 s；可以用不确定的结果（跳转除外） | 默认几乎看不出来（6.1） |
| agent（MCP 工具） | 默认与编辑器相同，可以用缓存换速度；`mcppls.answer.agent: authoritative` 或单次调用的 `fresh: true` 时等权威结果 | **结果里一定带** `provenance`，其中 `authoritative` 字段直接说明是不是权威结果 |
| CLI 与 report | 不涉及交互截止 | 命中统计、来源分布、缓存体积，都明确输出 |
| 日志 | — | 来源记录：`info` 级只记值得注意的应答，`debug` 级记每一次（6.4） |

请求从哪个使用面进来，由会话标记：LSP 客户端的请求，和 MCP 工具在内部发起的查询，走的是不同的入口。应答层按这个标记选择策略。

### 6.1 编辑器：以无感为核心

**刷新：不重弹列表**
- **R1 用户还在打字**：缓存结果标了 `isIncomplete`，编辑器每次按键都会重新请求。这时直接从已经更新的缓存回答，列表在打字过程中原地变成权威结果。
- **R2 用户停住不动**：不做任何事，下一次按键或下一次打开时自然就是新结果。
- **R3 唯一的主动刷新**：上一次在 `.`、`->`、`::` 之后只给出了空列表或少于 3 项，而且文档版本没变、光标没动、距上次请求不超过 5 s。这时 mcppls 发 `mcppls/completionReady {uri, version, position}`，VS Code 扩展执行一次 `editor.action.triggerSuggest`。对用户来说，这是列表第一次真正出现，和一个稍慢的补全没有区别。其他编辑器忽略这个通知。
- **顺序稳定**：R1 原地更新时，已经显示过的项保持相对顺序；权威结果里新出现的项按权威排序插进去；不存在的项去掉。
- 悬停和跳转没有刷新动作：悬停在下次悬停时就是新的；跳转只给确定的结果，或者经过大纲校验的结果。

**标记：默认看不出来**（设置 `mcppls.completion.provenance`，同时作用于补全和悬停）

| 值 | 补全列表里 | 补全项详情区、悬停卡片 |
|---|---|---|
| `subtle`（默认） | 不确定的项，在 `labelDetails.description` 的末尾加一个细间隔和 `·`；确定的项不加 | 详情区最后一行小字："来自上次的结果，正在确认"；悬停卡片不加 |
| `off` | 不显示 | 不显示 |
| `verbose` | 每一项都标来源：缓存、权威或大纲 | 补全详情和悬停卡片末尾，都写出来源与代际（用于报问题） |

**标记的是项，不是整个列表**。只有真正有疑问的项才带 `·`：
- 按大纲补进来的项；
- 按大纲判断已经不存在、被排到最后的项；
- 条目的提供者（定义该类型或作用域的文件）代际变了、又无法用大纲核对时，这个条目的项。

只因为用户在当前文件里继续编辑而变得不确定的条目，项本身并没有疑问：列表照常返回，标 `isIncomplete`、不预选，但**不加标记**。这样正常打字时几乎看不到 `·`。

### 6.2 agent：速度可选，来源一定明确

- **默认 `mcppls.answer.agent: cached`**：和编辑器一样，可以先用缓存，换取速度。
- **每一个结果都带 `provenance` 对象**（4.11 的来源记录），其中：
  - `authoritative`：`true` 表示是引擎在当前快照上算出的结果，`false` 表示来自缓存或大纲；
  - `source`、`certainty`、`ageMs`、`generationChanged`：细节；
  - 不确定时，另有 `notes`，用一句人能读懂的话说明，例如"成员列表来自 3 分钟前的结果，定义该类型的文件此后修改过"。
- **要权威结果时**：设置 `mcppls.answer.agent: authoritative`，或者在单次调用里传 `fresh: true`。这时等权威结果，直到工具的截止时间；截止时间到了仍没有，就照常返回失败，不用缓存充数。这与 `cxx_diagnostics` 现有的 `fresh` 语义一致，`cxx_symbol`、`cxx_references` 也加上同名参数。
- **跳转类的位置**：不确定的位置只有在 `cached` 模式下才会返回，并且 `authoritative: false`。
- `cxx_review` 和 `cxx_verify` 这类结论依赖正确性的工具，始终只用权威结果，不受设置影响。

### 6.3 CLI 与 report

- `cxxModules/report`、`mcppls report` 和诊断包里，新增"应答层"一节：
  - 按请求类型列出命中率（K1/K2/K3/outline/native/engine）；
  - 响应 p50/p99；
  - 收敛时间；
  - 误项率；
  - 后台续跑与预取的次数；
  - 缓存体积。
- `mcppls cache` 统计并清理工作区和全局两级缓存，规则沿用 C-8。
- 诊断包默认只带统计，不带缓存内容（缓存里有项目的符号名）。只有显式加 `--include-answer-cache` 时才带，而且经过现有的脱敏处理。

### 6.4 日志

格式统一、方便检索，但保持克制：

- **`info` 级只记值得注意的应答**：
  - 返回了不确定的缓存结果；
  - 权威结果到达后，和先给出的缓存结果不一样（写出差了几项）；
  - 权威结果迟于截止时间 3 倍以上。
- **`debug` 级记每一次应答**，以及预取、去重、防污染丢弃、失效降级。
- **进程启动时一行 `info`**：缓存条目数、体积、版本、读入耗时。
- **按会话汇总**的命中率、响应时间等，在 report 里看（6.3），不刷日志。

## 7. 引擎侧（mcppls-clangd，正确性前提下的效率）

| 编号 | 内容 | 针对 | 预期 | 把握 |
|---|---|---|---|---|
| **E1** | 模块输入校验按代际记住结果：项目内的输入（包括 `-I` 引入的第三方树）校验一次之后，在下一次输入变化提示之前不再重复 stat。提示用 `workspace/didChangeWatchedFiles`（mcppls 本来就在监听），另加一条引擎专用通知，用来告诉它"某一代所有输入都没变" | 每次补全 0.67–1.0 s | **−0.7–1.0 s** | 高（直接测得） |
| **E2** | ForceLoadPreamble 只用于真的 import 了模块的文件。它的作用是让 Sema 在补全时读入外部声明，因为索引里没有模块的符号；不 import 模块的文件，preamble 的符号索引里都有。"import 了模块"按这次请求看到的为准：preamble 之后才加上的 import（文件里新打的，或者经由某个头文件带进来的）只为这次请求构建，索引里还没有，仍要读入；文件里有 import 行时直接判定，否则用请求本来就要做的模块扫描（整次补全只重放一次）。成员访问和限定名补全仍然需要读入外部声明，所以不能按补全位置区分 | 头文件为主、但开着模块支持的文件 | 每次补全 −0.15–0.3 s（测得：同一个头文件，开关模块支持前后相差这么多） | 高 |
| **E3** | ~~补全项的文档注释改到 `resolve` 时再取~~ **不做**：clangd 本来就不解析简要注释（`IncludeBriefComments=false`），完整注释是补全项的文档内容；推迟到 `resolve` 需要 clangd 先支持 `completionItem/resolve`，代价和收益都不在本轮 | — | — | — |
| **E4** | 交互请求优先：补全和签名帮助使用单独的并发槽，不和其他文件的 preamble 构建、AST 构建排同一个队 | 请求成串时、以及准备期间的排队 | 排队时间 | 高 |
| **E5** | 常驻 AST 的数量按内存分档：15 GiB 以上 8 个，31 GiB 以上 12 个（按可用于判断的总内存取整，16/32 GB 的机器报告的值略小于整数；之前是 6 个或默认 3 个）。clangd 的这个选项只在启动时生效，所以按内存而不是按打开的文件数定 | 打开的文件比常驻 AST 多时，悬停和跳转要重建 AST | 悬停、跳转从秒级降到毫秒级（待验证） | 中 |

E1 的具体做法：新增引擎选项"项目输入的复查间隔"（默认 0，即每次都查，行为不变）。mcppls 设为 10 s。间隔内，项目输入的校验结论直接复用；收到 `didSave`，或者收到 `workspace/didChangeWatchedFiles` 且其中有校验过的输入文件时，立即作废。这样文件监听漏掉的磁盘变化，最多晚 10 s 被发现，这与 clang 自己"每个构建会话只校验一次"的选项是同一类取舍。

- 每个补丁都有开关，默认行为不变，直到测量证明收益；写法上不包含任何产品相关的内容，能直接提交上游。
- E5 只是 mcppls 侧的用法调整，不改引擎。

## 8. 与现有设置、行为的关系

- `MCPPLS_COMPLETION_REFILTER=off` 保留，作用同 `cache=off`。
- R-7 的预算继续存在：它变成"没有任何可用缓存时等引擎多久"，补全和悬停默认仍然是 1 s 和 2 s，跳转仍然是 10 s。新的 0.45 s 截止时间只在有可用缓存时生效。
- F9、F15、import 行补全、keywords 的合并都不变。

## 9. 指标与测试

### 9.1 指标

由 report 和 `cxxModules/report` 输出，bench 和 conformance 直接读取。

| 指标 | 定义 | 目标 |
|---|---|---|
| 响应 p50/p99 | 每类请求从收到到返回（稳定后） | 补全、签名、悬停 p99 ≤ 500 ms；确定的跳转 ≤ 500 ms |
| 命中率 | 按请求类型和来源统计 | 稳定后，补全的引擎加缓存命中 ≥ 95% |
| 收敛时间 | 从返回缓存结果，到同一个键的权威结果写入 | 大型模块文件 ≤ 3 s（E1、E2、E4 之后 ≤ 2 s） |
| 补全误项率 | 缓存结果里不在随后权威结果中的项的比例；**选中的项**单独统计 | 选中误项率 ≤ 0.1% |
| 补全漏项率 | 权威结果里有、缓存结果里没有，而用户最终输入的正是这个名字 | 记录并跟踪 |
| 悬停不一致率 | 缓存悬停与随后权威悬停内容不同的比例 | 记录并跟踪 |
| 跳转错误率 | 返回的缓存或大纲位置与权威位置不同的比例 | ≤ 0.1% |
| 主动刷新次数 | R3 触发次数占补全请求的比例 | 接近 0 |
| 不确定项占比 | 带 `·` 的项占全部返回项的比例 | 正常打字时接近 0 |
| 每个词的引擎请求数 | 去重效果 | ≤ 1 |
| 缓存体积与读入耗时 | 内存、工作区磁盘、全局磁盘；启动时读入 | 在预算之内；读入 ≤ 200 ms |

### 9.2 测试

- **单元测试**：
  - 键与指纹（别名展开、前缀、所在声明、局部上下文哈希）；
  - 代际向量的比较与确定性判定；
  - 合成器在各请求类型下的分支选择；
  - 顺序稳定的合并；
  - `retarget` 与悬停 `range` 的重算；
  - 声明大纲（成员、命名空间名、宏和条件编译时退出）；
  - 防污染规则；
  - 持久化文件的版本处理与损坏恢复；
  - 来源记录与日志格式。
- **conformance**（mock 引擎可以设定延迟与答案）：
  - 补全：引擎 3 s 才答时响应 ≤ 500 ms 并收敛；打了又删；跨文件同一作用域；类型加一个成员、删一个成员；热启动第一次按键；R3 只在空结果时触发；后台续跑上限；
  - 签名帮助：缓存结果立即返回，输入逗号后变成权威结果；
  - 悬停：同一处、同一符号跨文件；定义文件改动后不用过期的悬停；
  - 跳转：目标文件未变时立即返回；变了且大纲唯一命中时返回新行；有歧义时等引擎；
  - agent：默认等权威结果；`fresh: false` 时结果里带 `provenance` 和 `notes`；`cxx_review` 只用权威结果；
  - 防污染：模块加载失败期间的答案不进缓存；
  - 不受信任的工作区不写磁盘；`cache=off` 与 0.0.14 的行为一致。
  - **所有现有 fixture 默认用独立的新缓存目录**，避免缓存让结果依赖运行顺序；缓存相关的 fixture 显式准备缓存。
- **engine-bench**（Windows，大型模块项目）：在现有的打字、悬停、跳转场景上，加入跨文件、打了又删、类型变化、热启动四类用例，逐项输出 9.1 的指标。
- **VS Code e2e**：R1 原地更新；R3 只触发一次；默认档位下补全和悬停都没有可见标记；跳转不出现"跳了又跳"。

## 10. 设置与兼容

| 设置 | 取值 | 默认 | 说明 |
|---|---|---|---|
| `mcppls.answer.budget` | 100–2000 ms | 450 | 有可用缓存时，补全、签名帮助、悬停的截止时间 |
| `mcppls.answer.cache` | `on`、`memory`、`off` | `on` | `memory` 不写磁盘；`off` 回到 0.0.14 的行为 |
| `mcppls.answer.prefetch` | `on`、`off` | `on` | 4.8 |
| `mcppls.completion.provenance` | `subtle`、`off`、`verbose` | `subtle` | 6.1；同时作用于悬停 |
| `mcppls.answer.agent` | `cached`、`authoritative` | `cached` | 6.2；单次调用的 `fresh: true` 优先 |

- **升级无感**：第一次运行新版本时，缓存从空开始积累；旧格式自动作废。没有新增必填设置。
- 不认识 `completionReady` 的编辑器不受影响，只是少了 R3。
- agent 工具新增的 `fresh` 参数默认 `true`，结果里新增 `provenance` 字段，都向后兼容。
- 设置的中英文文档（`docs/30-settings.md` 与 `docs/zh-CN` 对应页面）、`docs/40-agents.md`、`docs/50-troubleshooting.md`（新的日志行怎么读），随实现一起更新。

## 11. 风险

| 风险 | 后果 | 处理 |
|---|---|---|
| 成员刚变，用户正好选了已删的成员 | 插入一个不存在的名字，几秒后诊断报错 | 大纲修正把它排到最后；不预选；单独统计选中误项率 |
| 成员刚加，缓存里没有 | 晚 1.5–3 s 出现 | 大纲修正补进来；R1 原地更新 |
| 局部变量刚加 | K1 缓存里没有 | 局部上下文哈希不一致时并入 `document_words` |
| 跳到旧位置 | 光标落错 | 只用确定的结果，或者大纲唯一命中的结果；其他情况等引擎；统计跳转错误率 |
| 悬停显示旧内容 | 一次看到旧签名或旧注释 | 定义文件代际变了、大纲里名字不在就不用；下次悬停即更新 |
| 同一文件在不同上下文里 | 成员集合不同 | 指纹里包含上下文；不同上下文之间只允许兼容命中，并算不确定 |
| 引擎在出问题时给出的答案被缓存 | 坏结果被反复使用 | 防污染（4.10） |
| 缓存占用内存、磁盘 | 资源压力 | 计入 C-8；LRU 和上限；`mcppls cache` 可见可清理 |
| 磁盘缓存里有项目的符号名 | 本机数据 | 只存在工作区缓存目录和用户缓存目录；不上传；诊断包默认不带；不受信任的工作区不写 |
| 后台续跑和预取抢占引擎 | 交互变慢 | 并发上限；交互优先（E4）；打字时预取暂停 |
| 学到的符号映射错了 | 用了错误符号的结果 | 映射也带代际；权威结果到达时校验，不一致就删除映射 |
| 缓存让测试结果依赖运行顺序 | 结果不稳定 | fixture 默认用独立的新缓存目录 |
| `isIncomplete` 让编辑器每次按键都请求 | 请求数增加 | 缓存回答在 5 ms 以内；去重保证不放大到引擎 |

## 12. 计划：一个版本完成（mcppls 0.0.15，mcppls-clangd 0.0.16）

### 12.1 拆分原则（多视角）

- **架构**：应答层是一个独立模块（`mcppls.orchestrator.answer`），对外只有"查缓存、合成、记录、学习、持久化"几个入口，不依赖 workspace 的内部状态，可以单独测试；workspace 只负责把请求、答案和代际事件交给它。声明大纲是另一个独立模块（`mcppls.orchestrator.outline`）。
- **稳定性**：所有新行为都有开关；`answer.cache=off` 时，路由与 0.0.14 完全一致（A1、C-2 的单测和 conformance 照常通过）。后台续跑、预取、持久化都有上限。
- **优雅简洁**：A1、C-2 只管同一个词，应答层管其余，职责不重叠；引擎侧每个补丁只做一件事。
- **用户体验**：编辑器默认无感；agent 结果明确标注；日志克制。
- **兼容性**：只用标准 LSP 和已有的自定义通知机制；新字段向后兼容；引擎的新选项默认关闭，旧引擎上 mcppls 照常工作（按能力声明决定是否传选项）。
- **跨平台**：应答层与平台无关；持久化路径走已有的缓存目录 API；引擎补丁在三个平台的 CI 上构建和测试。
- **一致性**：缓存预算、清理、报告并入 C-8、`mcppls cache`、report；设置走统一的设置表（文档由它生成和校验）。
- **无感升级**：缓存格式带版本号，旧格式作废；没有新的必填设置；引擎升级沿用 payload 的版本锁定。

## 13. 多视角自审

自审时发现的问题，已经改进到上文中的，标为"已改"。

**架构**
- 快和对分开，两侧各有独立的指标；应答层只依赖标准请求，换引擎不受影响。
- 一套通用框架，加上按请求类型的策略表，没有为每种请求各写一套缓存。
- 已改：可见性做成"每个结果都带来源记录（C5），各使用面决定显示多少"，而不是只有编辑器有标记。这样 agent、CLI、日志共用同一份数据。
- 已改：A1、C-2 保留在应答层前面、只管同一个词，应答层不重复它们的规则（4.5），避免两套规则互相干扰，也不必重写它们已有的测试。

**正确性**
- 权威结果总会覆盖缓存结果；跳转只用确定的结果或者大纲唯一命中的结果。
- 已改：K1 原先只看所在声明，局部变量刚加时会漏，改成同时看局部上下文哈希，不一致时并入局部单词（4.3）。
- 已改：增加防污染（4.10），模块加载失败期间的答案不进缓存。
- 已改：缓存项的 `textEdit` 范围和悬停的 `range` 都按当前位置重算（5.1、5.3）。
- 剩余风险：模板实参相关的悬停，在不同位置内容不同，只能保守处理（5.3），实现时需要依据引擎输出的格式细化。

**稳定性**
- 后台续跑和预取都有上限和让路规则；磁盘缓存原子写入、带版本号、损坏可以恢复。
- 已改：测试默认使用独立的新缓存目录，避免缓存让 conformance 结果依赖运行顺序（9.2）。

**体验**
- 编辑器里默认没有可见变化，只是变快：不重弹列表，悬停和跳转没有刷新动作，标记只在细看时才能发现。
- agent 默认拿权威结果，不会被缓存"悄悄"影响；需要速度时显式传 `fresh: false`，并且能看到来源。

**性能**
- 缓存应答在 5 ms 以内，所以 `isIncomplete` 带来的额外请求不放大到引擎。
- 去重让引擎在打字期间的请求数降到每个词至多一个，权威结果本身也会因为排队变短而更快。
- 启动时读入缓存要设上限（≤ 200 ms），超过就异步读入，先用内存里已有的。

**兼容性与无感升级**
- 不认识自定义通知的编辑器照常工作；`cache=off` 回到 0.0.14 的行为；agent 的新参数和新字段向后兼容；旧缓存格式自动作废。

**跨平台**
- 没有平台相关的逻辑。E1 在 Windows 上收益最大，在其他平台上也有收益。

**安全与隐私**
- 缓存只在本机；诊断包默认不带缓存内容；不受信任的工作区不写磁盘。

**一致性**
- 缓存预算、清理、报告并入现有的 C-8、`mcppls cache`、report 与诊断包；agent 的 `fresh` 沿用 `cxx_diagnostics` 的语义；日志沿用现有的级别约定。

**仍需在实现前确认的**
- 0.45 s、后台续跑上限（2 个、30 s）、R3 的阈值（少于 3 项、5 s 内）这些数值，用阶段 0 和阶段 1 的数据校准。
- E5 的常驻 AST 上限与内存预算的关系。
- K3 全局缓存的总量上限，以及按工具链分区的粒度。
