## 0. 摘要

### 0.1 结论

1. **"没有关键字 / 变量补全"不是 mcppls 答错了，而是 VS Code 根本没来问（已验证）。** 用户会话 18 分钟里 inlayHint 485 次、
   semanticTokens 311 次、codeAction 223 次，补全只有 24 次；用户专门复现的 66 秒里（两个诊断包之间）补全请求 **0 次**，
   同一时间 Copilot 发了 15 次内联补全、5 次 NES。到了服务端的那 24 次答得很快（p50 21 ms、p95 60 ms、最慢 119 ms，0 空、0 错）。
   原因：VS Code 在 1.108 之后、1.125 之前把 `editor.quickSuggestions.other` 的默认值从 `"on"` 改成了
   **`"offWhenInlineCompletions"`**。有内联补全提供者（1.132 内置 Copilot）时，每次按键先等内联补全：Copilot 给出了灰字就**不弹补全列表**；
   Copilot 没给出，要等它答完或 750 ms，并且这期间文档和光标都没动，才弹。于是"多数时候没有，停下来等一会儿偶尔有"。
   重启语言服务器无效是因为问题在编辑器侧。我们的 E2E 在没有内联提供者的干净配置里跑，conformance 直接说 LSP，都看不到它。
2. **修法：扩展用 `configurationDefaults` 把 `[cpp]`、`[c]` 的 `editor.quickSuggestions` 设回 `{"other": "on"}`（E-1，WA-VSCODE-002）。**
   `on` 就是 1.125 之前的默认：补全列表立即弹，Copilot 的灰字照常并行出现。1.132 实测：新装用户在 C/C++ 里生效，其他语言不受影响，
   用户自己写的 `[cpp]` 设置优先；唯一的代价是用户在全局（不分语言）写过的 `editor.quickSuggestions` 在 C/C++ 里会被这个默认值盖过，
   用启动时的一行日志和 README 说明（E-2）。诊断包补上决定补全的编辑器设置（E-3），下次一份包就能看出"编辑器没来问"。
3. **写模块时，自动保存会让模块自己和它的导入者整个离开 clangd（已验证，0.0.7 的真实缺陷，与第 1 条无关）。** 半截代码被自动保存到磁盘
   → clangd 编这个模块失败 → RP1.1 的遏制把**提供该模块的文件本身**和导入它的文件都判为 doomed：clangd 那边 `didClose`，诊断换成一条
   "module hello did not compile: Failed to compile …"，补全由 mcppls 自己的引擎回答（只有模块语法，对 `i`、`a_` 返回空）。下次保存又交回
   clangd、整份重建，再失败再 doom。复现：连续编辑 92 秒里 doom 18 次、交回 17 次；**正在编辑的模块文件里 223 次补全有 106 次（48%）在
   2 ms 内返回空**。用户这次的会话没有触发它（日志里没有 doom 事件），但它就在"写模块、开自动保存"这条最常见的路上。
4. **修法：正在编辑的模块失败不算 doomed（M-1）；clangd 不服务的文件，补全也至少有本文件的词和关键字（M-2）。** 不 doom 时 clangd 的表现
   （clangd 直连实测）：被编辑的模块用缓冲区编译，真实诊断与补全都在；导入者上 clangd 报一条模块错误，局部变量、参数、关键字照常补全（4 ms），
   但这段时间里其他模块的名字（含 `std::`）补不出来，模块重新编过后恢复。
5. **`preparation-stalled` 在用户编辑正被预建的模块时误报（已观察，M-3）。** 用户会话里 clangd 重启后一分钟，hello.cppm 在这一分钟里被重建 82 次，
   预建停在 1/2，mcppls 写了诊断包并通知"mcppls cannot recover from preparation-stalled by itself"；0.3 s 后那个 prime 单元就完成了。
   修法：被预建闭包里的源文件在改，算作进展；只有在这段时间里没人改它，才报 stalled、写包、通知。
6. **#34 的五项进 0.0.8**：K-3 让 Windows 过渡模型崩溃（#34-1）与扇出保存崩溃（#34-3）带着栈转储与 clangd 身份报上游（上游的 clangd 没有符号，
   第 2 版改写）；R-4（过渡模型不预建项目模块）缩短崩溃暴露并改善 mcpp 的首答；P-1 让部分模型的替身一次进场（一次重启）；U-* 预算的分布由 nightly
   汇总、两周后收紧，K-6 让已 settle 的状态不再随保存闪烁；O-6 Open VSX 多等一会儿。

## 1. VS Code 不来要补全（E-*）

### 1.1 现场（已验证）

| 来源 | 数据 |
|---|---|
| 诊断包（服务端 uptime 1063 s → 1130 s） | 补全 24 → 24 次（clangd 22、mcppls 2，后者是 `import` 后的空格）；inlayHint 431 → 485；codeAction 196 → 223；documentHighlight 5 → 10；signatureHelp 12 → 16 |
| 同一窗口的 Copilot 日志 | 整个会话内联补全 166 次、NES 37 次；两个包之间 15 次、5 次，每次 300–600 ms，全部 200 |
| 服务端作答 | 24 次：p50 21 ms、p95 60 ms、最慢 119 ms；0 空、0 错、0 取消；clangd ready，无 doomed、无扣住的请求 |
| 用户设置 | 没有 `editor.quickSuggestions`、`editor.inlineSuggest.*`；`files.autoSave: afterDelay`；cpptools、clice、mcpp-vscode 全局禁用，vscode-clangd `clangd.enable: false` |

服务端没有丢请求的路径：`session.cpp:298` 把每个请求交给根目录，`Workspace::route_client_request` 每个请求建一个 job，结束时 `note_request` 计数；
空格触发的另计（`spaceTrigger`，这次 2 次）。所以计数不动 = 请求没来。

排除过的：注入语法把代码标成字符串或注释（用 VS Code 1.132 的 cpp 语法加 `mcppls-modules.tmLanguage.json` 离线分词用户的 main.cpp，光标处不是
comment / string）；扩展的 completion 中间件（只丢不在 import 行的空格触发）；别的 C++ 扩展（都已禁用）；Copilot 的 `suppressSuggestions`（它的扩展代码里没有）。

同一段代码在 LSP 直连下（新会话、自动保存）一切正常：行首 `i` → `int`（第 2–3 项，21–35 ms），`re` → `return expression;`，函数体里 `a_` → 第一项 `a_number`。

### 1.2 根因（已验证：VS Code 源码）

1.132 的 `_doTriggerQuickSuggest`：按光标处的 token 类型取 `quickSuggestions` 的值；值为 `offWhenInlineCompletions` 且存在内联补全提供者、
`editor.inlineSuggest.enabled` 时，走 `_waitForInlineCompletionsAndTrigger`：

- 内联模型已有建议 → 直接返回，**不触发补全**；
- 否则等：内联模型答完且没有建议，或 750 ms 到点，才 `trigger({auto: true})`，并且要求**文档版本与光标位置与开始时相同**、编辑器有焦点——
  750 ms 内又按了键，这一轮作废。

默认值：1.108.0 `{other: "on", …}`；1.125.1、1.132.0 `{other: "offWhenInlineCompletions", …}`（本机三个版本的 workbench 代码）。1.132 内置 Copilot。
扩展声明 `engines.vscode: ^1.91.0`，1.125 以后装了 Copilot（或其他内联补全）的用户都在这条路上。触发字符（`.`、`::`）与手动 Ctrl+Space 不经过这个分支
（推断：用户那 22 次 clangd 作答多半来自 `std::` / `hello::` 与停顿）。

### 1.3 为什么我们的测试没看到

- conformance 与 ux-* 场景直接说 LSP，不经过 VS Code 的建议逻辑；
- VS Code E2E 用新的 `--user-data-dir` 与 `--disable-extensions` 启动（`test/runTest.ts:250-253`），只有被测的 VSIX，没有内联补全提供者，
  `inlineCompletionsProvider.has()` 为假，走的是直接触发。

### 1.4 修法

**E-1（P0）`configurationDefaults`。** `editors/vscode/package.json`：

```json
"configurationDefaults": {
  "[cpp]": { "editor.quickSuggestions": { "other": "on", "comments": "off", "strings": "off" } },
  "[c]":   { "editor.quickSuggestions": { "other": "on", "comments": "off", "strings": "off" } }
}
```

`on` 即"并行"：补全列表随打字立即弹出，内联补全照常独立运行，列表打开时 VS Code 按选中项预览灰字（1.125 之前的默认体验）。VS Code 1.132 实测
（探针扩展只声明上面的默认值，干净 user-data-dir）：

| 用户设置 | cpp 的实际值 | python 的实际值 |
|---|---|---|
| 无 | `on` | `offWhenInlineCompletions` |
| 全局 `"editor.quickSuggestions": {"other": "off", …}` | `on`（语言默认值高于非语言的用户值） | `off` |
| `"[cpp]": {"editor.quickSuggestions": {"other": "offWhenInlineCompletions"}}` | 用户的值 | `offWhenInlineCompletions` |

登记为 **WA-VSCODE-002**（`editors/vscode/src/workarounds.ts`，与 WA-VSCODE-001 同格式）：affects "VS Code ≥1.125 的 `quickSuggestions` 默认值
`offWhenInlineCompletions`"；removeWhen "VS Code 的默认值让补全列表与内联补全并行触发"；canary 见 E-4。

老版本（1.91–1.108）的默认本来就是 `on`，没有变化。服务端负载：每次按键多一个补全请求，0.0.7 已有 1 s 预算与回退，用户会话里实测 p95 60 ms。

## 2. 写模块时补全和诊断掉线（M-*）

### 2.1 复现（已验证：LSP 直连，0.0.7 payload，hello111 副本）

| 轮 | 做了什么 | 结果 |
|---|---|---|
| run5 | 新会话，在 main.cpp 全局作用域逐键写 `int add(int a_number, int b_number) { return a_ }`，自动保存 | 36 次补全全部由 clangd 作答，`int`、`return expression;`、`a_number` 都在，最慢 35 ms |
| run4 | 在 hello.cppm 里写到 `int s = a + b; re`，自动保存后回到 main.cpp | clangd `Failed to build module hello` → `3 files routed to mcppls's own engine`；此后 main.cpp 的补全 6/6 在 0 ms 返回空（`i` 没有 `int`） |
| run6 | 两个文件都打开，服务一启动就在 hello.cppm 里分段写函数（停 1.3 s 自动保存，有的停在半句），约 110 s | 92 s 内 doom 18 次、交回 17 次（间隔 0.6–8 s）；hello.cppm 里 223 次补全有 **106 次在 2 ms 内返回空**，93 次有结果；停手后 main.cpp 的补全仍为空（最后一次保存的内容编不过） |

用户这次的会话没有走到这里（服务端日志没有 `routed` / `module-failed` 事件），但开着 `files.autoSave` 写模块，每次停顿都会把半截代码写到磁盘。

### 2.2 机制（代码确认）

- clangd 报 `Failed to build module X`（`FailureKind::compile`）→ `doomRoots_` 加 X，记下闭包里每个源文件的时间戳 → `recompute_doom_`：X、
  所有传递导入 X 的模块、**提供它们的文件**和直接导入者都进 `doomedFiles_`；
- `mark_doomed_`：对 clangd `didClose` 这个文件，诊断换成 `publish_doom_diagnostic_` 的一条：`module hello did not compile: Failed to compile
  …/hello.cppm. Use '--log=verbose' …`（clangd 的原因字符串，没有错误位置），`claims()` 对它返回假，请求只问 mcppls 自己的引擎；
- `forget_changed_doom_`：闭包里任一源文件的时间戳变了 → 忘掉这个根 → `release_doomed_` 清诊断、重新 `didOpen` → clangd 整份重建 → 又失败 → 又 doom。

RP1.1 为的是"一个永远编不过的模块（第三方、工具链问题）不让它的导入者一直等 clangd、不触发重启"。它没有区分"模块坏了"和"有人正在写这个模块"——
后者编不过是常态。

### 2.3 不 doom 时 clangd 怎么表现（已验证：clangd 直连）

同一份引擎数据库，hello.cppm 在磁盘上是半截的（`{ retu }`），直接对 clangd 打开 main.cpp：clangd 记 `Failed to build module hello`，main.cpp 有一条
"Module file …"诊断；补全 `a_` → `a_number`（4 ms），`i` → `if`、`int`，`std::pr` → 空（前置模块失败时这次解析里所有模块都没加载）。被编辑的模块本身
是打开的文件，clangd 用缓冲区编译，诊断与补全都是真实的。

即：不 doom，被编辑的模块完全正常，导入者保住局部变量、参数、关键字，暂时失去其他模块的名字；doom，两者都只剩空列表和一条没有位置的错误。

### 2.4 修法

**M-1（P0）正在编辑的模块失败不 doom。** "正在编辑"：失败模块自己的单元，或它闭包里的某个源文件，在编辑器里打开并且 `EDITING_GRACE`（2 分钟）内有
`didChange`。此时：

- 不进 `doomRoots_`，记 `module-failed-while-editing` 事件（带模块、原因、正在编辑的文件）；
- 提供者与打开的导入者留在 clangd，照常答；不给它们换 mcppls 的诊断；
- RP1.3 照旧：不预建这个闭包里的模块（预建一定失败，只会占 worker）；
- 不因此重启 clangd，不报 `modules-doomed`；状态不变（错误已经在编辑器里）；
- 最后一次编辑 2 分钟后仍然失败，或所有闭包源文件都关掉了，按 RP1.1 doom（此时才是"模块坏了"）。

代价：编辑期间导入者每次重建都会让 clangd 再试一次这个模块（只对打开的导入者；这个模块就是用户正在写的那个，通常不大）；
导入者补不出其他模块的名字，直到模块重新编过。

**M-2（P0）补全永远有底。** 补全请求在路由时没有 clangd 可问（`claims()` 为假：doomed、F16 隔离、放在一边、崩溃退避、不可用），不再只问 mcppls 引擎、
得到空时回 `null`，而是走 `answer_without_core` 的同一条路：本文件里首字母相同的词 + 关键字（F15），`isIncomplete: true`。与 R-7 共用
`completion::document_words`，不新增逻辑。这也覆盖 K-2 退避期间和 F16 隔离期间的补全。

**M-3（P1）编辑中的预建不算 stalled。** `pump_primer_` 的进展时间（`lastPrimeProgressAt_`）在"进行中的 prime 单元的闭包源文件收到 didChange / 磁盘变化"时
也刷新；`preparation-stalled` 的自动诊断包与通知额外要求 stall 窗口里没有这样的改动。report 的 `preparation` 加 `running`：每个进行中的 prime 单元、
开始时间、clangd 对它的文件状态，下次能直接看出卡在哪。用户现场的机制（为什么 prime 单元一分钟没完成）是推断，M-3 之后用 U16 的时间线确认。

**M-4（P0）U16：写模块 + 自动保存。** 在 ux 套件里加：打开一个模块接口与它的一个导入者，在接口里按段写函数 90 s（150 ms 一键，每段停 1.3 s 自动保存，
约一半停在半句），同时在接口与导入者里按键要补全。预算：

| 检查 | 预算 |
|---|---|
| 被编辑模块的 doom 事件 | 0 |
| 补全返回 0 项（本文件有首字母相同的词时） | 0 |
| 补全 p95 | ≤ 1.1 s |
| `preparation-stalled`、clangd 重启 | 0 |
| 被编辑模块的诊断来源 | clangd（没有 `module-failed`） |
| 停手 2 分钟后仍编不过 | doom 生效（RP1.1 行为不退化） |

在 hello fixture（PR 阶段，几秒）、mcpp（一个被少量模块导入的接口）、xlings 上跑。

## 3. 0.0.7 的遗留（#34）

**3.1 Windows：过渡模型阶段 clangd 崩 4–5 次（#34-1）。** K-3（P1，第 2 版改写）：payload 的 clangd 来自 clangd/clangd 的发布包
（`packaging/payload.lock.json`），Linux 版 `file` 显示 `stripped`、`nm` 无符号，三个平台的发布包都不带 `.pdb` / `.debug`；自己从源码编带调试信息的
clangd 需要 20–40 GB 磁盘与数小时 CI，不在 0.0.8。能做且有用的是：崩溃时 incident 与 `lastExit` 记下 LLVM 打印的栈转储（`Stack dump:` 之后的编号条目与
` #N 0x… (clangd+0x…)` 帧，最多 64 行，没有 "Signalled …" 上下文的崩溃也记）和 clangd 的版本与可执行文件 SHA-256——上游持有同一构建的人可以据此还原，
我们自己日后有带符号的同版本构建时也可以。拿到带栈的 incident 后登记 #24、报上游。R-4（P1）：没有缓存、producer 还没回答时只预建 std，项目模块等 producer 的模型；这同时缩短崩溃暴露（崩溃只在过渡模型阶段出现）
与 mcpp 冷启动时被作废的 BMI（U4 首答 150 s 的主因之一）。验收：GalTranslPP 冷启动 0 次崩溃（或崩溃栈已符号化并登记）、U4 mcpp 首答预算收紧。

**3.2 部分模型的替身一次进场（#34-2，P-1，第 2 版改写）。** 探针 run 36676829043 的 `e-warm/restart-clean/server1-stderr.log`（已验证）：每次 clangd
重启后约 23–26 s，clangd 报**一个** `Failed to build module X; due to Don't get the module unit for module X`（依次 AbslContainers、GPPI18n、jpcre2、
nlohmann.json），mcppls 给 X 替身 → "a module's unit left the engine database (X)" → 2 s 后重启——一次会话只报一个，因为 clangd 构建打开文件时停在
第一个解析不了的 import 上。所以第 1 版"安静 5 s 再合并"合并不到第二个。同一份日志里，clangd 在报第一个之前早已逐个记下 `Scanning modules
dependencies for …\AbslContainers.ixx failed: 'absl/container/flat_hash_map.h' file not found`（以及 spdlog、utf8cpp、CodePageChecker 等），mcppls 也已把它们
解析为扫描失败。改为：clangd 报出第一个"提供者单元已在计划里却找不到"的模块时，把所有提供者单元在本次 clangd 里因头文件找不到或命令被拒而扫描失败、

fixture：三个模块单元在全局模块片段里 `#include` 一个找不到的头文件，main.cpp 全部导入，断言"单元离开数据库"引起的重启 ≤ 1 次。

**3.3 扇出保存崩溃（#34-3，UP-20）。** K-3 之后最小复现、报上游；U7b 在上游修好之前留在 nightly 的 long 阶段。

- **每个现象是否闭环**：用户的"没有关键字 / 变量补全、偶尔等几秒才有"→ E-1（根因已验证，修法已在 1.132 实测生效）；"重启无效"→ 同一原因；
  "性能差"→ 服务端 p95 60 ms，感觉到的是等 Copilot 与 750 ms 的条件触发，E-1 之后不再等。写模块时的掉线 → M-1、M-2（复现 + 代码确认）。
  `preparation-stalled` 误报 → M-3（现象已观察，机制推断，靠 U16 与 report 字段确认）。`hello::` → 不是缺陷。
- **E-1 的风险**：改变的是 VS Code 对所有 C/C++ 用户的默认；即使 mcppls 在某个工作区被关掉（`mcppls.enable`），这个默认值仍在（此时相当于 1.125 之前的 VS Code）。
  喜欢"Copilot 优先"的人要自己写 `[cpp]`。每次按键多一个请求，服务端已有预算与回退。
- **M-1 的风险**：一个真正坏掉、又被人反复打开修改的模块，在 2 分钟窗口里仍会让打开的导入者重试它；只影响打开的文件，不影响预建与重启。
  RP1.1 的原场景（没人编辑的失败模块）行为不变，由 failing-base fixture 卡住。
- **证据的边界**：用户现场的 stalled 机制未复现；run6 的脚本在最后几段留下了重复定义（模块确实编不过），不影响"编辑期间翻转"的结论；
  VS Code 默认值改变的具体版本在 1.109–1.125 之间，未定位到版本号；"触发字符与 Ctrl+Space 不受影响"是读代码的推断，E-1 之后不再重要。
- **复现脚本**：LSP 驱动（逐键 didChange、自动保存、记录每次补全的作答者与耗时）在这次会话的 scratchpad 里，不入库；U16 在 ux 套件里重写同样的动作。
