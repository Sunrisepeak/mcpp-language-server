## 0. 结论

1. **发布目标是 0.0.17 全绿**（D4）。这意味着在最终 head 上，PR CI 和 nightly 的**每一个 job** 都要通过，包括 continue-on-error 的 termux 和 two-core。对照这个目标，初稿漏了两项必须处理的工作：U13 RSS 和 two-core（§3、§5）。
2. `fcb3450` 的 CI 失败**没有一项来自 mcppls 服务端**：6 项是仓库规范检查，1 项是 Windows fixture 用了旧版 mcpp，另 1 项是 runner 证据工具在 Windows 上的断言失败。按 D5 处理证据包后，规范检查的失败会随之消失（§4.1）。
3. 用现有 artifact 对比 0.0.16（6 晚 18 轮）和候选版本（4 个 head 12 轮）后：
   - **U15**：0.0.16 就在预算边缘（busiest minute 10–12，预算 12），候选版本是 10–13。这不是回归，而是一直没有余量。W4 必须做出明显余量。
   - **U13 RSS**：失败的两次和通过的两次分成两组，差别在于测量期间分配器有没有把内存还回去（§3.2）。这个增长在 0.0.16 上多半也存在，只是被旧的测量起点掩盖了。要稳定通过，引擎 memo 修复（W7）实际上在关键路径上。

### 3.2 U13 RSS：失败与通过分成两组

| run | 结果 | 有限工作时长 | idle 开始时 RSS | idle 结束时 RSS | 增长 | idle CPU |
|---|---|---|---|---|---|---|
| `38366b9` | 通过 | 70.1 s | 1391.8 MB | 660.3 MB | −52.6% | 0.0059 |
| `e01e1c1` | 通过 | 80.1 s | 1494.3 MB | 675.4 MB | −54.8% | 0.0080 |
| `072c230` | 失败 | 122.4 s | 624.7 MB | 1086.6 MB | +73.9% | 0.0060 |
| `1341938` | 失败 | 126.4 s | 948.1 MB | 1188.3 MB | +25.3% | 0.0061 |

解读：

- 在通过的两次里，测量开始时 RSS 很高，期间 clangd 把内存还给了系统（trim），所以最后约为 670 MB。
- 在失败的两次里，这次 trim 发生在有限工作期间，测量开始时 RSS 已经很低。之后 10 分钟空闲期间 RSS 又涨回 1.1–1.2 GB，期间再也没有 trim。
- 两组的 idle CPU 都在 0.006 左右。600 s × 0.006 core ≈ 3.6 CPU 秒，与 memo 线程每 30 s 构造一次约 30 MB JSON、共 20 次的量级相符。

所以初稿的假设（空闲期间没有 LSP 消息，就不会 trim；memo 线程反复分配又释放的大块内存被分配器保留）得到了**间接支持**，但还没有被证明。两点推论：

1. **"0.0.16 没有 RSS 问题"不成立**。0.0.16 的测量窗口开始得更早，起点通常处在高位，所以增长被掩盖了。引擎同是 `.4`，增长多半一直存在。
2. 在 mcppls 侧，只有"挑测量起点"能让 U13 变绿，而这正是 #59 review 明确禁止的做法。要稳定变绿，只能消掉空闲期的分配：引擎 memo 修复（W7）。

### 4.1 W1：本地验收必须基于干净树（P0）

HANDOFF 里"本地 6 members / 58 programs / 0 failed"是在 dirty snapshot 上跑出来的，`verify.py` 是之后才提交的。所以本地全绿和远端 `test_check` 失败并不矛盾。规则：本地报告必须写明 commit SHA，并且 `git status --porcelain` 为空；dirty snapshot 上的结果只能作参考。

初稿里"把 `verify.py` 加进 `scripts.allow`"这一项取消：按 D5，它会离开 head 的树（§4.12）。

### 4.2 W2：真实 Windows fixture 使用正确的 mcpp（P0）

问题：CI 里有两个 mcpp（见 `.github/versions.env`）。一个是固定的 `MCPP_VERSION=2026.9.30.2`，它是默认版本、在 PATH 上；另一个是从 release 安装的 `MCPP_BUILD_PROGRAMS_VERSION=2026.10.11.1`，只有 `mcpp-build-programs` 会触发安装。`mcpp-target-windows-real` 写的是 `{env:MCPPLS_REAL_MCPP|mcpp}`，CI 没有设置这个变量，所以用了旧版。

方案（不改 validator，不改 fixture 断言）：

1. fixture 在 `scenario.json` 中自己声明 `"requires-mcpp": ">=2026.10.5.2"`。runner 在 prepare 之前读取实际 producer 的版本；不满足时直接失败，报"fixture 需要 mcpp ≥ X，实际是 Y"，而不是让 clang 报一串看不懂的路径错误。
2. CI 的"The mcpp that describes build programs"步骤改为：只要本矩阵项里有 fixture 声明了 `requires-mcpp`，或者包含 `mcpp-build-programs`，就安装。两个环境变量合并成一个 `MCPPLS_REAL_MCPP`，`mcpp-build-programs` 也改用它。schema 预检查选择 `emit=` 时，读的也是同一份声明。
3. 默认 `MCPP_VERSION` 这次不升级。升级会改变全部 fixture 的基线，放到 0.0.18 单独评估。
4. 在 `docs/20-projects.md` 中补一句："Windows MSVC 下使用 `import std` 需要 mcpp ≥ 2026.10.5.2。"

验收：win32-x64 conformance 上，`mcpp-target-windows-real` 实际跑通 i686→x64→i686。这是 #63 设计要求的原生生产链，**到目前为止从未通过过**。

### 4.3 W3：runner overflow trace 的 Windows 断言（P0）

**更正初稿的诊断**。读代码（`src/bin/conformance.cpp` 约 2773–2832 行）可以确认：统计和 trace 遍历的是同一组 `completions` id、同一个 `asyncRequests`，中间也不会 pump 客户端；而且 `typed["answered"] == total`（471 行）是通过的。所以"两边集合不一致"这个解释**不成立**。

对 470 行，目前有一个候选解释：mock 的计数器 `completions == 270`（`tests/test_conformance.cpp:120`）统计的是 mock 收到的**所有** completion，包括打字开始之前，runner 为等首个回答而发出的那些请求。Windows 上等首个回答需要的轮次更多，于是被故意放慢的那个请求在客户端的 index 就落到了 256 以下。466/467 两行（最慢的不等于 max）目前还无法解释。

方案：

1. 先让测试在失败时打印诊断信息：trace 的 `slowest*`（index、elapsedNanoseconds）、`completion.max`、`total`、打字开始之前 mock 已经收到的 completion 数，以及 elapsed 最大的前 3 项。在 Windows CI 上跑一次，拿到数据。
2. 如果候选解释成立：mock 改为从打字开始之后才计数（例如由 runner 在打字开始时发一个标记，或者改用 request 内容里的位置），不改 runner 的产品逻辑。
3. 466/467 等数据出来再定。在原因查清之前，不放宽断言，也不按平台跳过。

### 4.4 W4：正在输入的文件，autosave 每次保存都 reload（P1，U15）

**证据**：最忙一分钟的 13 次转换全部是 `ready→loading→ready`，每次 loading 只有 0.65–1.0 s，间隔约 2 s。它们全都发生在 U6 autosave 期间，脚本反复在 `src/build/execute.cppm` 第 17 行输入 `import mcpp.build.`。这和 `fcb3450` 修掉的"条件 import 导致重复 discovery"不是同一个问题：这里每次保存都是真实的结构变化。0.0.16 上同一指标是 10–12，所以这个问题一直存在，只是刚好落在预算以内。

**机制**（`src/orchestrator/workspace.cpp`）：watched-file 的结构变化会调用 `schedule_reload(fromEdits=true)`，等待时间是 `clamp(lastProducerMs, 1.5s, 60s)`，而且后续的变化会把它往后推。producer 很快时，窗口就是 1.5 s；autosave 大约每 2 s 保存一次，每次都超过窗口，于是各触发一次 reload。

**方案**：

1. **复用已有的状态**，不新建原语：workspace 里已经有 `editedAt`（每个打开文件最后一次 didChange 的时间，import-hang plan §5）和 `EDIT_SETTLE = 2000ms`（F13，replan 用）。新增一个辅助函数 `edit_quiet_at(path) = editedAt[path] + EDIT_SETTLE`。
2. 保存触发结构 reload 时，如果文件是打开的，并且还没到 `edit_quiet_at`，就令 `reloadAt = max(现有等待时间, edit_quiet_at(path))`；之后每次输入和保存都继续往后推。没有打开的文件（checkout、外部工具写入）以及停止输入之后的保存，行为不变。
3. 上限：从第一次被推迟算起，最多推迟 `5 × EDIT_SETTLE = 10 s`，避免一直不停输入时模型永远不更新。
4. 本版**不**合并 `BUILD_PROGRAM_QUIET`（它针对磁盘上的变化）和 `DOOM_RETRY_QUIET`（3 s，在引擎层，靠 `touchedAt_` 判断）。合并它们会改变两处现有行为，放到 0.0.18（§7 原则 1）。
5. 不改 status 的语义，不加 hold，不改 U15 的 12/min 预算。

**验收**：

- 新增确定性 fixture `mcpp-autosave-import-typing`：mock producer，10 Hz 在 import 行输入，每 1 s autosave 一次，持续 20 s。旧产品的 producer 调用和状态转换应 ≥ 8 次，新产品 ≤ 2 次；停止输入之后，模型在 EDIT_SETTLE + 1.5 s 内反映最终的 import。
- 现有 70 项 watched-source fixture、U8 和 U15 场景保持不变。
- nightly 上 U15 的 busiest minute **≤ 8**（预算仍是 12）。没有余量的"通过"不算通过。

### 4.5 W5：crash/exit 之后的隔离期（P1，U7a、U9）

**证据**：

- U9（0.0.16 nightly 10-17）：测试主动 kill clangd，没有 crash context。probe 的首个回答等了 121.35 s，正好对应 `Quarantine::FIRST_TERM = 2 min`。
- U7a（`u7a-postrun-analysis.md`）：clangd 在构建 `config.cppm` 的 AST 时崩溃，**有 crash context**（Build AST，栈里有 realloc），文件被隔离 120.216 s。在这期间，它依赖的 `mcpp.log`、`mcpp.config` 已经重建成功；交回之后，AST 只用了 0.73 s。
- 代码：`settle_exit_` 对所有 suspect 一律执行 `set_aside_(…, Reclaim::no)`。`sources_changed()` 只释放 `moduleFailed` 类型的隔离，其他隔离只有在文件自身变化或期满时才交回。

**方案**（两条新规则；现有规则不变）：

1. **原因不明的退出，第一次不隔离**（对应 U9）：没有 crash context 指认的 suspect 文件，只记一次 strike。同一个文件在 10 min 内第二次成为 suspect，才隔离。被 crash context 指认的文件，照旧立即隔离。U7a 属于这一类，所以这条规则**帮不了 U7a**。
2. **依赖闭包变化之后，交回重试一次**（对应 U7a）：
   - 隔离时记录该文件 import 闭包的身份。闭包从 mcppls 自己的计划里取；身份用的是 mcppls 观察到的每个模块 `module-built` 事件的序号。引擎只报告"Built module X to …"，不报告 BMI 的内容哈希，所以不需要改引擎。
   - 之后，闭包里的模块全部构建成功、并且身份与记录的不同时，交回 clangd 重试一次。每个不同的身份只重试一次。重试之后再崩溃，按现有规则把期限翻倍。闭包里有模块构建失败时，不交回。
3. 现有规则不变：文件自身变化时交回、期满交回、`MAX_TERM = 16 min`。最坏情况由引擎现有的崩溃计数兜底：5 min 内退出 5 次，就改为退避重启（1、2、4、8 分钟），而不是放弃。初稿把这里写成了"放弃"，已更正。

**安全边界**：最坏情况是依赖每真实变化一次，clangd 就多重启一次，并且受崩溃计数约束。不缩短 `FIRST_TERM`，不做无条件交回，不改 U7a/U9 的预算。U7a 背后的崩溃本身（AST 构建时 realloc）是引擎的 bug，靠 W8 符号化之后才能定位，不在本版修复范围内。

**验收**（确定性，使用 mock 或 fake-crash 引擎）：

- kill 一次 → probe 在 25 s 预算内由 clangd 回答；同一文件在 10 min 内两次成为 suspect → 隔离。
- 指认了文件的 crash → 隔离；无关文件保存 → 不交回；依赖重建但身份相同 → 不交回；身份变化 → 交回一次；再崩溃 → 期限翻倍，同一身份不会再交回；依赖构建失败 → 不交回。
- 旧产品必须在"kill 一次"和"闭包身份变化"这两个用例上失败。

### 4.6 W6：U5/U6 慢补全（P1，D2 判定）

**已有数据**（§3.1）：

- 0.0.16 的 18 轮：U5 max 0.52–0.84 s（中位约 0.76），U6 max 0.47–0.76 s。
- 候选版本的 11 轮（不含离群那一轮）：U5 max 0.57–1.01 s（中位约 0.89），U6 max 0.53–0.96 s。
- 离群值是 1/12：`1341938` r2 中，U5 为 8.26 s、U6 为 6.38 s，同一会话里两项都慢，像是会话级的事件，不像单个请求的问题。
- 典型 max 大约上移了 0.13 s，离 3 s 预算还很远，但值得确认它是不是来自产品本身。

**A/B 方法**（改进初稿）：

- 同一个 runner、同一个 fixture、同一种 runner 机器，只换 `--server/--payload`：一边是 v0.0.16 release 的 `payload-linux-x64.tar.gz`，一边是候选版本的 payload。这样可以排除 runner 改动的影响。
- 实现方式：nightly 的 workflow_dispatch 增加输入 `payload-from`。ux-mcpp 的 edits 阶段各跑 6 次。如果新 runner 读取了 0.0.16 不提供的报告字段，runner 必须把它们当成 null 处理（`serverCompletionEvidence` 已经是这样），并在结果里记下缺了哪些字段。
- 顺带跑 U13：ux-xlings 的 long 阶段各 3 次，用来验证 §3.2 的推论（0.0.16 在新测量窗口下同样会出现 RSS 增长）。

**D2 判定规则**：

1. 典型分布（每轮的 p95 和 max）在 A/B 中明显变差（候选版本的中位数比 0.0.16 高出两边合并标准差的 2 倍以上）→ 阻断，先找原因。
2. 离群值：6+6 次分辨不出约 1/12 的发生率，所以不靠计数下结论。在最终 head 的 nightly（§5）中再次出现 → 阻断，用 `fcb3450` 保留的失败阶段日志归因。没有再出现 → 记入 #59，但取证改动照样随 0.0.17 发布。

**取证**（这是 server 改动，但只增加观察，不改变行为）：server 已经记录每个请求的 `engineSentAt/engineRepliedAt`、按方法统计的 `engineP95Ms/overheadP95Ms`，以及 ≥ 5 s 的 `slow-request` journal。在此基础上扩展，而不是另起一个环形缓冲：

- `slow-request` 增加 `queueMs`（收到 → 发给引擎）、`engineMs`、`answerLayerMs`，以及发送时这个文件的 clangd fileStatus（是否正在构建 preamble 或模块）。
- 对 completion，把阈值从 5 s 降到 1 s，最多保留 32 条。

预设假设 H1：import 行的编辑使 preamble 失效，之后的函数体补全要等 preamble 和模块前置重建。取证结果应该能直接证实或否定它。修复方向（取证之后再定，现在不实施）：answer layer 在 preamble 重建期间使用上一代的答案（作为 standin 标注出来），或者在引擎侧让补全使用旧 preamble。

### 4.7 W7：引擎 memo 周期性构造 JSON（P1，D4 关键路径，按 D3 不绑定）

已证明的部分：`.4` 的 `ModuleMemoStore::write()` 每 30 s 先构造完整的 JSON，然后才判断有没有变化。隔离实验（只载入 30 MB memo，零次写入）中，RSS 在 180 s 内从 177 MiB 涨到 267 MiB。采纳[引擎提案](2026-10-22-issues-59-63-evidence/engine-memory-proposal.md)：先比较两个缓存的廉价 changeCount；最后一次 flush 仍然强制写 snapshot。

§3.2 的数据让它从 P2 升为 D4 的关键路径。验证"分配器保留"这一推论：

- runner 在 idle 窗口两端各发一次 clangd 的 `$/memoryUsage`。
- MemoryTree 基本不变而 RSS 上涨 → 是分配器保留，修复点在 memo 写入；MemoryTree 本身在涨 → 是真实的数据增长，要另找原因。
- 如果打了补丁之后仍然出现"未 trim 的增长"，再考虑在引擎侧做第二步：memo flush 之后，如果确实分配过，就调用一次 `malloc_trim`。本版不预先做这一步。

**流程**（沿用既定做法：引擎先在产品 CI 中验证，再合并和发布）：

1. **现在就**在 mcppls-clangd 开 PR：补丁 + 原生 canary（旧实现必须失败）。
2. mcppls 通过 `packaging/engine-candidate.json` 用这个 PR 的 CI 构建，跑完整 CI 和 U13 各 3 轮。
3. 两边都绿之后，发布 mcppls-clangd v0.0.17（`23.1.0-mcppls.5`），切换 `payload.lock.json`，删除候选文件。

按 D3，0.0.17 不等它。但要做到 D4，它必须赶上，所以它从第一天就并行开工。

### 4.10 W10：two-core（P1，从 P3 升级）

D4 的"全绿"包括 continue-on-error 的 job。two-core 在 `38366b9` 上通过过，说明可以做到。失败的情况分两类：

- U5 有 1–2 次 server 侧 `request-timeout`，预算 0。U5 的 p95 0.71–0.76 s、max 0.83–0.98 s 都很低，所以超时的**不是补全本身**，而是同一时间段里的其他请求（`clangd.cpp` 中按 deferred/held 或 pending 超时统计，事件里带有 method 和 file）。现有 artifact 只有总数，没有 method。
- U7a 的 p95 为 1.53/1.71 s，预算 1.5 s，超出很少。

方案：

1. 先在 `fcb3450` 之后的 nightly 中，从保存下来的失败阶段日志里查出超时的 method 和原因：`waited too long for …` 还是 `did not answer … in time (while …)`。
2. 如果是 mcppls 的等待上限在两核机器上太紧（例如等 "clangd to accept requests"），在 mcppls 中修复；如果是 clangd 在两核上确实答不过来，记录证据，并回到 §6 E2。
3. 不改 two-core 的预算，也不把它从矩阵里拿掉。

### 4.12 W12：证据包只留在 PR 历史（P0，D5）

## 5. "全绿"的定义（D4）

在最终 head（产品字节不再改动的那个提交）上：

1. **PR CI**：每个 job 都是 success。按条件跳过的 real Zed / release checks，由 W9 中的 release checks 补跑。
2. **nightly**：**两次**独立的 workflow_dispatch nightly（不在同一个小时触发），每个 job 都是 success，包括 termux 和 two-core。要两次，是因为 U13 在候选版本上的失败率是 2/4，U15 也没有余量，一次通过的证据太弱。每次 nightly 约 1.5 h。
3. **不改预算，不挑测量起点，不跑到绿为止**。出现红的 job 先归类：环境问题（镜像、限流、runner 故障）→ 修环境，然后两次都重跑；产品问题 → 修复，最终 head 改变，计数从零开始。
4. 余量要求：U15 busiest minute ≤ 8；U13 的 RSS 增长和 CPU 都要低于预算的 50%（当前 CPU 0.008 离 0.01 太近）。只为 U13/U15 设余量，是因为只有这两项已经证明会在边缘来回摆动；不新增其他门槛。

## 7. 架构原则（这次收口中统一下来的规则）

1. **"等用户停下来再做"应当只有一个判定**：本版先让 reload 使用 `editedAt + EDIT_SETTLE`；`BUILD_PROGRAM_QUIET` 和 `DOOM_RETRY_QUIET` 合并到同一判定上，放到 0.0.18 做，并且要逐一说明行为变化。
2. **隔离要有证据才执行，有证据就交回**：进入隔离需要重复出现或有明确指认；交回由可观察的事实触发（文件变化、闭包身份变化、期满），而不是只靠计时器。
3. **测试需要哪个版本的外部工具，由 fixture 自己声明**：runner 负责检查并给出清楚的错误；workflow 不再为单个 fixture 硬编码 `case`。
4. **验收必须基于提交后的干净树**，报告里写明 SHA。
5. **先归因，后修复，预算不变**：每个性能修复都要有确定性复现，旧产品必须失败、新产品必须通过。一次 nightly 通过不能替代归因。
6. **跨版本比较时，先固定 runner**：只换 server/payload，才能把产品的变化和测量方法的变化分开。初稿中"0.0.17 是净改善"的结论，就混入了 runner 和 CI 的修复。
7. **大的二进制证据不进主分支**：留在 PR 历史中，主分支只保留指引和 SHA。

## 11. 风险

- **W4**：推迟 reload 之后，正在输入 import 的用户最多要等 10 s 才能看到新模块的补全。缓解：`import` 行的模块名补全由 mcppls 自己负责，不依赖模型 reload。
- **W5 规则 1**：一个没有 crash context 的真实 crash-loop 文件，会多崩溃一次。最坏情况由退避重启约束。
- **W5 规则 2**：如果 U7a 的崩溃是读取正在重建的 BMI 时发生的竞争，重试可能再崩一次。这种情况期限会翻倍，同一身份也不会再交回，所以最多多一次重启。
- **W7**：是 D4 的关键路径，但在另一个仓库，CI 和发布有自己的节奏。E1 的时间盒用来防止它无限期拖住 0.0.17。
- **A/B 与两次 nightly 的成本**：A/B 约 18 个 runner job，最终两次 nightly 约 2 × 1.5 h。
- **W2**：只给声明了版本需求的 fixture 换上真实 mcpp；默认 pin 2026.9.30.2 与用户实际使用的版本之间的差距，到 0.0.18 处理。
- **U13 CPU 余量**：`e01e1c1` 的 idle CPU 是 0.008，预算 0.01，余量只有 20%。如果 W7 之后没有改善，就单独归因，不调预算。
