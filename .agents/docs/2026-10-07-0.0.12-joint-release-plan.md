# mcppls 0.0.12 + mcppls-clangd Joint Release Plan

> **历史记录。** 0.0.12 的最终范围、决策与实施见 [Part 3](2026-10-09-0.0.12-part3-convergence-plan.md) §8。文中 `.agents/docs/2026-10-08-0.0.12-part2-evidence/`、`.agents/docs/assets/`、`tests/evidence/` 等原始证据路径位于 `mcpp-language-server-0.0.12-evidence.tar.zst`（[evidence-0.0.12](https://github.com/Sunrisepeak/mcpp-language-server/releases/tag/evidence-0.0.12)），完整增量历史在 `archive/0.0.12-joint` 分支。

> **For agentic workers:** review 通过后，使用 `superpowers:executing-plans` 逐项实施；当前文档不授权发布、改生产配置或移除保护。各根因修复先提交复现与设计，再提交实现，保留独立 review 和追加 commit。

**Goal:** 让 mcppls 0.0.12 默认携带可追溯、语义正确、经真实项目验证且四平台可分发的维护版 clangd，而不只是将上游缺陷隐藏在产品保护或更快但错误的补全后面。

**Architecture:** fork 负责 Clang/clangd 内部的语义、模块构建、锁、生命周期和性能；mcppls 负责项目/编译器画像、调度、缓存失效、故障隔离和统一分发。两仓以不可变引擎身份、能力声明及同一组缺陷复现协议联动；发布依据是候选二进制和产品安装包的联合验收，而非 patch 数或绿色 build。

**Tech Stack:** C++23 modules、LLVM/Clang 23.1.0 基线、Python LSP replay、CMake/Ninja/lit、GitHub Actions、VS Code extension host、mcppls payload/VSIX/xlings。

**Spec:** [既有缺陷覆盖与本地实测](2026-10-07-maintained-clangd-0.0.12-plan.md)，[#24](https://github.com/Sunrisepeak/mcpp-language-server/issues/24)、[#37](https://github.com/Sunrisepeak/mcpp-language-server/issues/37)、[#43](https://github.com/Sunrisepeak/mcpp-language-server/issues/43)、[#44](https://github.com/Sunrisepeak/mcpp-language-server/issues/44)。本文件取代前份方案的初步发布顺序；测量记录保持原样。

状态：2026-10-07，联合设计供 review，**未实施，当前 fork 不可直接发布**。以下性能数值是建议的 release 目标，不是已经达到的结果。存在未定位的根因，因此这是 release 设计与工作包，不是可跳过诊断直接执行的完整 patch 蓝图。

## Global Constraints

- 产品版本目标 `0.0.12`；引擎首个合格正式版本目标 `23.1.0-mcppls.1`，当前 `23.1.0-mcppls.0` 仅实验。LLVM 基线 tag 解析为 commit SHA 后锁定。
- 发布平台 `linux-x64`、`win32-x64`、`darwin-x64`、`darwin-arm64`；linux-arm64 本轮不承诺。四平台均需运行测试，而非交叉编译完成即可。
- compiler-agnostic 保持：用户的 GCC/MSVC/Clang 工程不改成 LLVM 编译；clangd 的内部语义 BMI 不宣称能直接消费其他编译器的 BMI。
- 同一源码/patch digest/构建配方生成平台产物；所有编辑器及 CLI 入口使用对应平台同一已验收引擎。显式用户 `--clangd` 配置优先，保留外部原版 clangd 支持。
- 不以清缓存、禁模块、关闭 autosave、返回任意 lexical/global 候选作为真实修复；正确的 `-c` 编译命令、通用 watchdog/backoff/隔离/bundle 保留。
- 不自动上传源码、日志、dump；full-memory dump 可含用户代码/凭据，必须显式 opt-in、容量限制和本地清理。
- 只提升有证据的 ledger 状态：最小复现、对照失败、候选成功、回归测试、适用平台与包身份缺一不可。

## Review Focus

1. 补全点不在文件最后一行、成员/指针成员与同名全局符号：必须保留正确作用域与插入文本（W1）。
2. 模块导出、头文件、编译参数在请求进行中改变：不得复用旧依赖结果或发布过期响应（W2/W3）。
3. 未保存的 import、取消/关闭和锁持有者死亡：不能挂死、误删活跃缓存或无限重启（W3/W4）。
4. 用户自带 clangd/格式配置与编译器扩展：不能套用不支持的 fork 参数、覆盖用户配置或提示目标不支持的语法（W5/W6/W7）。
5. 没有 xlings/开发机依赖的干净机器：包能启动；未找到 debugger、空 corpus 或缺 license 必须失败（W4/W7/W8）。

### 路线选择

- **推荐：联合根因修复后切换默认引擎。** 按本文件G0–G4推进，实际解决正确性/稳定性并获得性能收益；成本最高，但符合本次“真实修复、优化、跨平台”目标。
- **备选：0.0.12仅准备身份与分发，fork继续实验性opt-in。** 风险较低、可先交付基础设施，但不满足本轮默认启用真实优化引擎的完整目标；只有用户明确接受缩小范围后采用。
- **不建议：当前fork直接打包默认发布。** 实测有成员语义/C7回归、raw hang与portable缺口，不具备发布依据。

本稿先供架构与release范围review。批准后，各工作包的诊断/复现产物决定具体函数接口与patch设计，再形成包含真实代码断言/命令的可执行实施计划；不会为尚未定位的crash提前编造修复代码。

## 2. 两仓边界与身份契约

共同身份记录如下，字段是本轮拟定契约，不代表现有 manifest 已支持：

```json
{
  "engine-version": "23.1.0-mcppls.1",
  "llvm-base-version": "23.1.0",
  "llvm-commit": "<resolved LLVM commit SHA>",
  "fork-commit": "<candidate fork commit SHA>",
  "patch-series-sha256": "<ordered series digest>",
  "platform": "linux-x64",
  "sha256": "<binary SHA-256>",
  "features": ["semantic-tokens-range"]
}
```

尖括号表示每次构建生成并严格校验的身份值，不是允许打包的字面量。`features` 仅写经过测试并随该二进制启用的能力；新格式 fallback、crash dump 等分别测完再加。产品不得仅根据版本后缀推定能力。

完整 engine version 用于日志、报告、缓存分区和用户显示；kit/libc++ 兼容用 LLVM base version，resource-dir 仍依据对应 LLVM 资源目录。旧 manifest 没有新字段时保留旧解析，不凭空赋予 fork 能力；新 manifest 缺少身份或 SHA 校验失败拒绝组装。用户自带 clangd 不强行绑定 bundled kit，不传 fork-only 参数。

缓存契约：补全复用必须匹配 engine identity、workspace/context、compiler profile、CDB generation、document semantic context 和 module dependency epoch；导出变化必定失效。正文的兼容前缀缓存可复用，但旧 generation 的异步回复必须丢弃；`isIncomplete` 按真实语义处理。不由 mcppls 把无关全局候选过滤成“看起来像成员”来遮盖 fork 错误。

缺陷证据包契约：`id / platform / baseline engine sha / candidate engine sha / commands / request-edit sequence / expected symbols or diagnostics / observed outcome / raw logs / timing samples / root-cause link`。crash 追加 build-id、PDB identity/符号栈；无法定位时标记 open，不填写推测的“修复”。

**文件：** fork LLVM `clang/lib/Format/Format.cpp`、`clang/include/clang/Format/Format.h` 及 `clang/unittests/Format/`（新增命名 style 的备选落点），Sema completion 回归测试；产品 compiler-profile/format 请求路径通过源码审计定位后单独提交实现设计，VS Code `editors/vscode/test/suite/` 新增 formatting/extensions 测试。

**设计决策：** #43 提到 `.clangd`，实际样式来源应是 `.clang-format`。以 mcpp 仓库 `.clang-format` 形成固定版本的、clang23 可解析的样式快照，不运行时从网络读取。优先级为项目 `.clang-format` / 显式用户设置 > mcpp project fallback > 原有通用 fallback；不向用户项目写文件。mcpp fallback 的默认适用范围仅 mcpp project，其他工程 opt-in。若选命名 `mcpp` preset，必须 fork 注册并声明能力；不能给原版 clangd 传不存在的 preset。最终样式快照及样例 diff 作为 W6 的独立 review 产物。

- [ ] #43 保存格式 golden cases：模块/global fragment、import、模板、namespace、lambda、长表达式；校验 mcpp 默认与固定样式一致、项目/用户 override 有效、外部 clangd 不报未知 style。官方配置依据：[ClangFormatStyleOptions](https://clang.llvm.org/docs/ClangFormatStyleOptions.html)。
- [ ] #44 的 `__attribute__` 是属性引入语法、`cleanup` 是属性名称、`__try` 是 SEH 关键字，不能全部当函数名塞进词典。按编译器/目标/语言及语法位置支持 GNU/Clang attributes 和 Windows MSVC/clang-cl SEH。
- [ ] 验证属性位置、`cleanup(function)` 合法插入及声明、普通标识符位置、注释/string、Linux 与 Windows target；SEH 用实际目标编译器可接受的最小例子，不用任意含析构的 C++ 函数证明支持。
- [ ] 语义 completion 在 fork parser/Sema 的合法上下文实现；产品只传准确画像与控制提示能力。clangd 尚不能忠实模拟的厂商语义明确标为限制，lexical 建议不能冒充编译通过。

**通过条件：** mcpp 格式 golden 和 override 测试通过；本轮指定的三类扩展有目标匹配、合法位置和实际编译检查。不承诺完成所有厂商所有扩展。格式配置依据与[属性参考](https://clang.llvm.org/docs/AttributeReference.html)不能替代目标编译器测试。

## 4. 建议联合验收指标

| 指标 | 阶段/方法 | 建议门槛 |
|---|---|---|
| 语义补全 | raw 引擎 + 产品 + VS Code；W1 所有语境 | 目标符号与合法插入100%通过；无上下文污染，无依赖更新漏符号 |
| 引擎补全延迟 | warm、每语境至少30请求、三次独立启动；报告全部原始样本 | 普通/限定名 p95≤200 ms，模块成员 p95≤300 ms；对约1 s的原版相同正确路径至少改善50% |
| 产品命中缓存延迟 | 独立于 raw 测量，body/prefix edit | p95≤50 ms；原版已有2–5 ms缓存场景不因强制绕缓存变成75 ms |
| 新导出生效 | 模块 export 编辑→消费者正确补全 | 小型 inferred fixture ≤5 s；C7不超时；重型项目按阶段报告，不套用小 fixture 限值 |
| 冷/温导航 | 继承 release-checks，固定机器与 fixture | 5次 median cold<12 s、warm<5 s；fork不退化，能达到什么幅度单列数据 |
| hang/crash | raw repro、产品序列、真实 corpus | 已复现阻断集0 hang/0 crash；不靠重启掩盖；未知问题明确 open |
| 稳定性 | 先短 smoke，RC 每平台≥2 h；UP-20≥1000 save iterations | 无异常重启/孤儿进程；请求无超期积压；RSS稳定期末≤1.2×初始且无持续线性增长 |
| cache | edit/reopen/kill循环、owner与预算测试 | 活跃 BMI不误删；孤儿最终回收；目录/磁盘回到配置预算以内 |
| 交互验证 | 每个平台真实 VS Code + 所支持 CLI入口 | 无弹窗 crash；补全选中后合法代码；格式/保存/跳转/关闭重开通过 |
| 分发 | OS下限干净机器，移除开发依赖/PATH偶然命中 | 四平台 hash可追踪、启动成功、license完整、无本机绝对依赖 |

采样区分 cold/indexing/warm/cache-hit，不能混在一个 p95 中；超时、错误和丢候选样本计失败，不能从延迟样本中悄悄剔除。性能与正确性 conjunctive（同时满足），不做总分互相抵消。CPU/RSS 同机器比较，要求新增优化无≥20%的稳定期 CPU/RSS退化；噪声或 trade-off 有数据后重新 review，不自行放宽。

真实项目基线：qt-demo、mcpp `d1f1c98fa26d953e084a183a9672fc1e0ce63558`、xlings `84572b0cc8502a16afaa4ae00867aef17f18c2c2`，记录 CDB/工具链/硬件。先修旧 WA009 probe 缺失 `heavyh000` 输入，再做性能结论。此前真实 extension-host 40请求/引擎可作回归基线，但不等同于人手键入/选中建议；RC 增加录屏或人工交互记录。

## 5. 依赖顺序、评审点与退出条件

1. **G0：证据与门槛正确。** W8 的负例 gate、W1/C7隔离、W3 raw hangs、W4非空 corpus 和构建身份先落地。修复质量 benchmark，不能先发包再找证据。
2. **G1：正确与稳定。** W1语义回归、W2失效、W3挂死、W4已复现crash/锁/泄漏、W5诊断通过；此阶段先不要求高风险结构优化。
3. **G2：真实优化与功能。** 基于 trace 进入 W1/W2优化，W6格式/扩展；任何优化都重跑G1。仅禁用0006恢复原速不满足用户的优化目标。
4. **G3：跨平台产品化。** W7产物/身份/kit，四平台最终安装包跑第4节；Windows符号、macOS两架构及Linux低版本缺一不可。
5. **G4：RC review→release。** 连续完整验收、2 h稳定性、真实项目交互、记录剩余限制，使用相同bytes晋升。发布后具备候选回退与用户显式选择原版路径。

任何可重现新增语义回归、原有确定 hang/crash 未修、C7超时、性能未达、平台不能安装、空 corpus、身份不真实都阻断 **joint 0.0.12 默认启用维护版**。若成本超出本轮，向用户带数据提出拆分范围/延期；不能自行把“隐藏问题的当前 fork”命名为真实修复版本发布。

## 6. 本轮 review 的核心决策

1. 接受“根因修复 + 语义正确 + 性能 + 四平台”联合门槛，而不是只换引擎或跑通打包。
2. 同意先修当前成员补全/C7回归及 hang/crash，再按 trace 做性能优化；不预设 BMI summary 或增大线程栈必然解决问题。
3. 同意 mcpp 格式默认仅适用于 mcpp项目，且项目/用户配置优先；#44本轮以明确三类语法和目标为边界。
4. 确认第4节性能预算、四平台范围及建议 OS floor；未达到时需要重新review，不隐式降低指标。
5. 同意保留通用隔离/重试/bundle，feature workaround逐项退休，externally configured clangd继续可用。
6. 同意按G0→G4推进：先可复现证据与正确gate、再根因修复、再优化、再候选联合验收，最终发布另行授权。
