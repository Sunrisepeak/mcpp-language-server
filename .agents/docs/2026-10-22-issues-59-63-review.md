# #59 / #63 设计与实施自审摘要

日期：2026-10-22。已复核路径身份与未信任回退补修；`dc12357` 为此前检查点，最终验收尚未完成。代码存在、本地检查通过、全平台交付完成是不同状态。

详细设计见 [目标与可靠性设计](2026-10-22-issues-59-63-target-and-reliability-design.md)，实验及限制见 [证据目录](2026-10-22-issues-59-63-evidence/README.md)。本摘要不替代其中的实现检查点。

## 1. 已实施的方案

**不修改 mcpp；mcppls 默认跟随根编译数据库中明确且唯一的目标，也允许项目工作区固定分析目标。** 仍由 mcpp 生成模块分析模型，mcppls 负责选择、传参、缓存和状态一致性。

这能够解决 #63 的主要缺口，但承诺是“跟随最近发布的编译配置”，而不是“识别最近一次成功构建”。现有根 CDB 不提供后者的证明。`build`、`test`、`run`、configure-only 等都可能发布 CDB，外部工具也可能写入它。

不以是否存在 `mcpp emit build-database` 或某个构建 target 判断“有哪些平台可切换”：前者是 producer 能力，后者可能表示程序、库或构建节点，均不是受支持架构列表。首版不枚举平台候选，不从宏、目录时间或宿主架构猜测。

## 3. 一个配置项，三种明确意图

新增 `mcppls.buildDiscovery.mcppTarget`，默认 `auto`；其他客户端可使用 CLI `--mcpp-target`。

| 值 | 选择规则 |
|---|---|
| `auto` | 根 `compile_commands.json` 有明确唯一目标则使用；否则由 mcpp 默认规则决定，并解释回落原因 |
| `project` | 禁止从 CDB 选择目标，完全采用 mcpp 默认规则 |
| `<triple>` | 固定分析目标，例如 `i686-windows-msvc`；producer 失败时不能偷偷取消 target 重试 |

项目仅固定编辑器分析目标时，可提交 `.vscode/settings.json`：

```json
{
  "mcppls.buildDiscovery.mcppTarget": "i686-windows-msvc"
}
```

项目真实默认构建目标则使用 mcpp 的 `[build].target`，配合 `project` 模式。两者职责不同，不新增独立 `.mcppls` 配置文件。

单窗口共享 server 的现有架构下，显式设置按 window 作用域生效；`auto` 对每个项目根独立读取 CDB。多根工作区逐根固定不同目标需要后续 root→target 协议，不能由一个窗口字符串假装实现。

该配置只影响已选中的 mcpp provider。显式数据库、其他 provider、discovery/off、未信任工作区仍沿用原规则。`buildTool=off` 不运行 producer，因此无法保证强制切换成功；必须展示未应用状态。

本期仅跟随 target，不从优化选项、宏或路径推断 profile/toolchain/features。需要完整复用 CDB 参数的用户可选择现有 `compile-commands` provider；不混合两个 provider 的数据库。

## 4. 数据流与实现边界

```text
配置 + 根 CDB 快照
    ↓ project：只读目标解析与路径归属判断
不可变选择 {mode, requestedTarget, source, reason}
    ↓ orchestrator：generation、异步加载与事件合并
mcpp emit build-database --format json [--target ...]
    ↓ 校验 effective target 和当前 producer 身份
模型 / cache / clangd / 状态展示采用同一代数
```

自动选择仅接受明确 `--target` / `-target`。排除有可靠角色信息的宿主构建程序及外部 producer 后，纳入决策的项目条目必须全部可判定且一致。无法解释的 wrapper、response file、`-m32` 等不能被忽略后仍认定唯一；冲突时不取第一条、不多数投票。读取有大小/条目上限，解析在后台，不执行 CDB 中的命令。

目标切换使用 generation：输入变化立即使旧请求过期，晚到结果不能覆盖新选择。创建、删除、原子替换、符号链接、半写文件均有处理；半写短期重试，稳定无效时明确回落。相同目标的格式重写不应触发 producer 循环。目标提取不反写根 CDB；不支持 emit 的旧 producer 仍沿用 configure-only 兼容路径，由 mcpp 写项目文件并显示提示。

producer 身份包含当前解析路径、文件身份/变更信息、已确认版本及选择输入。旧缓存不能用自身保存的版本证明自己仍新鲜；新会话重新确认，运行中使用有界查询和可观察输入失效。launcher 内部全局状态改变却没有任何可观察变化时，只能在下次实际 emit 或新会话确认，不能承诺即时发现。

已知目标不匹配的模型不能采用。失败时允许保留可用旧模型，但必须同时显示“实际旧目标”和“待应用/失败的新目标”。状态栏、报告和缓存不能各自判断一次目标。

BMI 按有效命令和工具链隔离，切回复用仍有效的旧产物；不全局删缓存。目标设置变化不应重载其他 provider；项目关闭后 polling worker 应退出。

## 5. 可靠性修复与性能优化

确定性修复包括 UTF-8 输出、Termux 绑定、当前 producer 身份校验，以及目标切换引入的缓存/竞态/worker 生命周期问题。

性能项分别验收：

- **U15**：仅当前准备代数、实际需要模块的完成属于进展；心跳、旧事件和无关任务不能消除停顿。原节点停顿和真实活动间隔都保留。
- **U13**：把可观察的准备、索引及 implementation 工作期与空闲测量区分；工作期有等待上限，不能靠 CPU/RSS 已合格来选择起点。保留原 600 秒、0.01 cores、10% RSS 门槛；晚到的内存增长仍是待查问题。
- **U8**：记录真实构建数、有效命令、原缓存 key 及产物。必须证明“曾有效的同一 key 被重建”，才能认定缓存复用缺陷；首次构建不能只凭发生在 undo 后就称为重复构建。保留原场景和未通过结果。

上游归因需要独立证据；不因使用 clangd 就把问题移交上游。只有确认需要上游 workaround 时，才另按仓库规范登记并定义移除条件。

## 6. 验收与交付次序

1. 固定基线和复现：区分旧行为、真实缺陷、已存在的配置以及未决性能项。
2. 实现目标选择与身份链路，补配置/状态/报告；UTF-8 和 CI 修复可独立验证。
3. 单测加真实 LSP conformance：auto/project/固定目标，错误与冲突，冷暖缓存，producer 替换，连续目标切换、晚响应、半写与 polling，禁用及非 mcpp provider。
4. Windows 原生验证 x64 宿主下的 i686/x64 条件声明；Linux/macOS 回归。规范正文、schema、示例、traceability、配置文档与本地化同步。
5. 原 CPU 限制和 cache lineage 重放 U13/U15/U8，记录版本、日志与失败；本地通过不能代替全平台 CI 或 Termux 实际执行证据。

本次设计 review 不把“代码已写”作为最终验收通过，也不要求先升级 mcpp 才能提供显式目标入口。若将来需要严格跟随最近成功构建、完整 profile/toolchain/features 或枚举平台，再讨论 mcpp 的正式状态接口。

## 7. 已执行的设计边界

1. 接受默认 `auto`，其语义为“最近发布 CDB 的明确目标”，而非“最近成功构建”。
2. 接受一个 `auto | project | triple` 设置；首版项目工作区可固定目标，不提供平台猜测菜单。
3. 保留 mcpp provider 优先级，仅把目标作为 producer 输入；完整 CDB 使用现有 provider。
4. 目标选择、producer 身份、缓存和实际状态一起验收；性能根因未明确的项继续保留，预算不放宽。
