# 0.22.0: the include completion's second quote (#80) and the Windows grant cliff (#86)

Status: implemented · the release vehicle is PR #85 (branch `answer-routing-overslept`), which
keeps its two test/CI fixes and carries these; its CI is green and the plan is realized as
written except where §3.1 records what verification changed on the way (Linux keeps /usr, macOS
its list) · evidence measured on the released 0.21.0 payload (linux-x64, commit 4fcf290;
reproduction scripts and logs under `.test-scratch/issue80/`) and on the reporter's two
diagnostic bundles (unpacked under `.test-scratch/issue86/`); main at 91390e6 adds no runtime
change over 0.21.0. Target: 0.22.0 (a series release: every component together — docs/92-release.md:
fixes, tests, docs, the changelog entry and `version --series 0.22` all in the one PR).

The goal this plan serves: **an include completion is accepted once, in either of VS Code's two
accept modes, without a doubled closing quote; and a Windows session survives more engine starts
than the sandbox's grant tables hold, without the engine becoming unstartable.** mcppls-side only:
the engine (mcppls-clangd) is not touched; platform fixes enter as dependency bumps, as 0.21.0 did.

## 0. What the evidence says (2026-11-11 analysis)

- **#80, fixed part.** 0.0.20's `retarget` cut every edit's end to the cursor, so the editor's
  auto-paired closing quote survived. `aaf7174` (in 0.21.0) keeps ends past the cursor while the
  line after it is unchanged, and the answer layer gives include lines no key. Measured on the
  0.21.0 payload over 11 keystrokes (`#include "`, letters, `render/pass/`, `common/numb` …):
  every answer, fresh from the engine and re-served from the word cache alike, applies correctly
  in **insert** mode.
- **#80, residual.** Every include item the engine gives (and therefore everything mcppls passes
  on or retargets) has `insert = [word, cursor+1)` — through the auto-paired quote — but
  `replace = [word, cursor)`. In **replace** accept mode VS Code applies the replace range, the
  paired quote survives, and the line becomes `#include "common/number-literals.hpp""` with the
  cursor between the quotes: character-for-character the reporter's 0.21.0 screenshots, whose hint
  bar (`Replace (Tab), Insert (Shift+↵)`) shows the editor in replace mode. Both reports' editors
  are; it is why 0.21.0 "changed nothing" for them.
- **#86.** The error is not memory. mcpplibs.os 0.4.1 wraps openkal-windows 0.20.0's
  `kal_err_no_memory`, which `attenuate()` also returns when its fixed root table (`kRoots = 64`,
  `rights.cpp:101`) has no slot — and `forget()` never frees one ("the root itself stays until the
  program ends", `rights.cpp:395`). Each engine start attenuates the read-only grants — nine on
  the reporter's machine — one root each. b1: initial start + 6 crash restarts = 63 roots; the
  backoff restart consumed the 64th (`C:/ProgramData`) and failed on the 65th (`C:/Program Files`,
  exactly the directory the error names). 0.21.0 pins the same versions, so the arithmetic stands;
  b2 shows the trigger alive too (the new engine 23.1.0-mcppls.10 exits twice in its first two
  minutes, crash-loop again), that session simply ended before the 8th start.

## 1. I1 — balance the item's two ranges before the answer leaves (fixes #80's residual)

One rule, applied once, at the single egress every completion result already passes through
(`finish_job`, where R-7's fallback and F15's merge already run; `retarget` results included):

> For an item whose `textEdit` is an InsertReplaceEdit on the cursor's line: if `insert.end` lies
> past the cursor and `replace.end` is at the cursor, set `replace.end = insert.end`.

- Pure addition to `mcppls.orchestrator.completion`
  (`void balance_for_replace(Json& result, base::Position at)`), called from `finish_job` for
  `textDocument/completion` results whose line prefix is an include line — the check the module
  already knows how to make (`is_import_line_prefix`'s sibling for `#include`, `#include_next`,
  `#import`, which `answer.cpp:253` spells `include_line`; lift one helper, use it in both).
- Why this shape: it makes replace mode consume the same text insert mode already consumes, so
  the editor's paired quote is eaten exactly once in either mode. newText, label and filterText
  are untouched (filtering by the typed prefix is unaffected). Identifier completions — whose
  replace range extends *past* the cursor to the word's end — do not match the rule's premise and
  are not touched. Directory items (`pass/`, no closing delimiter) do not match it either.
- A plain TextEdit (single range) has no asymmetry to fix; nothing to do.
- Narrow and local: the alternative of stripping the closing delimiter from newText was rejected
  because label, filterText and sortText all carry it, and the item's meaning (an include path
  with its closing quote) would be rewritten in five places instead of one range end.

## 2. I2/I3 — the word cache closes to include lines; the late path stays, on purpose

The 0.21.0 changelog states "an include line is never answered from kept answers, whose words are
the code's identifiers". True today only of the answer layer (`answer.cpp:311`); the word cache and
the late path still keep and re-serve them. The two make different claims, and only one of them is
true for an include list:

- **the word cache (0.0.14 A1) claims freshness by the file's text**: a complete answer holds for
  its word (`WORD_ANSWER_KEPT`, 30 s) while the document outside the word is unchanged. An include
  list's candidates come from the file system and the index — no key over this file's text can say
  when they changed — and a complete list is filtered client-side anyway, so the cache's whole
  contribution was ~50 ms on the rare re-ask (a re-open, a `.`/`:` trigger) while it retained
  1000-item lists per open file. The claim is false and the value nil: **close it**.
- **the late path (C-2) claims only that the engine answered this very word moments ago**
  (`LATE_ANSWER_KEPT`, 5 s) and that its answer beats nothing while the engine is behind. That
  claim holds for any content: it is the engine's own answer, seconds old, for the position being
  typed. **Keep it** — it is what fills the include popup while the engine is cold (preamble) or
  busy (module builds), which is also more than vanilla clangd gives.

Changes:

1. `WordKey` gains an include-line flag (`#include`, `#include_next`, `#import` — the spelling
   `answer.cpp:253` already has), set in `word_key` from the text before the word.
2. The word cache closes with **one guard at its only writer**: `note_word_answer_at` keeps
   nothing for such a key. `answered_from_word` needs no change — it finds nothing. The late path
   needs no change either — `answered_late`'s existing guard passes include lines today, and the
   comment there changes to say that is deliberate; `answer_without_core` still registers the
   `LateCompletion` (the request is detached, not cancelled) and `EnginePace` still learns from
   late include answers. Everything the late path serves passes the §1 egress, so its items are
   balanced for replace mode like any fresh answer.
3. I3, the same principle at the fallback: R-7's "file's words" answer (`workspace.cpp:2361`)
   excludes import lines today; include lines join them — identifiers of the program are not
   candidates where a header name belongs. During the cold or busy window the popup shows the
   engine's late answer once it exists, and nothing before: empty beats wrong, and the late path
   is what makes "empty" brief.

The invariant, as the changelog of the release should state it: **an include completion is the
engine's own answer — fresh, or its late answer of at most five seconds — never the file's words,
never a thirty-second-old list.** Roughly fifteen lines of production code (the flag, one guard,
the fallback's), and no liveness or pacing behavior changes at all.

## 3. W1–W4 — the grant cliff, Windows and Linux alike

### 3.1 W1 — a start grants what its system's driver adds to every compile, and no more

`system_roots()` handed the engine `ProgramFiles`, `ProgramFiles(x86)` and `ProgramData` on
Windows and `/usr`, `/opt` and six more on Linux — on the reporter's machine nine of thirteen
grants, on a Linux box eleven of fifteen (eight roots plus two package stores plus the payload).
What the engine actually needs there it already receives by name: the compiler's installation
(parent of parent of the command's program), every `-I`-like flag, and the MSVC/Windows-SDK roots —
flags **mcppls itself injects** from its toolchain probing (`normalize/gnu.cpp:108-120`), which
`plan_directories` then derives; and a plan that names a directory the engine lacks is granted by a
restart (`clangd.cpp:941`). The blanket's remaining coverage is one case: the toolchain probe
failed while the engine's driver auto-locates its toolchain at analysis time. That case is better
served explicitly than by a standing grant of city blocks. So:

- `system_roots()` answers what the driver adds to every compile whatever the flags say: nothing
  on Windows (the plan names each toolchain; the MSVC and SDK roots are flags mcppls injects),
  `/usr` alone on Linux (the GCC driver's implicit include root — without it a toolchain's std.cc
  cannot be scanned, `features.h` not found, measured on xmake-basic), macOS' conventional list
  (its SDK and system frameworks, found by convention; removing them settled a real macOS kit
  project *degraded*). The plan's first draft emptied Linux too, on the belief that the
  attenuating table was Windows-only — the conformance cases of §4 falsified that twice: a Linux
  session's eleventh start failed with `granting ~/.mcpp/registry/data/xpkgs: out of memory`, and
  the GCC flows above lost std. Eight Linux roots became one; Windows' three became none.
- `plan_directories` resolves a bare first argument against PATH (the server already knows the
  tool environment) and adds its installation directory — a compiler invoked by a bare name keeps
  its headers reachable, one directory per compiler actually used.

**Configurable already, no new setting.** A user in the probe-failure case (or anyone wanting the
old reach) re-adds exactly what they need with the grants setting mcppls has had since 0.0.20:
`"mcppls.grants": ["/usr"]` or `["C:/Program Files/Microsoft Visual Studio"]` narrows to the piece
that matters; `"all"` drops the sandbox outright. A dedicated `systemRoots` toggle would say the
same thing the existing setting already says, and the repo's settings discipline is one setting per
decision a person must make — the default here should simply be right. (Considered and rejected:
keeping the blanket conditionally, when the probe fails — a conditional rule in the grant set to
optimize a case that already shows itself in the profile's level, when `mcppls.grants` lets the
person say it in one line.)

### 3.2 W2 — read-only grants beneath one directory collapse, always; never into a volume root or the home

`engine_grants` merged read-only grants into their deepest shared ancestor only when a set exceeded
`MAX_GRANTS` (16). On the reporter's machine four grants (package store, ftxui src, ftxui include,
a build-database dir) sit beneath one mcpp data directory, and the payload's clangd and okrun
directories beneath the payload. Collapse them unconditionally on every system (the merge itself costs nothing and saves every table): per-start slot
consumption drops from nine or eleven to two or three, and sets that fit stop paying for neighbors
they contain. The widening is read-only and the >16 path already accepted the same tradeoff.

Two guards the collapse needs — the second of which the existing >16 path lacked, a latent hazard
this fix closes with it: the shared ancestor must be neither a **volume root** (`C:/`, `/` —
`C:/Program Files` and `C:/Program Files (x86)` share only `C:/`; eight Linux roots share only
`/`) nor the **user's home** (the payload under `~/.vscode` and the stores under `~/.mcpp` share
only `~`, and a merge there would hand the engine every file the person owns read-only). With
those, the merge takes an ancestor only when it names a directory worth granting on its own.

### 3.3 W3 — the failure names its cause and its way out

When a start is refused with `granting <dir>`, the `engine-start-failed` issue (`clangd.cpp:2102`)
says what happened and what to do, instead of a bare system message:

> clangd could not be started: granting C:/Program Files: out of memory. The Windows sandbox's
> grant tables hold 64 entries for this server process and are spent after ~8 engine starts
> (openkal 0.20.0); restarting the editor restores them, or `mcppls.grants: ["all"]` does without
> the sandbox. Repeated clangd crashes spend them faster — see the engine-crash-loop issue.

Recognition is a prefix (`granting `) plus the message (`out of memory`) on the start failure; the
count of starts and of read-only grants this process has made is known to mcppls and goes into the
sentence. No automatic server restart: an editor that restarts itself is a surprise no issue text
justifies; the message is the recovery path. (Deliberate exit was considered and rejected — the
extension's crash counter would restart the server and reset the tables, but a self-restarting
server is harder to trust than a sentence that tells the person what to press.)

### 3.4 W4 — the durable fix is upstream, and lands as a pin bump

The table is the defect: `forget()` should return a root slot when its last handle closes (its
`names`/`listed`/`base` are already released there; `live` is not cleared), or attenuated handles
should be kept and reused across spawns so a grant costs one root for a process's lifetime, not
one per start. That work is openkal-windows's (and mcpplibs.os's, for handle reuse), not this
repository's; mcppls takes it the way 0.21.0 took the platform: a pin bump and a changelog line.
W1–W3 hold the line until then and remain worth their cost regardless (narrower grants and a
self-explaining failure are good in themselves).

## 4. T — tests and CI, with PR 85

PR #85 (`answer-routing-overslept`) is adjacent, not in the way, and lands first:

- Its subject is the kept list's wait past the engine's pace; §2 removes include lines from the
  kept paths entirely, which only shrinks what that machinery can be asked about. Its case uses
  identifier words; nothing to reconcile.
- Its CI half — a second attempt runs only failed cases (`mtest run --failed`,
  `CONFORMANCE_FAILED_ONLY`) — is the rule the new conformance cases below follow: no case may
  require a side effect (a bundle, a bundle check) that only a first attempt produces.
- Its under-load discipline — measure, then skip saying so — is why every case below is
  deterministic: no real sleeps.

New tests:

- Unit, `tests/unit/test_completion.cpp` (I1): the balance rule on the measured shapes — insert
  `[word, cursor+1)` / replace `[word, cursor)` → replace end moves; identifier shape (replace
  past cursor) untouched; directory items untouched; plain TextEdit untouched; non-include lines
  untouched.
- Unit (I2): `WordKey` carries the include flag for the include spellings (`#include "`,
  `#  include_next <`, `#import "`) and not for a plain word; `note_word_answer_at` keeps nothing
  for such a key; a late include answer still serves (the existing retarget cases of
  `test_completion.cpp:302` carry its correctness, and §4's conformance case the egress).
- Unit (I3): the fallback's own predicate — include and import lines, nothing offered.
- Unit (W1/W2): plan directories from a bare compiler name resolve through PATH (injected); the
  unconditional collapse of read-only grants under a shared ancestor, writable ones never
  collapsed, a volume root never the ancestor, `MAX_GRANTS` behavior unchanged.
- Unit (W3): the failure sentence is built from a start failure carrying `granting …` and the
  process's own start count.
- Conformance, the `inferred` fixture (I1, end-to-end): an include completion asked as the reporter
  typed it (`#include "` with the paired quote, then `common/`, letters) asserts on the returned
  items — `replace.end == insert.end` wherever insert passes the cursor — without driving VS Code
  itself. Deterministic; safe under a failed-only rerun.
- Conformance, `engine.cpp` topic (the cliff, Windows and Linux): start the engine, then
  `mcppls.restartEngine` in a loop (nine starts), asserting after each that the engine answers
  again. On 0.21.0 this fails — Windows around the eighth start, Linux around the eleventh (the
  `engine-restarts` fixture caught exactly that during this release's own verification); with W1+W2
  it passes; macOS keeps its roots for now, so the fixture does not run there, and W4 makes it
  every platform's.

## 5. Docs and rollout

  start failure after repeated restarts or a crash loop), cause (openkal 0.20.0's 64 unrecycled

- Order: PR #85 → I1/I2/I3 (one PR, one behavior) → W1+W2+W3 (one PR) → the conformance cliff case
  with them; the plugins need nothing (their middleware is on neither defect's
  path).

## 6. Non-goals

- No change to mcppls-clangd, to openkal, or to mcpplibs.os *in this repository's tree* (W4 is a
  pin bump of released upstream fixes, when they exist).
- No editor-side (plugin) change: the middleware is not on either defect's path.
- No new settings: the grants setting keeps its spelling; behavior improves underneath it.
- Not addressed here: the engine crashes themselves (b2's exit -1 on module-heavy files) — a
  separate defect in the engine's repo; this plan only stops those crashes from becoming an
  unstartable engine.
