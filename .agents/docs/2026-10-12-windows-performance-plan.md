# Windows 专项性能方案：暖启动与编辑补全（2026-10-12）

目标：在 Windows 上，**第二次打开项目**与**编辑时的补全反应**接近 Linux。基线是 mcppls 0.0.13 加 mcppls-clangd 0.0.14。

本文先说清楚一次补全、一次按键、一次暖启动在引擎里各做了什么，再说明 Windows 为什么把这些开销放大。然后逐个分析可选方案，给出分阶段计划和验收预算，最后从多个角度自审。冷启动（第一次构建全部模块）不是主线，只在相关处提到。

## 0. 结论

1. **Windows 上慢的主要不是编译，而是逐文件的元数据检查。** LLVM 在 Windows 上 stat 一个文件，要打开一个句柄（`CreateFileW` → `GetFileType` → `GetFileInformationByHandle` → `CloseHandle`），而且每次打开都要经过 Defender 等文件系统过滤驱动；Linux 上同样的操作只是一次 `stat`。C++ 模块的"能否复用"全靠逐文件确认：扫描缓存重放、BMI 校验缓存、preamble 输入。所以 Windows 上暖启动慢 2.8 倍，最慢的请求慢 4–5 倍，大项目上每次补全光检查就要约 1.2 s。
2. **编辑器协议把这份开销按键次数放大。** clangd 默认一次最多返回 100 条补全。全局模块片段里有 `<windows.h>`、Qt 这类头文件时，几乎每个列表都是 `isIncomplete`，VS Code 就会在每次按键时重新请求。所以在 Windows 上打一个标识符，每个字符都要付一次完整的 clangd 补全。
3. **暖启动没有可以复用的状态。** 扫描缓存和 BMI 校验缓存都只在 clangd 进程的内存里。第二次打开时，要把每个模块单元重新扫描一遍（预处理 `<windows.h>`），并把每个 BMI 的所有用户输入按内容重新算哈希。大项目上一个文件的 25 个前置模块全部复用，也要 28 s：复用检查 8.5 s，扫描与规划约 20 s。
4. **被逐文件核对的头文件，大多来自 mcpp 管理的包。** Windows 上 mcpp 用 xlings 安装的 llvm-mingw，`<windows.h>` 来自它自带的 mingw-w64 头；第三方库也装在 mcpp 的包仓库里，按 `<包>/<版本>/` 组织，并带安装完成标记。这类文件不必逐个核对，**按包版本核对一次**就够了。
5. 因此方案分五层：
   - **产品层减少 clangd 请求**：让 clangd 一次给出完整的列表，由编辑器在本地过滤；同一个词的再次请求用完整列表本地作答。
   - **引擎层减少每次请求的检查**：去掉重复的 stat，系统头每个会话只核对一次，mcpp 管理的包按版本核对，Windows 上用快速 stat。
   - **持久化两个缓存**：暖启动只核对、不重新扫描。
   - **不保留进程的重开优化**：先准备上次活跃的文件，缓存异步加载。
   - **环境建议**：Dev Drive / Defender。

   除"系统头每会话一次"与 clang 自己的默认策略一致外，都不改变"认为什么是新鲜的"。

## 2. 成本模型：引擎里每一步做了什么

### 2.1 一次 stat 在 Windows 上的代价

LLVM `sys::fs::status(path)` 在 Windows 上的实现是 `CreateFileW(..., FILE_FLAG_BACKUP_SEMANTICS)` → `GetFileType` → `GetFileInformationByHandle` → 关闭句柄。打开句柄（IRP_MJ_CREATE）会经过所有文件系统过滤驱动，Defender 实时防护就是其中之一。clang 的 `FileManager` 需要文件的 UniqueID（卷序列号加文件索引），所以不能简单换成不开句柄的 `GetFileAttributesExW`。下文所有"逐文件"的开销，都是在这个单价上乘出来的。

### 2.2 一次补全（`CodeComplete.cpp` 的 module validation 段，加上之后的 Sema）

| 步骤 | 做什么 | 文件系统操作 |
|---|---|---|
| a. 草稿的模块输入 | `getCompletionInputs` / `getRequiredModuleNames`：查扫描缓存（0029 之后，模块单元打字也能命中） | 命中时**重放**这次扫描记录的每一个观测：stat、open、fstat、对磁盘再 stat 一次、关闭。全局模块片段的 `<windows.h>` 就是几百个文件 |
| b. 新 import？ | `isBuildableModule`，有新模块时等最多 250 ms（0027） | 少量 |
| c. 依赖改了吗？ | `canReuse` → 每个 BMI 调一次 `IsModuleFileUpToDate` → `ModuleValidationCache::isFresh` | 每个 BMI stat 一次；每个用户输入 stat **两次**（经 VFS 一次、`sys::fs::status` 再一次）；**整段持有一把全进程锁** |
| d. Sema | 读 preamble 和 BMI，选择性加载（0025） | preamble 默认存在磁盘上（`--pch-storage` 默认 `disk`） |

在大项目上，c 一步就要约 1.2 s（25 个 BMI）。a 一步在 Windows 上占多少还没有数据，阶段 0 去量。全进程锁还会让补全线程和其他 AST worker 互相等待。

c 里的"用户输入"在 clang 看来包括经 `-I` 引入的所有头文件，其中也包括 mcpp 包仓库里第三方库的头文件。clang 的系统头豁免（`ValidateSystemInputs=false`）只对 `-isystem` 和系统目录生效。

### 2.3 一次按键

- clangd 的文档更新（`TUScheduler`）：要判断 preamble 能不能跳过（`hasBuildableRequiredModules`、`getTextualPreambleInputs`），走的也是 a 那条重放路径；防抖之后重建 AST，又要走 c。
- 编辑落在 preamble 区（`#include` 区或 import 区）时，要重建 preamble：带 `<windows.h>` 时是 28 MB、2.4–3.9 s，并写进 `%TEMP%`。
- mcppls 自己的开销很轻：更新单词索引、记录结构变化、发布诊断，都在毫秒级。

### 2.4 编辑器协议的放大

clangd 默认 `--limit-results=100`，mcppls 没有改它，`isIncomplete` 原样交给编辑器。LSP 规定，列表标了 incomplete 时，后续输入要重新计算这个列表，所以 VS Code 每打一个字符就发一次新请求。全局模块片段里有大头文件时，第一个字母之后的匹配往往远超 100 条，于是**一个单词的每个字符都会付一次 2.2 节的完整开销**。mcppls 已有的 C-2（超时的 clangd 结果在同一个词内交出）只是在请求超时以后才起作用。

### 2.5 暖启动（第二次打开）

| 部分 | 现在 | 原因 |
|---|---|---|
| 项目模型 | 内容相同即视为新鲜（0.0.13 W5） | 已解决 |
| 依赖扫描（每个模块单元） | 全部重做，按完整内容预处理 | 扫描缓存只在 clangd 进程内存里 |
| BMI 复用检查 | 完整校验，把每个用户输入按内容重算哈希 | 校验缓存只在内存里 |
| 打开文件的 preamble | 重建 | 不跨会话 |
| 后台索引 | 加载索引分片并核对文件，与上面几项争 I/O | 后台优先级，Windows 上也降了 I/O 优先级 |
| 准备顺序 | 等编辑器的 didOpen 到了才开始准备这个文件 | 服务器不知道上次在编辑哪些文件 |
| 缓存目录换位置 | 全部重建 | BMI 的键与位置有关 |

### 2.6 输入文件的三类来源

| 类别 | 例子 | 会怎样变化 | 现在怎么核对 |
|---|---|---|---|
| 项目文件 | 工作区内的源码和头文件、路径依赖、mcpp 构建生成的目录 | 随时会被编辑、生成、检出 | 每次逐文件核对 |
| mcpp/xlings 管理的包 | `<仓库>/<包>/<版本>/` 下的一切：工具链（llvm-mingw 及其 mingw-w64 头、`<windows.h>`）、第三方库 | 安装后只由 mcpp/xlings 改动（重装、修整），每个版本目录有安装完成标记（`.mcpp_ok`、`.xpkg-install.json`、可能有的 `.mcpp-fixup.json`） | 和项目文件一样逐文件核对 |
| 系统与外部工具链 | 系统 include 目录、外部安装的 Windows SDK 或 MSVC、kit、clang 资源目录 | 系统更新时才变 | BMI 校验已豁免（`-isystem`），扫描重放仍逐文件 |

第二类数量最多（`<windows.h>`、Qt、第三方库都在这里），又最可控：它的变化只来自 mcpp/xlings 自己，而且有标记文件可以确认。B2 就是按这三类分别处理（§4）。

## 4. 方案分析

收益估计都标明了依据，最终以阶段 0 的度量为准。

### A. 产品层：减少发给 clangd 的补全请求

**A2 让 clangd 一次给出完整的列表**（采纳，阶段 1，是这一组的主体）

- 编辑器对**完整**的列表（`isIncomplete: false`）会在本地按后续输入过滤，不再请求；逐键请求只发生在列表不完整时。列表不完整，绝大多数是因为 clangd 的结果上限（`--limit-results`，默认 100）。
- mcppls 给内置引擎传入更高的上限（默认 1000，由阶段 0 的度量确定）。匹配数在上限以内时列表就是完整的，同一个词之后的输入完全由编辑器处理，一个词只请求一次 clangd。
- 代价：第一次回答的 JSON 变大（1000 项约几百 KB，本地管道传输与解析都在毫秒级），clangd 为更多项生成细节。阶段 0 用 `ux-modules-qt` 和大 fixture 量 100 与 1000 的单次耗时，增加超过 20% 就降低上限。
- 第一个字母就匹配上几千个名字时（`<windows.h>` 的 `C`），列表仍然不完整，下一键照常请求 clangd；通常到第二、三个字母就完整了。

**A1 同一个词内的再次请求，用完整列表本地作答**（采纳，阶段 1；界面上不区分，只写进日志和 report）

- 有的客户端每次按键都请求，不看 `isIncomplete`；VS Code 也会在某些情况下重新触发。对同一个词的再次请求，如果 clangd 上一次给这个词的回答是**完整的**，就用它在本地作答：
  1. 同一个文件，光标仍在这个词里（`word_key`/`typed_on`，C-2 已有）；
  2. 词起点之前的全部文本、光标之后的全部文本都与那次回答时相同（逐字比对两段的哈希）；
  3. 每一项的插入范围改写成"从词的起点到当前光标"（C-2 已有的 `retarget`），`filterText`、`sortText`、`score`、`additionalTextEdits` 不变，过滤和排序交给编辑器。
- 上一次的回答不完整（包括 0027 的部分模块回答），就照常请求 clangd，不在本地作答。所以本地答案的候选集合与 clangd 当时给出的完全相同，不会漏项，也不需要后台刷新。
- 它是 C-2（超时答案按词交出）的推广，复用同一套数据结构。
- **退出开关**：命令行 `--no-completion-refilter`，供排查用，不做成用户设置。

### B. 引擎层：每次请求的文件系统检查

**B1 校验缓存：stat 时不持锁**（采纳，阶段 1，可上游）

- 先在锁内把条目拷出来，在锁外做 stat，最后再加锁比对并删除。补全线程和 AST worker 不再串行等这把全进程锁。
- 每个输入的两次 stat（经请求的文件系统一次、直接对磁盘一次）**保留**：`IsModuleFileUpToDate` 有多个调用点，传入的文件系统可能是带 stat 缓存的，对磁盘的那一次是防止旧状态的安全网。减少 stat 的工作交给 B2（按来源跳过）和 B3（更便宜的 stat）。
- **风险**：无。判定条件不变。

**B2 按来源分类核对输入**（采纳，阶段 1；分类见 2.6）

- **B2a 系统与外部工具链**：扫描缓存重放时，路径落在系统 include 根（`-isystem` 指向的系统目录、外部安装的 SDK 或 MSVC、kit、clang 资源目录）下的观测，本会话成功重放过一次后就不再重放。
  - 依据：clang 对模块输入本来就默认不检查系统头。mcppls 发现工具链变化时已经会重启 clangd。
  - 风险：会话中途系统更新头文件，要等 clangd 重启才生效，与 clang 的默认策略一致。
- **B2b mcpp/xlings 管理的包**：以**包版本**为单位核对，不再逐文件。
  - **包版本的身份**：版本目录下安装标记文件的身份（`.mcpp_ok`、`.xpkg-install.json`，以及存在时的 `.mcpp-fixup.json`），加上 `.xpkg-install.json` 里的 revision。
  - **适用范围**：扫描缓存重放、BMI 校验缓存（这些头经 `-I` 进来，clang 当作用户输入），以及 D1、D2 的持久化条目。一次请求里，同一个包版本只核对它的标记文件，大约 3 次 stat，取代几百次。
  - **哪些路径算包**：由 mcppls 告诉引擎。mcppls 已经知道 mcpp 和 xlings 的包仓库位置，以新的引擎参数传入（例如 `--managed-input-root=<仓库>`，可重复）；引擎按 `<仓库>/<包>/<版本>/` 切出包版本。路径依赖、`[patch]` 指向本地目录的包，以及 mcpp 构建生成的目录（`<mcpp 缓存>/build-database/…/deps/<包>@<版本>/out/`），都不在仓库下，仍按项目文件处理。
  - **失效**：任何一个标记文件的身份变了，这个包版本的所有记录都失效，回到逐文件核对一次，然后记下新身份。另外，mcpp 的描述回答报告了安装类 effects 时，mcppls 让引擎丢掉所有包身份记录（新的引擎通知，或者重启引擎，取实现更简单的一种）。
  - **依据**：mcpp 安装的库是规范、可控的模型：一个版本装进自己的目录，装完写完成标记，之后只有 mcpp/xlings 会动它。
  - **风险**：如果有人手工改了包仓库里的头文件又不动标记，mcppls 看不到这个改动，直到包被重装或标记变化。这是使用包仓库时的预期行为，文档里写明。
- **它与已撤掉的 UP-34 的区别**：UP-34 不分来源，对项目头也放宽，`module_preamble_mode` 用项目头测出了问题。B2 对项目文件什么都不改，那个测试的语义不受影响。
- **收益**：Windows 上 `<windows.h>`（mingw-w64，在 llvm-mingw 包里）和第三方库头的逐文件核对，从每次请求几百次 open/stat，降到每个包版本几次 stat。按 2.2 节，这是 a、c 两步的大头；确切比例由阶段 0 量出。

**B3 Windows 快速 stat：`GetFileInformationByName`**（采纳，阶段 2，可上游到 LLVM Support）

- Windows 11 24H2 和 Windows Server 2025 起，`GetFileInformationByName(FileStatBasicByNameInfo)` 不用打开句柄，就能拿到文件 ID、卷序列号、大小和时间，足够构造 UniqueID。运行时用 `GetProcAddress` 探测，没有这个 API 时回到现在的实现；符号链接和重解析点也走旧路径。
- **收益**：每次 stat 从 4 次系统调用加一次过滤驱动的打开，变成一次调用，估计单价降到 1/2–1/4（需实测）。B2 之后剩下的都是项目文件，B3 让它们也变便宜。
- **CI 限制**：GitHub 的 `windows-2022` 镜像是 Server 2022，没有这个 API，度量需要 `windows-2025` 镜像。
- **风险**：API 较新，回退路径必须保留并测试。

**B4 按目录批量 stat**（阶段 3，取决于 B2、B3 之后的数据）

- 同一个操作里要核对同一目录下的很多项目文件时，用 `NtQueryDirectoryFile(FileIdExtdDirectoryInformation)` 一次读出整个目录的文件 ID、大小和时间。
- NTFS 目录项里的大小和时间是延迟更新的，修改时间离现在不到 30 s 的文件要回到逐文件 stat（与扫描缓存现有的 `unchangedOnDisk` 规则一致）。
- B2 之后剩下的多是项目文件、目录分散，收益可能不大；数据不支持就不做。

**B5 以文件监视为准信任项目文件**（不进本期）

- 正确性取决于编辑器的监视是否可靠（VS Code 在高负载时会丢事件），引擎的 e2e 测试也明确守着"没有事件也要看到改动"。B1–B3 做完后，项目文件的核对已经不是瓶颈，不需要冒这个险。

**B6 复用最近一次重放**（已否决）

- 这就是 mcppls-clangd 0.0.14 试过又撤掉的 UP-34。B2 是它安全的部分：只放宽来源可控的那两类。

### C. preamble 与 AST

**C1 Windows 上 preamble 放内存**（阶段 1，A/B 度量后决定默认值）

- `--pch-storage=memory`：preamble 不写 `%TEMP%`，避免 Defender 扫描 28 MB 的临时文件，也省掉写盘再映射回来读。代价是常驻内存，约等于打开文件数乘以 preamble 大小。
- 默认只在 Windows 上、物理内存不少于 16 GB 时开启。
- 新设置 `mcppls.engine.preambleStorage`：`auto`（默认，按上面规则）、`disk`、`memory`。

**C2 AST 保留数可配置**（阶段 2，引擎加开关）

- `MaxRetainedASTs` 写死为 3，没有命令行开关。Windows 上大 preamble 的文件来回切换时，悬停和跳转要重建 AST。
- 增加 `--max-retained-asts`，mcppls 按物理内存给出默认值（16 GB 以上为 6），只传给声明了这个开关的引擎。

**C3 preamble 跨会话复用**（不进本期，D、G 之后的首选候选）

- 收益在 S1、S10，但它的键（preamble 文本、命令、所有输入的身份）和体积管理都比较复杂。F1 不做之后，它是剩下的重开手段里最大的一项；D、G 落地后，用启动行和 cost 行看 preamble 在 S10 里的占比再定。

### D. 暖启动：持久化与扫描

**D1 持久化 BMI 校验缓存**（采纳，阶段 2，可上游）

- 进程退出时（以及周期性地）把 `ModuleValidationCache` 写进工作区缓存目录，启动时读回。条目本来就带着 BMI 和每个用户输入的身份（大小、修改时间、文件 ID），读回后照样核对：项目文件逐个 stat，包内的输入按 B2b 的包版本身份核对，有任何不一致就回到完整校验。
- **收益**：第二次打开时，复用检查从"按内容重算哈希"变成"核对身份"。大项目上那 8.5 s，加上 B1、B2、B3，估计降到 1 s 以内。
- **风险**：文件 ID 在复制或恢复的目录上会变，这时回到完整校验，结果仍然正确。

**D2 持久化扫描缓存**（采纳，阶段 2）

- 把 `ModuleScanManifest`（观测记录）和扫描结果写到磁盘，键与现在相同（文件、命令、主文件内容摘要、环境），读回后照样重放：项目文件逐个重放，包和系统根按 B2 处理。
- **收益**：第二次打开时，每个模块单元从"预处理 `<windows.h>`"变成"核对"。大项目上约 20 s 的扫描与规划，是这一项的目标。
- **风险**：重放规则不变，所以正确性不变。体积受现有的字节上限约束。

**D1、D2 的共同约定**

- 文件放在 mcppls 的工作区缓存目录下（由 mcppls 以引擎参数传入），计入现有的缓存预算，"重置缓存"会清掉它们。
- 格式带版本号和引擎身份（fork 版本、补丁序列哈希），不匹配就整体丢弃。
- 写入用"写临时文件再改名"，只由持有工作区租约的实例写；损坏或读不懂就丢弃。
- 读入在引擎启动时**异步**进行，读完之前的查询按缓存未命中处理，不阻塞第一个请求。

**D3 磁盘上的模块源也按前缀扫描**（采纳，阶段 2，引擎）

- 0029 只对草稿（编辑器里的文本）生效。对磁盘上的模块源也做同样的切分（模块声明加紧随的 import），自动保存改正文时扫描缓存仍然命中。
- **收益**：减少 S5、S7 里导入方重建前的扫描（Windows 上约占一次重建的一半），也减少 D2 的失效。

**D4 BMI 的键与缓存位置无关**（阶段 3）

- 去掉命令键里与缓存目录有关的参数，按模块名和内容身份重新组织。缓存搬家、多个工作区副本之间就能复用。用户场景少，CI 和容器场景多。

**D5 暖启动时后台索引延后**（阶段 2，先度量）

- 后台索引在打开的文件拿到第一次诊断之后再启动，避免暖启动时争 I/O。只有在度量显示它确实影响 S1 时才做。

### E. 环境

**E1 Dev Drive 与 Defender 提示**（采纳，阶段 1，产品与文档）

- 启动时探测缓存目录所在卷是不是 Dev Drive（`GetVolumeInformationW` 加卷持久状态里的 Dev Drive 标志）。不是时，在 report 和 hub 概览的环境信息里写一行，并在文档里说明两种做法：把 `MCPPLS_CACHE_DIR` 放到 Dev Drive 上（Defender 对 Dev Drive 用异步的性能模式扫描），或者由用户自己为缓存目录添加 Defender 排除。
- 不弹窗、不重复提示。**mcppls 不自动修改任何安全设置**，也不提示以管理员身份运行。
- CI 上用 Dev Drive（VHD）做一次 A/B，把对 S1、S10 的影响写进文档。

### F. 编辑器关闭后让 clangd 保留一段时间（已否决）

- 编辑器关闭后还留着语言服务进程，不符合用户习惯。重开的开销改用 D 组（持久化）和 G 组（不保留进程的重开优化）解决，C3 作为之后的候选。

### G. 不保留进程的重开优化

**G1 先准备上次在编辑的文件**（采纳，阶段 2，产品）

- mcppls 在工作区状态里记下每次会话最后打开、最后活跃的几个文件（只记路径，存在本地缓存目录）。下次 `initialize` 之后、编辑器的 `didOpen` 到来之前，就按这个顺序让引擎准备它们的前置模块。这复用现有的 prime 机制，以及"有文件在等前置集合时，prime 只用剩下的 worker"的规则（R-1）。
- 编辑器恢复窗口、插件激活本身就要几秒，这段时间用来校验和装载模块。
- 做法：模型就绪、数据库写好后，用 mcppls 已有的"后台打开"机制（找定义和补索引时用的那一套）把这些文件在 clangd 里打开。编辑器随后打开同一个文件时，**接管**而不是关闭重开：发一次全文更新（编辑器的文本），clangd 沿用已经建好的 preamble，诊断照常发给编辑器。
- 只准备上次真正打开过、现在仍存在、仍在计划里、编辑器还没打开的文件；最多 5 个，只记当前工作区。两分钟内编辑器没有打开的，就关掉。
- 收益主要在恢复后的非前台标签页（切过去时 preamble 已经建好）和打开时机晚于模型就绪的情况。

**G2 BMI 预读**（阶段 2，先度量）

- 重启或长时间不用之后，BMI 不在系统文件缓存里，第一次装载要真正读盘。G1 选出的文件，在后台以低 I/O 优先级顺序读一遍它们的 BMI，让之后的映射命中缓存。
- 只有度量显示 S1 里冷读盘占比明显时才做。

## 5. 计划

所有阶段在一个版本里交付：产品 0.0.14，引擎 mcppls-clangd 0.0.15。按惯例单 PR，以 commit 作为检查点；引擎 PR 先由产品 CI 通过 `engine-candidate.json` 测过再合入。

### 阶段 0：度量（先做，决定 A2、B3、B4、C1、D5、G2 的取舍和参数）

1. **引擎的 cost 行**：慢的补全（超过 200 ms）在 info 级别说明时间花在哪，格式与 0026 的 "Prerequisites of" 一致：`Completion in <file>: 412 ms (scan replay 40 ms over 380 inputs, module validation 280 ms over 25 BMIs / 1340 inputs, wait 0 ms, sema 90 ms)`。文档更新和 preamble 构建各加一行。
2. **VFS 操作计数**：用一个计数用的 VFS 包装 clangd 的真实文件系统，统计每个操作的 stat、open、目录遍历次数，**按 2.6 节的三类来源分开**，写进上面的 cost 行。B2 的收益直接从这里读出来。
3. **Windows 大项目 fixture `ux-modules-windows-large`**：在 prepare 阶段用脚本生成，仓库里只存生成器。30 个模块单元，全局模块片段都 include `<windows.h>` 和几个项目头，依赖链深 4，`main.cpp` import 25 个模块（贴近探针里那个文件），另有一个经 mcpp 依赖引入的第三方库头。场景：
   - S10 暖启动：第一次跳转、第一次补全；
   - S2 空闲补全；
   - S3 逐键补全（新的 typing 模式：clangd 返回 incomplete 时每个字符都重新请求，与 VS Code 一致）；
   - S5 在模块单元里打字（U16 式）；
   - S8 编辑 `#include` 区；
   - S9 在 4 个文件之间切换。
4. **Windows runner**：`windows-2022` 与 `windows-2025` 各跑一次（B3 需要后者），另加一次 Dev Drive 的 A/B（E1）。
5. **摘要**：conformance 的 measure JSON 按场景写出 p50/p95，CI 摘要分平台列表，不用下载大文件。

### 阶段 1：每次请求和每次按键

A1、A2、B1、B2a、B2b、C1（A/B 后定默认值）、E1。

### 阶段 2：暖启动和 Windows stat

D1、D2、D3、B3、C2、G1，以及度量后决定的 D5、G2。

### 阶段 3：视数据而定

B4、D4；C3 是否立项。

| 依赖外部约定 | B2b 依赖 mcpp 的安装模型 | 与 mcpp 确认并写进它的文档：版本目录安装后只由 mcpp/xlings 改动，改动会更新标记文件。长期更好的方式是 mcpp 在描述回答里直接给出包根和安装身份（见 §9） |

## 8. 风险与已否决的方案

- **已否决**：
  - B6（UP-34，补全看不到编辑器外的项目头改动）；
  - F1（编辑器关闭后保留 clangd，不符合习惯）；
  - 以任何形式自动添加 Defender 排除，或要求管理员权限。
- **风险**：
  - A1 的排序与 clangd 直接回答有细微差别。缓解：保留 `sortText` 和 `score`，最终排序交给编辑器。
  - B2b 依赖 mcpp 的安装模型。缓解：标记文件身份加上安装 effects 两道失效；与 mcpp 确认这条约定。
  - D1、D2 文件损坏或格式变化。缓解：带版本，坏了就丢弃，结果仍然正确。
  - B3 依赖新的系统 API。缓解：运行时探测，保留回退路径，并在两种 runner 上测试。

## 9. 决定与待定

**已决定**：

1. 系统目录与 mcpp 安装的包分开处理：系统目录每会话核对一次（B2a），mcpp/xlings 管理的包按包版本核对（B2b）。
2. C1 在 Windows 上默认开启的门槛是物理内存 16 GB。
3. A1 的本地答案在界面上不区分，只写进日志和 report。
4. 编辑器关闭后不保留 clangd（F1 否决），改用 D 组和 G 组优化重开，C3 作为之后的候选。

5. B2b 的包身份用标记文件（`.mcpp_ok`、`.xpkg-install.json`、`.mcpp-fixup.json`），不改 mcpp。原则是尽量解耦，只有像 emit build-database 这样必须两边联动的才配合开发。
6. G1 记录最近活跃的 5 个文件，只记当前工作区。

**待定**：无。
