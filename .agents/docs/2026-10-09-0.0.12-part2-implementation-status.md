## 已完成的证据与范围调整

- 维护目标为 `linux-x64`、`win32-x64`、`darwin-arm64`；保留 Ubuntu 20.04 运行下限。Intel macOS 历史失败保存，不继续适配或作为门槛。
- 正式引擎仍是 67 个补丁/67 条台账。PR head `d2140299d1a68a68d15acfb5f9ccec844621eea0` 的 CI `37797560280` 三平台与 Ubuntu 20.04 全部通过；实际 built merge checkout 为 `771501f43131a716419f07068b33a16fded8d49b`。这不包含私有 PCH 集成候选。
- Linux third-party-import 原失败已解释并补齐契约：正文导入可保留完整审计的 import-free PCH；header 导入必须收缩。原生 Linux 的 12,187,172-byte PCH 在正文阶段合法保留，header 阶段收缩到 251,880 bytes。ARM macOS、Windows 均走保守收缩路径。三场景与五次实际 typed Sema 均通过，原始 artifact 归档在引擎 `tests/evidence/part2-linux/third-party-contract/`。
- Manifest 插桩发现：622 个路径各 open/close 三次，只读一次，共约 9.22MB。代表性 replay 计量的底层 FS 成本约 7.53ms；额外 shadow hash 约 2.17ms，不能作为原 hash 的 exclusive 时间。需要文件会话来源证明才能合并重复 open；目前没有生产路径缓存优化。
- 空 index 的 USR 候选通过 136 项 CompletionTest 和此前四次 GCC 插入，但短 A/B/A 的 edited 中位数仍约 240ms，没有关键收益，暂不导出。

## 当前 PCH 集成候选：正确性初步通过，性能负例

私有源 `/tmp/mcppls-pch-scan68-review` 基于最终 joint67 `66ed2d104d8affc9e75c82a5b015f9e6869a6b00`，涉及公共头文件的 141 个消费者已重建后才执行。已通过借用 entry eviction 后仍计费、当前正文选择新 import、same-size/same-mtime header 失效、`__COUNTER__` 函数体影响正文条件导入，以及选定现有前缀/alias/dirty-header 控制。不能据此称完整正确性通过。

首次原始 Qt std 探索回放四次真实语义与选定 GCC 插入均通过，但 cold 约 7.31s、warm 约 434/309ms、edited 约 1.33s，明显回退。精确 diff、构建配方、身份、报告与 trace 保存到引擎 `tests/evidence/part2-linux/pch-first-negative/`，没有导出 0068。

两个已定位的问题决定下一步实现：

1. 成功路径反复重放 canonical-prefix/compiler/current-full manifests。源码计数有四次 prefix+compiler 成对验证、约五次 full manifest 验证，单次 proof revalidation 实测约 33–76ms。先设计同一 validate-and-consume 事务，保留输入变化、重建及可能 I/O 后的必要验证，不跨请求复用旧证明。
2. 编辑触发 fresh scan 时，在读 PCH 前因宏向量顺序不同被误拒绝；随后候选拒用 PCH，语义执行增至约 1.19s。LLVM `DependencyScannerImpl.cpp` 已在 hook 前调用 `canonicalizeDefines`，候选却与普通 invocation 的原宏顺序比较。实际 Qt 两侧宏/value 集合一致。本地候选正在对临时 owned PP 副本使用同一 LLVM 函数后比较，不改真实宏或关闭 PCH 校验。此问题属于候选实现，不能称为新的上游缺陷。
