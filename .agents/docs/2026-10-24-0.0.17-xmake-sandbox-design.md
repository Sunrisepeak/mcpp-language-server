# 0.0.17 增修：xmake 私有运行的隔离与自愈（#68、#69）

日期：2026-10-24。状态：**已实现**（PR #67；D1 进 0.0.17，D2 全部构建工具，D3 纳入所有 `xmake.lua`）。基线：PR #67 head `e929d12`（引擎已切到 mcppls-clangd 0.0.17 正式版）。
上游登记：#24 的 [UP-X1](https://github.com/Sunrisepeak/mcpp-language-server/issues/24#issuecomment-6370881870)（mapper 文件共享）、
[UP-X2](https://github.com/Sunrisepeak/mcpp-language-server/issues/24#issuecomment-6370882444)（describe 依赖只有构建才更新的模块缓存）。

## 0. 结论

| issue | 用户看到的 | 根因 | 归属 |
|---|---|---|---|
| #69 | mcppls 跑过之后，自己的 `xmake` 增量构建报 `failed to read compiled module`，路径指向 mcppls 的缓存 | mcppls 私有运行写了 xmake 共享临时目录里的 GCC mapper 文件（UP-X1） | **mcppls 的副作用越界**，xmake 的缓存 key 设计是底层原因 |
| #68 | 重新打开项目后，第三方库（gtest）头文件找不到 | mcppls 私有目录里的 xmake 模块缓存过期且不自愈（UP-X2），每次 describe 失败，退回 `inferred` | 坏的是 **mcppls 自己的私有状态**，用户的 `.xmake/`、`build/` 未受影响；xmake 缺陷，mcppls 的用法（只 describe、跨会话复用、原地重配）正好踩中 |

工程文件（`xmake.lua`）没有问题：同一份工程，guest 实例用全新私有目录每次都成功，用户自己的构建也正常。

## 1. 责任划分

mcppls 读用户的构建，不替用户构建，也不替 xmake 修状态。由此：

- **必须做**：mcppls 子进程的一切写入只落在 mcppls 自己的目录里（#69 是这条被违反）。
- **可以做**：mcppls 自己的私有目录是缓存，坏了就丢掉重来（#68）。
- **不做**：
  - 在私有目录里跑 `xmake build` 来"修"缓存：这是一次真正的编译，有下载包、执行规则脚本等副作用；
  - 修改 xmake 的缓存文件；
  - 改动用户的 `.xmake/`、`build/`、`~/.xmake`；
  - 锁定 xmake 版本。
- **用户自己**跑 `xmake project` 碰到 UP-X2，或两个 checkout 碰到 UP-X1：mcppls 不处理，只把 xmake 的原话和绕法讲清楚。xmake 的问题在 #24 登记，报给上游。

## 2. 证据

**log 包**（#68、#69 两个 bundle 共 12 个会话）：

- owner 实例（私有目录 `workspaces/<ws>/xmake/`）的 describe **全部失败**：08:48、09:10、13:18、15:07、15:08、15:16。
- guest 实例（`instances/<id>/xmake/`，每次全新）**全部成功**：06:51、08:49、09:11、15:07、15:08、15:18。
- 失败的会话退回 `inferred`，engine 数据库里没有 `-isystem …/gtest/include`。
- 15:16 那次是 release 模式下 `xmake f -c` 之后紧接着 describe，失败在 `module/data.cppm`：release 的 dependfile 从未生成，xmake 却认为"已扫描"。
- 用户点过多次 "reset cache"，都没用：它只删 `model.*.json`，不碰私有 xmake 目录。
- #69 截图中的 BMI hash `8cd20c490f207114`，和本地复现得到的完全一致。

**纯 xmake 复现**（默认布局，不经过 mcppls；xmake 3.1.1、3.1.2，GCC 16.1）：

- UP-X1（mapper 共享）：
  - 同一项目先用第二个 builddir 做 describe，再在自己的 builddir 增量构建：失败。
  - 同一项目的两个副本（例如两个 git worktree）同一天交替构建，删掉第二个后，第一个增量构建：失败。
  - 同一项目 debug、release 交替构建：不受影响。
- UP-X2（模块缓存过期）：只 describe、从不构建的项目，加一个 target 后删掉 `build/`，之后每次 `xmake project -k compile_commands` 都失败，`xmake f -c` 也恢复不了，构建一次才恢复。3.1.1 上，加 target 后切到 release 也会失败（3.1.2 不会）。

**未查明**：报告者私有目录里 dependfile 具体是怎么丢的（报告者的 xmake 版本不在 bundle 里）。下面的方案不依赖这一点。

**修复验证**（本地）：加 `XMAKE_TMPDIR` 后，用户的 mapper 文件 md5 不变，用户的增量构建成功；全新私有状态下的 describe 总是成功（guest 实例的每一次运行也证明了这一点）。

## 3. 方案

### XS-1　隔离临时目录（#69）

`xmake_environment()` 增加 `XMAKE_TMPDIR=<私有目录>/state/tmp`，和已有的 `XMAKE_CONFIGDIR` 并列。`XMAKE_TMPDIR` 是 xmake 公开的环境变量（`xmake show -l envs` 列出）。

### XS-2　私有状态是可丢弃的缓存（#68 的预防）

- **布局**：`<cache>/xmake/state/{config,build,out,tmp}`，加上标记文件 `state/configured`。`xmake-help` 自带 key，仍放在 `<cache>/xmake/` 下。
- **key**（写进 `configured`）在现有的基础上补两项：
  - 现有：在线/离线、`xmake.lua` 的戳、用户 `xmake.conf` 的戳；
  - 补充：xmake 可执行文件的身份（路径、大小、mtime）；
  - 补充：根 `xmake.lua` **以及它 `includes()` 的所有 `xmake.lua`** 中最新的 mtime 和文件数。`xmake-help` 的 key 已经用了 `xmake_manifests()`，这里保持一致。
- **key 变了**：先 `remove_all(state)`，再从空目录 `xmake f -c …` 配置。不再在旧状态上原地重配。这样"加 target"、"切模式"、"升级 xmake"这几种情况都从全新状态开始，UP-X2 无从触发。
- **代价**：每次改 `xmake.lua` 多一次全新扫描。log 中 configure 约 1.1 s、describe 约 0.85 s，现状本来就会在 `xmake.lua` 变化时重新配置，增量很小。
- **磁盘**：只保留一份 state。

### XS-3　一次自愈重试（#68 的兜底）

key 没变、但状态依然过期时（比如目录被外部改动、xmake 自身的边界情况），按 xmake 的原话识别：

- `dependfile for '…' not found at '…'`
- `module scanner did not run for target(`
- `failed to load moduleinfo for '`

只在**这次调用开始前 state 就已存在**时才处理。处理方式：丢掉 state，从头配置，再 describe 一次；记一行日志（带 xmake 的原话），两次运行都留在报告的 `toolRuns` 里。还失败，就走现有的失败路径。（实现差异：provider 没有 journal 的接口，所以没有加 journal 事件。）

工程错误（比如 `missing json dependency for module …`）不在识别范围内，照常报给用户。

### XS-4　reset cache 包含构建工具的私有目录

`Workspace::reset_cache()` 现在只删 `model.*.json`。增加删除各 provider 的私有目录 `<cache>/<provider id>/`（见 D2），使"reset"的含义和用户的预期一致：mcppls 推导出来的东西全部重来。

### 不在本次范围（0.0.18）

- producer 失败时，保留上一次成功的 xmake 模型（标为 stale），而不是退回 `inferred`。
- 模型问题的提示文字按 UP-X2 给出绕法。

## 4. 多角度

- **架构**：改动全部在 `src/project/xmake.cpp` 的 `run_private` 及其辅助函数，加上 `reset_cache`。provider 接口不变，其他构建系统不受影响（D2 除外）。
- **稳定性**：
  - 预防（XS-2）和兜底（XS-3）分层：XS-3 最多重试一次，不会循环；
  - 私有状态不跨 xmake 版本复用，xmake 升级不会带来旧状态问题。
- **优雅简洁**：用"按 key 丢弃"代替"原地重配 + 各种修补"，代码路径反而少了 `-c` 原地重配这一支。
- **用户体验**：
  - #68 用户不再丢失第三方 include，不需要手动清缓存；
  - #69 用户的构建不再被打断；
  - reset 真正有效。
- **兼容性**：
  - 用户的 `.xmake/`、`build/` 继续只读；
  - 不支持 `XMAKE_TMPDIR` 的旧 xmake 会忽略这个变量，退回现状（只是没有隔离），不会出错。
- **跨平台**：
  - 路径用 `base::join_path`；
  - `XMAKE_TMPDIR` 是 xmake 跨平台的环境变量，但只在 Linux 上实测过，Windows/macOS 要在 CI 上确认；
  - mapper 只在 GCC 下出现，其他工具链设置这个变量也无害。
- **一致性**：
  - key 的构成和 `xmake-help` 的 key 一致（都用 `xmake_manifests()`）；
  - journal 事件和日志措辞沿用 provider 的现有格式；
  - #24 的 UP-X1/X2 行在发布时更新为 "shipped in 0.0.17"。
- **无感升级**：
  - 0.0.16 的旧布局（`<cache>/xmake/{config,build,out,configured,left-out}`）在第一次运行时被删掉，并在新布局下从头配置；
  - 用户无需任何操作，升级后第一次 describe 多花约 1–2 s；
  - 已经处在 #68 状态的用户，升级后自动恢复。

## 5. 测试与验收

**单元测试**（`tests/test_xmake*.cpp`，不起 xmake）：

- `xmake_environment()` 包含 `XMAKE_CONFIGDIR`、`XMAKE_TMPDIR`、`XMAKE_THEME`；
- 新增的识别函数 `xmake_state_stale(output)`：三种原话为真，`missing … dependency`、`Invalid option`、包缺失为假；
- `xmake_configuration_key()`：xmake 身份或任意 included 的 `xmake.lua` 变化时，key 也变化；
- 旧布局识别和清理。

**conformance**（真实 xmake，CI 固定 3.1.1，GCC 16）：

- **新 fixture `xmake-shared-tmp`（#69）**：
  - 准备阶段：用户自己 `xmake f && xmake` 构建一次（模块库 + 实现单元）；
  - mcppls describe 完成（status ready，source xmake）；
  - 新 check kind `run`：在工作区里改动实现单元，再跑 `xmake`，要求 exit 0；
  - runner 给进程设一个专用的 `XMAKE_TMPDIR`，使用户和 server 共享同一个临时目录（这正是 #69 的条件），同时不污染 CI 机器；
  - 0.0.16 必须失败，新版必须通过。
- **新 fixture `xmake-target-then-mode`（#68）**：
  - 初始只有库和 app，用户的配置是 debug；
  - 用 `write-file` 加一个依赖库的 `json-test` target，等 reload 完成；
  - 再用 `write-file` 把用户的 `xmake.conf` 改成 release，等 reload；
  - 断言 source 仍为 xmake，`json-test` 的 engine 命令里有 release 的标志；
  - 在 3.1.1 上 0.0.16 预期失败（退回 inferred），新版必须通过。纯 xmake 下验证过的是 `xmake f -m release` 这个序列，mcppls 实际执行的是 `f -c`，所以实现时要先确认 0.0.16 确实失败；如果不失败，就改用 XS-3 的识别路径构造这个 fixture（例如外部删掉私有的 `.d`）。
- **新 check kind `run`**：在工作区里运行给定程序，断言退出码。现有的 `cli` 只能运行 mcppls 本身。
- **新 fixture `xmake-stale-state`（XS-1、XS-3、XS-4，实现时增加）**：用 stand-in `xmake` 脚本（POSIX），它的私有状态会像真实 xmake 那样过期：同一份状态里第二次 `xmake project` 报 `dependfile ... not found`，重新配置也修不好。
  - 第一次会话：`XMAKE_TMPDIR` 在 mcppls 的私有目录里；
  - 杀掉 server 再启动（等于重新打开编辑器，即 #68 的场景）：过期状态被丢掉并重建一次（这次会话 1 次配置、2 次 describe），模型保持 xmake，没有 stale；
  - `mcppls.resetCache` 之后：私有状态已经删掉，下一次加载不会失败。
- **本地结果**：三个新 fixture 在 0.0.16 上都失败（3、1、6 项），新版全部通过；5 个原有的 xmake fixture 通过。xmake 3.1.2 下 `xmake-shared-tmp` 同样能区分新旧；`xmake-target-then-mode` 的模式切换在 3.1.2 里已经由 xmake 修好，CI 固定 3.1.1，在那里能区分。
- **回归**：`xmake-basic`、`xmake-late-config`、`xmake-user-mode`、`xmake-no-standard`、`xmake-needs-download` 全部通过；`W1 workspace-unchanged` 保持。

**本地**：`/tmp/xm/*.sh` 的纯 xmake 脚本在 3.1.1、3.1.2 上复跑；用报告者布局（模块库、实现单元、`import std`、测试 target）走一遍 #68、#69 的序列。

## 7. 对 0.0.17 发布的影响与需要你决定的事

- 只改 mcppls，引擎不动。#67 上多一个提交，再跑一轮 PR CI（约 50 min）；xmake 不在 ux nightly 里，不需要重跑 nightly。
- **D1**：进 0.0.17（推荐：代码量小，修的是 0.0.16 用户正在遇到的两个问题），还是放 0.0.18。
- **D2**：reset 清哪些私有目录：只清 xmake，还是所有构建工具（cmake、meson、xmake）？推荐全部清：reset 的语义一致；cmake 重新配置的代价只在用户主动 reset 时发生。
- **D3**：key 是否纳入所有 `includes()` 的 `xmake.lua`？推荐纳入：target 常常定义在被 include 的文件里，不纳入的话那条路径只能靠 XS-3 兜底。

## 8. 风险

- **XS-3 的识别依赖 xmake 的报错原话**：xmake 改了措辞就识别不到，退回现状（describe 失败、给出提示），不会更糟；XS-2 不依赖原话。
- **全新扫描的代价**：每次改 `xmake.lua` 多约 1–2 s，这段时间里规划用的是缓存的模型，用户不需要等待。
- **D2 选"全部清"时**：大型 cmake 项目在用户 reset 之后，要多等一次私有配置。
