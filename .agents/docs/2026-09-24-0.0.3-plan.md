## 1. B1: a clangd that cannot start hangs the editor

**Found** while asking what a user on an unsupported arm64 system would see. A stand-in clangd that
does what the dynamic loader does on such a system (prints ``version `GLIBCXX_3.4.30' not found``,
exits 1) was given to the server over LSP
([`probe-clangd-start-failure.py`](assets/2026-09-24-0.0.3/probe-clangd-start-failure.py)):

| Server | `initialize` answered? |
|---|---|
| 0.0.2 (installed payload) | no, still unanswered at 330 s |
| `main` 37ce3d7 (after #18) | no, still unanswered at 200 s |

The server restarts clangd with a growing backoff (exits at +0, +1, +11, +31, +71 s), and after the
fifth exit it gives up on clangd (`unavailable_`). But nothing ever answers `initialize`. Requests
sent anyway are answered by the module engine: definition on `import hello` and completion after
`import ` both work. A real client never sends them, though, so in VS Code the extension stays
"starting" with no features at all, and the status never says why.

**Root cause.** `initialize` is answered from `engine_settled` (`src/server/session.cpp:348`).
Every startup failure `start_process_` can see calls it: payload corrupt, clangd missing, spawn
failed (`src/engine/clangd.cpp:958-1040`). A clangd that spawns fine and then **dies before the
handshake** goes to `handle_closed_` (`src/engine/clangd.cpp:1399-1436`), which never calls it. The
"did not answer initialize" timeout (`:840`) only fires while a clangd process is still alive.

This does not depend on arm64. Anything that kills clangd at load time hits it: a musl
distribution (Alpine) on x64, a `noexec` mount, an antivirus quarantine, a truncated payload. With
the official arm64 clangd (§5) it becomes the *normal* outcome on RHEL 9, Amazon Linux 2023 and
openEuler 22.03, which is why it goes first.

**Fix.**
1. `handle_closed_`: if this clangd never completed its handshake, and `initialize` has not been
   answered, report settled with no engine capabilities. The client then gets mcppls's own
   module-level features at once, the same result the "clangd missing" path already gives.
2. Load failures are not crashes. If clangd exits before its handshake and its stderr matches the
   loader's wording (`error while loading shared libraries`, `` version `GLIBC``,
   `not found (required by`), do not retry. Raise one issue, `engine-incompatible`: "the bundled
   clangd cannot run on this system: *first stderr line*". Its action is Show Logs, the status is
   failed, and the message links the supported-systems list in `docs/00-install.md`. Restarting
   cannot fix a missing glibc.
3. Conformance: a stand-in clangd that exits 1 at start. The test expects:
   - `initialize` answered within a few seconds;
   - definition on an `import` working;
   - the status carrying the issue;
   - no restart loop.

## 3. S: being found by "mcppls"

Measured against the Marketplace search API (`extensionquery`, 2026-09-24):

| Query | Result |
|---|---|
| `mcppls` | **0 results** |
| `mcpp` | found, 2nd (after mcpp-community.mcpp-vscode) |
| `mcpp-language-server` | found, 1st |

Search matches whole words in name, display name, description and keywords, and "mcppls" was in

users could not find it under any name (§4 fixes that).

**Done locally** (`editors/vscode/package.json`):
- Keywords: added `mcppls`, `mcpp-language-server`, `c++ modules`, `cpp modules`, `cxx modules`,

- Description: now ends with " (mcppls)".

Both take effect with the next upload to each store. The Zed `extension.toml` and CLion `plugin.xml`
descriptions get the same word when those plugins are published to their stores (not in 0.0.3).

## 4. P: publishing

**Decision:**
- **Open VSX:** published by CI.
- **VS Code Marketplace:** unchanged. The maintainer verifies the VSIX locally, then uploads it
  (`docs/92-release.md`, *The VS Code Marketplace*).

**Order: one verification gate for both stores.** Open VSX must not receive a version before the
local verification that decides the Marketplace. `release.yml` already creates the GitHub release
as a **draft** by default, so the sequence is:
1. `release.yml` stages and tests the candidate, then creates a draft release.
2. The maintainer verifies the draft's `mcppls-<platform>.vsix` locally.
3. The maintainer publishes the draft. That triggers the Open VSX workflow.
4. The maintainer uploads the same VSIX files to the Marketplace.

A release made with `draft=false` skips step 2 on purpose, and Open VSX follows it at once.

**Workflow `publish-openvsx.yml`.**
- Triggers:
  - `release: published`, which fires when a draft is published in the UI;
  - `workflow_call` from `release.yml` when it runs with `draft=false`, because a release created
    with `GITHUB_TOKEN` triggers no other workflow;
  - `workflow_dispatch` with a tag, for a retry.
- Steps:
  1. `gh release download <tag> -p 'mcppls-*.vsix' -p SHA256SUMS`, then `sha256sum -c --ignore-missing` (the sums
     cover every release file; only the VSIX files are downloaded).
  2. For each VSIX, `npx ovsx publish --packagePath <file> --skip-duplicate`, with the repository
     secret `OVSX_PAT` (set 2026-09-23). Each VSIX carries its target (`vsce package --target`), so
     Open VSX serves each platform its own file, and linux-arm64 joins once §5 produces it.
     `--skip-duplicate` makes a retry a no-op.
- A GitHub pre-release is published to Open VSX as an ordinary version. No pre-release channel.

**Blocker: the Open VSX namespace does not exist yet.**
`https://open-vsx.org/api/sunrisepeak` answers "Namespace not found: sunrisepeak" (checked
2026-09-24). Run once, locally, with the same token as `OVSX_PAT`:
`npx ovsx create-namespace sunrisepeak -p <token>`. The namespace must equal `publisher` in
`package.json`. Claiming ownership, for the verified badge, is optional.

**Also changes.**
- The comment at the top of `release.yml`.
- `docs/92-release.md`: the four-step order above, and Open VSX leaves "Not here yet".
- README's install table: Open VSX, for VS Code-compatible editors.

## 5. A: Linux arm64

**Why.** VS Code's Remote-SSH, Dev Containers and WSL install a `workspace` extension where the
code is, and that is increasingly an arm64 machine (Graviton, Ampere, Kunpeng, Raspberry Pi 5,
Asahi). Zed, Neovim and CLion only need a `payload-linux-arm64.tar.gz` on `PATH`; their plugins need
no change.

### 5.1 The server: done by the toolchain

`mcpp build --profile release --target aarch64-linux-musl` on the x64 host finished in 18 s. It
produced a static, stripped aarch64 ELF of 3.6 MB, which answers `--version` with `0.0.2` under
`qemu-aarch64`. openkal-musl already carries aarch64. `aarch64-linux-gnu` is refused by mcpp
("registered but not yet supported (planned)"). That does not matter: the server is static either
way, so it adds no glibc requirement.

### 5.2 clangd: the official LLVM build

**Decision:** use the official LLVM arm64 clangd; do not build it.
- clangd/clangd publishes no Linux arm64 build.
- LLVM's release does: `LLVM-23.1.0-Linux-ARM64.tar.xz`, 1.83 GB, with `bin/clangd` from the same
  commit (`ea7d852`) as the x64 clangd we ship.

| | linux-x64 today (clangd/clangd) | linux-arm64 (official LLVM) |
|---|---|---|
| glibc floor | 2.18 | **2.34** |
| libstdc++ | static | **system's, needs GLIBCXX_3.4.30 (GCC 12)** |
| zlib | not needed | `libz.so.1` (part of a minimal install; the package managers depend on it) |
| Size, stripped | 62 MB | 56 MB |
| Features | `linux+grpc` | `linux`; grpc is only the remote index, which mcppls never uses (it passes only standard flags) |

**Where it runs.** Each row loads the official arm64 clangd with that distribution's own glibc,
libstdc++ and zlib packages, through `qemu-aarch64 -L`
([`arm64-clangd-distros.sh`](assets/2026-09-24-0.0.3/arm64-clangd-distros.sh)):

| Distribution | glibc / newest GLIBCXX | Runs |
|---|---|---|
| Ubuntu 22.04, 24.04 | 2.35 / 3.4.30, 2.39 / 3.4.33 | ✓ |
| Debian 12 | 2.36 / 3.4.30 | ✓ |
| openEuler 24.03 LTS | 2.38 / 3.4.30 | ✓ |
| Ubuntu 20.04, Debian 11 | 2.31 / 3.4.28 | ✗ `GLIBCXX_3.4.29` not found |
| Rocky/RHEL 8 | 2.28 / 3.4.25 | ✗ `GLIBC_2.29` not found |
| Rocky/RHEL 9 | 2.34 / 3.4.29 | ✗ `GLIBCXX_3.4.30` not found |
| openEuler 22.03 LTS SP4 | 2.34 / 3.4.28 | ✗ `GLIBCXX_3.4.29` not found |

Not run, inferred from package versions: Amazon Linux 2023 (glibc 2.34, GCC 11) ✗; Kylin V10
(glibc 2.28) ✗; Alpine ✗, as for x64.

**What users get, accepted with this decision.**
- On a ✓ system, nothing differs from x64: same clangd, same flags, same features.
- On a ✗ system, after B1: the module-level features (module navigation, import completion, module
  diagnostics), plus a status saying the bundled clangd cannot run here and linking the supported
  list.
- `docs/00-install.md` states the list: arm64 needs glibc ≥ 2.34 and a GCC 12 libstdc++, i.e.
  Ubuntu 22.04+, Debian 12+ and openEuler 24.03+ (tested); Fedora 36+ (by package versions).
- If ✗ systems turn out to matter, the way out is a CMake build (manylinux_2_28 container, static
  libstdc++, glibc 2.28 floor; recipe as clangd/clangd's `autobuild.yaml`). It enters the payload
  through the same lock entry, so nothing downstream changes.

**How it enters the payload.** No repackaging and no hosting of our own. A lock entry
`clangd-linux-arm64` points at LLVM's own release asset (URL, size, sha256), and the platform row
`linux-arm64` names it. What already works, and what has to change:
- `modules/pack/src/archive` already reads `tar.xz`.
- The trim step needs one top-level directory and `lib/clang/<major>/include`, both of which the
  official tarball has. It takes only `bin/clangd` and the builtin headers.
- **Strip:** `strip_linux` runs only for `linux-x64` (`modules/pack/src/clangd.cpp:175`). It must
  run for every Linux platform. `llvm-strip`, which it prefers, handles aarch64 on any host.
- **License:** the payload requires `LICENSE.TXT` at the archive root
  (`modules/pack/src/payload.cpp:262-266`), and **the official tarball has none**: its only license
  file is `include/llvm/Support/LICENSE.TXT`, a third-party notice (listed 2026-09-24). So the lock
  entry names where its license comes from, `llvm-project-src`'s `llvm/LICENSE.TXT`. The kit build
  already reads that archive for the same license (`modules/pack/src/kit.cpp:411`).
- **Download size:** 1.83 GB, once per lock hash. The payload job already caches its inputs under
  `payload-inputs-<platform>-<lock hash>`. The trim step decompresses the archive twice (list, then
  extract), about a minute each.

### 5.3 Pipeline changes

- The cross-build matrix gains `aarch64-linux-musl`, building the server, the conformance runner,
  the mocks and `mcppls-devtools` for arm64. The darwin payload already works this way: build on
  Linux, assemble on the target.
- The payload matrix gains `linux-arm64` on `ubuntu-24.04-arm`, a free runner for this public
  repository.
  - It assembles with the cross-built `mcppls-devtools`, so mcpp is not needed on an arm64 host.
    Whether mcpp's own toolchain runs there is untested.
  - The kit is built natively, so its C headers come from the runner's `libc6-dev`.
- The conformance matrix gains `linux-arm64` on `ubuntu-24.04-arm`. Ubuntu 24.04 is a ✓ system.
- VSIX: `vsce package --target linux-arm64`. `release.manifest.json` platforms gain `linux-arm64`.

## 6. X: one platform table

The set of platforms is written out in eight places, and the host's platform is decided per OS
with no regard to architecture:

| Where | What |
|---|---|
| `modules/pack/src/payload.cppm:25`, `modules/pack/src/kit.cppm:39`, `modules/pack/src/clangd.cpp:128` | three copies of `{"linux-x64","win32-x64","darwin-arm64"}` |
| `editors/vscode/src/payload.ts:41` | a fourth, `SUPPORTED_PLATFORMS` |
| `modules/os/{linux,macos,windows}/src/os.cppm:16` | `VSCODE_TARGET`: one fixed platform per OS, so an arm64 Linux server would call itself `linux-x64` |
| `tools/devtools/src/common.cpp:121` (`host_triple`), `tools/devtools/src/packaging.cpp:30` (`triple_for_platform`), `tools/devtools/src/release.cpp:28` | platform → triple → xlings names, three more times |
| `packaging/payload.lock.json`, `packaging/release.manifest.json`, `.github/workflows/*.yml` | the data and the matrices |

**Design.**
- The platform rows of `payload.lock.json` become the one table. Each row has `os`, `arch`,
  `server-target` (the mcpp triple), `clangd` (a lock entry), `kit`, and `runner`.
- `modules/pack` gets one C++ table and `host_platform()`, computed from `os::FAMILY` and the
  architecture the server was compiled for. That replaces the three `PLATFORMS` arrays,
  `VSCODE_TARGET`, `host_triple` and `triple_for_platform`.
- What cannot read the lock is **checked** against it by `mcppls-devtools check`, the same way
  `version --check` keeps versions in step: TypeScript's `SUPPORTED_PLATFORMS`,
  `release.manifest.json`, and the CI matrices. A platform missing anywhere fails CI.

Adding darwin-x64 or win32-arm64 later is then one lock row plus the CI rows the check asks for.
Neither is in 0.0.3.

## 7. H: syntax highlighting (status), `.mcpp` (deferred)

**Syntax highlighting needs nothing from us, and nothing from the user.**
- **Basic coloring** comes from the editor's C++ grammar. VS Code maps
  `.cppm .ixx .mpp .cxxm .ccm` to `cpp`, and the Neovim plugin adds the same extensions.
- **Semantic highlighting** comes from clangd through mcppls. Measured over LSP:
  `semanticTokensProvider` (full + delta) is advertised, and tokens arrive across modules; in
  `main.cpp`, `Greeter`, imported from `hello`, is `class`. VS Code turns semantic highlighting on
  per theme; Dark+ and Light+ have it on.

Two gaps, neither needed for 0.0.3:
- No test covers semantic tokens. One conformance case would do.
- While a module is not yet built, or fails to build, the answer is `null`, and only the grammar's
  colors show.

**`.mcpp` (deferred).** A `.mcpp` file is mcpp's build program, `build.mcpp`, and it starts with
`import mcpp;`. Mapping it to `cpp` today puts ``module 'mcpp' not found`` on line 1 of every one
(measured with `mcppls check`). The `mcpp` module is bundled in the mcpp binary and written to
`target/.build-mcpp/mcpp.cppm` only when a build runs. There are two options:
- **(a)** Coloring only: a `mcpp` language using the C++ grammar, with the server not attached.
- **(b)** Real support: the server treats `build.mcpp` as a host-toolchain unit and finds `mcpp`
  under `target/.build-mcpp/`. Best done after mcpp's build database describes the build program
  itself.

**Self-review after review 1.** What changed in this plan, and why:
1. **Publishing order.** Automatic Open VSX plus a manual Marketplace could put a version on
   Open VSX that local verification later rejects. Fixed by tying Open VSX to *publishing the
   draft*, after verification (§4). No new mechanism; `release.yml` already drafts by default.
2. **Open VSX namespace missing.** `OVSX_PAT` is set, but the `sunrisepeak` namespace does not
   exist, so the first publish would fail. Added as a blocker with its one command (§4).
3. **The official clangd needs no hosting.** The first draft proposed repackaging it into a zip and
   hosting it in a release of this repository. The payload's archive reader already takes `tar.xz`
   and the trim step already fits the official layout, so the lock points at LLVM's asset directly:
   one less artifact to maintain, and provenance straight from LLVM (§5.2).
4. **Two code gaps the first draft missed:** stripping is x64-only, and the payload requires a
   `LICENSE.TXT` the official tarball does not have; it comes from the LLVM source entry instead (§5.2).
5. **B1 becomes more urgent** with the official build. It is how every ✗ system in §5.2 will look
   without the fix, so it stays step 1, and its message links the supported list.
6. **"No difference" is true only on supported systems.** Stated as the accepted scope rather than
   left implicit (§5.2, *What users get*).
7. **CLion icon:** the chosen SVG embeds a raster. Whether the IDE's renderer shows it is not known,
   so it is an acceptance check with a fallback, not an assumption (§2).
