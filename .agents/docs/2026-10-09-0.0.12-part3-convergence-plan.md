## 2. Part 3 的原则

1. **内容冻结。** 除 Windows/ARM macOS 原生失败的根因修复、本文 §4 列出的代码项外，不再加入性能优化补丁。31.74ms warm 差距转为 0.0.13 输入（§6）。
2. **先整理，后资格。** 补丁合并、仓库历史整理、evidence 外移都会改变或重排已测身份；必须在最终资格运行**之前**完成，最终资格只跑一次。整理后若 tree 不同，旧证据只作开发参考。
3. **合入资格（M1）与发布资格（M2）分开**，各自门槛在本文登记，不临时迁移。
4. **证据是摘要 + 可校验指针，不是仓库里的原始数据。**
5. 测试投入预算沿用：不超过实现时间的三分之一；超出时报告并调整批次，不降门槛。

## 3. 工作分解与顺序

### P3-A：跨平台 save-plan 失败（阻断，先做）

现象：macOS/Windows 的 `test_save_plan.cpp:171/188/202/214` 失败，Linux 通过；第 3 例在**保存前**的草稿重规划阶段就失败（:188），说明不只是 `880cc4b` 新增的 `saved_structure_is_planned` 判定。

首要假设（未证实）：URI 派生路径与 model/plan 路径的身份不一致——macOS 临时目录 `/var` ↔ `/private/var` 符号链接，Windows 盘符/分隔符形态；`path_key` 不解析别名。

1. 本地 Linux 用符号链接根目录复现；若复现，即为产品级缺陷（用户工程在符号链接路径下同样受影响），不是测试问题。
2. 在 workspace 对 `editedAt`、`structures`、`plan.entries` 统一使用同一规范化身份；保留原拼写用于显示与引擎消息。
3. 新增 Linux 符号链接根与大小写路径控制，使 Linux CI 能抓住此类回归。
4. 若假设不成立，以 macOS/Windows 原生日志定位，不放宽断言或延长 tick 掩盖。

出口：三平台 unit 全绿，`880cc4b` 的 UP20 正确性回放保持通过。

### P3-B：仓库与证据整理（阻断合入）

证据策略：
- 仓库只保留：每项证据的 `manifest.json`（命令、身份 SHA、输入 SHA、结论、样本数、p50/p95、失败计数）与人可读摘要，单项建议 ≤64KiB。
- 原始报告、日志、trace、复制的头文件/资源目录、压缩 report 移到**专用 GitHub release（如 `evidence-0.0.12`）资产**或 Actions artifact（注意 artifact 有保留期，最终证据用 release 资产）；manifest 记录 URL 与 SHA-256。
- 路径统一改写为 `${WORKSPACE}`/`${LLVM_SRC}`/`${TMP}` 占位；`ci/check_ledger.py` 或 devtools 增加检查：拒绝 `/home/`、`/Users/`、`C:\Users\`、单文件 >1MiB、`.pcm/.pch/.o`。
- `.gitignore` 从仅 `*.pcm` 扩展到 `*.pch`、`*.pcm.gz`、构建目录产物与 resource 复制目录。

合入策略（需用户决定，见 §7-2）：
- 推荐：合入前从当前 tree 生成**整理分支**（代码/测试/摘要 + 主题提交），以普通 merge 或 squash 合入；原 PR 分支保留为历史档案，不进入 main。main 的克隆体积不受 PR 历史影响。
- 产品 #46 提交整理为主题：客户端崩溃/写入所有权、engine identity + payload v4、格式化 fallback、后台索引优先级、save-plan、模型初始化期限、CI/平台范围、文档。去掉先加后撤的 Intel 提交。
- `.agents/docs`：Part 2 状态文档（日志体）压缩为结论 + 指针；联合方案/maintained 方案/Part 2/Part 3 标明当前有效与已被取代。

### P3-C：补丁系列定稿（阻断发布，建议阻断合入）

1. 按主题合并 74 补丁为约 15–20 个可审阅补丁（例：模块扫描 memo/验证、DAG 调度与 worker 监管、缓存 lease/admission、preamble 策略、completion 选择性加载、directive 恢复/诊断、Windows crash dump、格式 preset、const-correctness、backport）。每个补丁自带测试，台账一行一补丁。
2. 定义 `stabilizing → steady`：该补丁所在最终字节通过三平台 build+unit、所属 e2e 与 canary、无未解决的已知负例、drop condition 可检验。M2 前所有随发布补丁必须是 steady；5 个 draft 要么升级、要么移出 series。
3. 合并后 series digest 改变：从固定 tarball 干净应用、Ubuntu20 构建、consumer 测试——这一步就是最终字节的起点（P3-E）。
4. 修复 `PATCHES.md` 表格格式与无编号文件名。

### P3-E：最终字节与产品集成（合入资格的核心）

1. 以 P3-C 定稿 series 生成**同源三平台引擎包**（linux-x64 Ubuntu20 下限、win32-x64、darwin-arm64），记录 source/series/binary/resource SHA。
2. **产品 lock 切换到该引擎**（独立提交），产品 CI 首次在三平台跑 maintained 引擎；不再以 stock CI 代表最终结果。
3. Linux 最终字节复跑：12 语境 3×30、选定 GCC 插入、stock/candidate 对照、资源审计（一次，不重复挑选）。
4. Windows：module-faults 原生稳定性根因、UP12 crash corpus 重放、UP13 补齐真实输入；文件身份/共享模式/rename/lease/取消。
5. ARM macOS：toolchain/SDK/VFS/生命周期、语义与延迟分布（同 Linux 语境集，可缩为 3×10，见 §7-4）。
6. 产品闭环：VS Code 真实编辑（typing/import/autosave/保存新 export/导航）、inferred/C7、UP20，raw 与产品缓存分开报告；真实缓存命中时序。

### P3-F：发布长期验证（M2）

1000 次真实保存（内存/生命周期/缓存物理增长）、全局物理缓存预算、完整 Ubuntu20 产品安装、7 次合格 nightly（日历上 ≥7 天，从 P3-E 字节冻结起算）、每平台 ≥2h RC soak。任何代码改动使已完成的 nightly 计数归零，因此 M2 期间只接受阻断级修复。

## 5. 风险

- 补丁合并可能引入应用顺序/冲突错误：以"合并前后最终 tree 字节一致"为硬检查，tree 一致则语义不变，只需重做构建身份与 CI。
- 历史整理会让 PR 讨论中的提交链接失效：原分支保留为档案并在新 PR 描述中链接。
- Windows module-faults 与 crash corpus 是最可能拖长周期的项；如超出预算，按 §2-5 报告，不调大期限掩盖。
- 7 nightly + soak 是日历约束，不能通过并行压缩。

## 6. 移交 0.0.13 的输入

warm 31.74ms 差距的已知方向（来自 Part 2 trace，未实施）：推导指引 GetDecl 线程 CPU 约 28–33ms、operator 名称加载、documentation lookup、构造函数多重性；manifest 622 路径重复 open（约 7.5ms）；PCH 辅助 canonical 扫描为性能负例，保持不导出。

                                                                                              ↓ (URL/size/sha256)

版本后缀保持 `-mcppls.0`：`LLVM_VERSION_SUFFIX` 进入 `llvm-config.h`，修改会使四平台几乎全量冷编译；引擎身份由 fork commit、series digest 与二进制 SHA 决定。下一次随产品发布的引擎变更须递增后缀，避免不同引擎以同一版本串接受彼此的 BMI。
