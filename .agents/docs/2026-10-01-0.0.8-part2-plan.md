## 0. 摘要

### 0.1 结论

1. **"越改越慢、慢到补全不出来"的主因是 mcppls 自己在 clangd 里开着一批 prime unit（代码确认 + 已验证）。**
   模块准备时，已经准备完的 prime unit **不关**，要等整个准备空闲才一起关（`finish_prime_` → `heldPrimeUnits_`）。GalTranslPP 上一次关 15 个，
   ux-xlings 上一次关 70 个。clangd 每收到一次 `didSave` 就把**所有**打开的文件重检一遍，导入了刚改过模块的文件还要完整重建一遍（E2 实测）。
   所以用户每保存一次（autosave 下就是每停顿一次），clangd 就要替这批用户看不见的文件重建一轮，和用户正在编辑的文件抢 `-j` 个工作槽。
   clangd 23 的 BMI 本来就落在磁盘缓存里（E3），开着这些文件并不能保住 BMI。
2. **"完全不出来"是因为迟到的答案被丢掉了（代码确认）。**
   补全 1 s 没等到 clangd，mcppls 就拿文件里的词回答，并**取消** clangd 那边的请求（`answer_without_core`）。下一次按键再问 clangd，又排在同一轮重建后面，
   于是每次都超时，语义补全一次也出不来。GalTranslPP 这次 48 次补全里只有 21 次是 clangd 答的，p50 正好是预算 1001 ms。
3. **原先怀疑的"GMF 不进 preamble"不成立（已验证，E1）**：clangd 23 在 `module;` 之后的 `#include` 同样进 preamble（12.2 MB，与普通 cpp 一样大）。
4. **xmake "配置了也不生效"（已观察 + 代码确认）**：
   - 项目根目录下有一份 `compile_commands.json` 时，mcppls **原样读它、不再运行 xmake**（`XmakeProvider::existing`）。
     这份文件比 xmake.lua 旧：用户加了 `set_languages` 之后连续保存 5 次，模型都是"unchanged"；
   - 等文件被重新生成时，mcppls 恰好读到写了一半的内容，报了 `compdb-invalid` 警告；
   - xmake.lua 没写标准时，clang 按自己的默认 gnu++17 读 gcc 16 的 `std.cc`，编不过（E4：20 个错误）；gcc 16 自己的默认是 gnu++20，构建本身没问题；
   - `std.cc` 扫描失败被当成"用户正在打字"忽略掉，准备一直卡在 0/1。重启后 47 ms 又被旧时钟判成 preparation-stalled，
     弹出"无法自行恢复，请报告"并写了自动包（这一条主方案 M-3 已修）。
5. **include cleaner 不建议默认禁用（已验证，E6）**：module 接口、实现单元、导入方三种写法下只报真正没用到的头文件，没有误报；开销是毫秒级；
   GalTranslPP 的崩溃栈里没有它。clangd 也没有命令行开关能关它，只能改用户自己的 clangd 配置，这本身就是副作用。
6. **Zed / CLion 目前没有任何"在真实 IDE 里能用"的测试（代码确认）**：CI 只验证构建、打包、用 devtools 放置文件、卸载干净，以及服务端能回应项目。
   CLion 插件还编译在 2025.2 上，文档写着"尚未在运行中的 CLion 里跑过"。两边都有自带的 C++ 引擎和 mcppls 同时回答同一个文件的问题。
7. **主方案遗留：U16 / U7a 在 4 核上超预算（已观察）。** PR CI 上 ux-mcpp 的 U16 engine share 0.36 < 0.40，U7a 导入方诊断 31 s > 20 s；
   本机 4 核的 ux-xlings 上 U16 p95 1.14 s，另有 1 次重启、2 次超时，U7a p95 1.67 s。U15-edits 的 prepared 长达 917 s，
   也就是整段编辑期间 prime unit 一直开着，和结论 1 是同一个机制（推断，C-1 的门槛里验证）。

### 0.2 做什么（一句话一项）

| 编号 | 做什么 | 解决 |
|---|---|---|
| C-1 | prime unit 一准备完就关，不再攒到准备空闲 | 保存引发的重建风暴；U16 / U7a |
| C-2 | 预算到期不取消 clangd 的补全，迟到的答案留给同一个词的下一次请求 | 慢文件里补全"永远不出来" |
| C-3 | （有条件）用户在打字时 primer 不开新的 prime unit | C-1 之后仍超预算时再做 |
| C-4 | 诊断包带上每个文件的 clangd 构建耗时和每个文件的请求统计 | 下一次能直接看出"哪个文件慢、慢在哪" |
| X-1 | xmake 项目以 xmake 为准：能运行 xmake 就私有地运行它，项目里的 `compile_commands.json` 只在 xmake 跑不了时读 | 改了 xmake.lua 不生效 |
| X-2 | 私有运行沿用用户自己 `xmake f` 的平台、架构、模式、工具链 | 自动识别，和用户构建一致 |
| X-3 | 编译命令没写 `-std` 时按构建编译器自己的默认补上（gcc ≥ 16 → gnu++20） | `import std` 在 gcc 16 项目里编不过 |
| X-4 | 标准库单元（和工作区外的单元）扫描失败算项目问题，报一次原因，不算"卡住" | 误报 preparation-stalled |
| X-5 | 刚改过、还不是合法 JSON 的 `compile_commands.json` 等它写完再读，不报警 | 读到写了一半的文件 |
| X-6 | 临时模型（扫描源码）不再说"工作区未信任" | 启动时的误导信息 |
| I-1 | include cleaner 保持 clangd 默认；文档写怎么关；加一个守护检查 | 回答用户的问题，防 clangd 升级回退 |
| CL-1 | CLion 插件编译到 2026.2.3，Gradle 插件升到 2.19.0，sinceBuild 保持 252 | 新版本可用 |
| CL-2 | CI 用 Plugin Verifier 对 2025.2 与 2026.2.3 两个版本检查插件 | API 不兼容在 CI 里暴露 |
| CL-3 | CI 在真实 CLion 2026.2.3 里 headless 加载插件，打开模块文件，断言 mcppls 起来并答出诊断和补全 | "基本可用"有测试 |
| CL-4 | 与 CLion 自带引擎的冲突：默认"一个文件只由一个引擎回答"，加一个开关 | 两份补全、两份诊断 |
| Z-1 | Zed 扩展的查找逻辑抽成纯函数，`cargo test` 覆盖 | 回归 |
| Z-2 | CI 在真实 Zed（xvfb + lavapipe）里装扩展、打开模块文件，断言 mcppls 起来并发出诊断 | "基本可用"有测试 |
| Z-3 | 与 Zed 自带 clangd 的冲突：冒烟测试覆盖推荐设置与默认设置两种情况，文档写清楚 | 两个 C++ 服务器 |

### 0.3 需要你定的（§5 详述，括号里是建议）

- Q1 xmake 数据来源：以私有运行 xmake 为准（建议），还是较新的用户 `compile_commands.json` 优先；
- Q2 CLion 默认：mcppls 只服务 CLion 没有建模的项目，另给开关（建议），还是所有 C/C++ 文件都由 mcppls 服务；
- Q3 真 IDE 冒烟（CL-3、Z-2）在什么时候跑：改动相关路径的 PR、`release/*`、nightly、release-checks（建议），还是每个 PR；
- Q4 include cleaner：不默认禁用（建议）；
- Q5 C-3：先不做，C-1 之后 U16 / U7a 仍超预算再做（建议）。

- 慢请求里的"error"大多是 clangd 因文档被修改而放弃的旧请求（推断：同一时刻的同类请求成批出现）。编辑器会重发，用户基本看不到；
- 看得到的是补全：一半落在 1 s 预算上，拿到的是文件里的词；
- definition 13/15 失败，0.0.7 的包里没有足够信息判断原因，留给 C-4。

**E1：GMF 是否进 preamble（已验证，排除）。** 同样 6 个标准头：放在 `module;` 之后的接口单元 preamble 12,242,824 字节 / 1.12 s，
普通 cpp 12,244,028 字节 / 1.42 s。clangd 23 的 preamble 包含 GMF 里的 include，这条假设排除。

**E2：didSave 让 clangd 重建所有打开的文件（已验证）。** 打开 `n.cppm`（模块）、`n_impl.cpp`（实现单元）、`n_user.cpp`（导入方）、
`plain.cpp`（无关文件）。改 `n.cppm` 并发 `didChange` + `didSave` 后 90 ms 内：

- `n_user.cpp`、`n_impl.cpp` 重建 preamble 和前置模块（"Built prerequisite modules"），再重建 AST 并重新发布诊断；
- `plain.cpp` 也重建了一次 AST（"ASTWorker building file plain.cpp"）。

clangd 的补全在 preamble 上跑，但和这些构建共用 `-j` 个并发槽（机制来自 clangd TUScheduler，实现时对照 23.1 源码复核）。
所以保存引发的重建越多，补全排队越久。

**E3：clangd 23 的 BMI 落在磁盘（已验证）。** clangd 进程退出后，`.cache/clangd/modules/n.cppm-<hash>/<hash>/n.pcm` 仍在。
mcppls 启动时清理的 "module locks" 与 "freed … BMIs built for commands no unit has any more" 也说明同一件事。

**代码确认：prime unit 一直开到准备空闲。** `finish_prime_` 把准备完的单元放进 `heldPrimeUnits_`；
`release_prime_units_if_idle_` 只在 `primer_` 不忙、没有等诊断的文件、没有被扣住的请求时才一次性关掉。代码注释给的理由是
"等数据库的文件交给 clangd 时需要同样的模块"，而 E3 说明模块在磁盘上，关掉并不会丢。原始提交已被 squash，没有更多记录。

**代码确认：预算到期取消 clangd 的补全。** `answer_without_core` 先用文件里的词回答，然后 `engine->cancel(clientId)`；
回退列表是 `isIncomplete: true`（`without_engine`），编辑器下一次按键会再问。

### 1.2 xmake：配置了也不生效、报了不该报的错

时间线（UTC，`auto-preparation-stalled-20260930T175130Z` 与 `mcppls-bundle-20260930T180310.063Z` 合看）：

| 时间 | 发生了什么 | 说明 |
|---|---|---|

| 17:50:23–17:50:43 | `std.cc` 扫描失败 3 次："invalid suffix on literal…" | 命令里没有 `-std`，clang 按 gnu++17 读 |

| 17:56:15 | 用户删掉根目录的文件、重载窗口 | mcppls 运行 xmake，一切正常（std 1/1，ready） |

**E4：没写标准时 `std.cc` 为什么编不过（已验证）。** mcpp 的 clang 23.1.0 + gcc 16.1.0 的 libstdc++，预编译 `bits/std.cc`：

| 标准 | 错误数 |
|---|---|
| 不写（clang 默认 gnu++17） | 20 |
| `-std=gnu++20` | 0 |
| `-std=c++20` | 0 |
| `-std=c++23` | 0 |

`g++ -dM -E` 显示 gcc 16.1.0 的默认是 `__cplusplus 202002L`（gnu++20）。xmake.lua 不写 `set_languages` 时，xmake 给出的命令里没有 `-std`：
构建用 gcc 16 能编，mcppls 用 clang 读就编不过。这是 mcppls 读命令的方式与构建编译器不一致，不是用户的配置错。

**代码确认：标准库单元的扫描失败被忽略。** `note_scan_failure_` 只把命令被拒（driver）和找不到文件当问题。其余语法错误按"文件正在被编辑，
扫描失败是常事"处理，只记事件。可标准库单元永远不是用户在编辑的文件。于是准备卡在 0/1，状态上看不到原因。

**代码确认：统一标准只看写了标准的单元。** `unify_language_standard` 在所有模块单元都没写 `-std` 时直接返回，不补标准。

**E5：私有运行能否沿用用户的 `xmake f`（已验证）。** 在项目副本里先 `xmake f -m debug`（用户的配置在 `.xmake/linux/x86_64/xmake.conf`）：

| 私有运行的做法 | 结果 |
|---|---|
| 现在的做法：`xmake f -c` | release：`-O3 -DNDEBUG` |
| 把项目 `.xmake/` 复制进私有 `XMAKE_CONFIGDIR/.xmake/` 后 `xmake f --builddir=…` | 仍是 release：`xmake f` 把没给的选项重置了 |
| 从用户的 xmake.conf 读出 `plat`/`arch`/`mode`，显式 `xmake f -c -p linux -a x86_64 -m debug …` | debug：`-g -O0`，与用户构建一致 |
| 任一做法之后，项目目录里比时间戳新的文件 | 无 |
| 给 `xmake f` 一个它不认识的选项 | 退出码 255 |

### 1.3 include cleaner（用户的问题：module 场景要不要默认禁用）

**E6（已验证）。** 用 clangd 23.1.0 的 LSP 会话（`--experimental-modules-support`，`.clangd` 里切换 `UnusedIncludes`）：

| 文件 | 写法 | Strict 下报的 | 对不对 |
|---|---|---|---|
| `m.cppm` | GMF 里 6 个标准头，`export using std::string` 等 | `<regex>`、`<format>` 未使用 | 对（确实没用到；using 声明算作使用） |
| `plain.cpp` | 同样内容，普通 cpp | 同上 | 对 |
| `user.cpp` | include + `import m;` | 无 | 对 |
| `n_impl.cpp` | 实现单元，GMF 与接口单元 include 同一第三方头，用宏和函数 | 无 | 对 |
| `n_user.cpp` | include 第三方头 + `import n;`，只访问模块返回对象的成员 | 无 | 对（成员访问算作使用） |

- 开销：Strict 与 None 首次诊断时间相差在几十毫秒以内（0.74 s 对 0.67 s），属于噪声量级；
- 稳定性：GalTranslPP 探针的崩溃栈里没有 include cleaner，它只打过一行找不到 `toml.hpp` 的日志；
- 能不能关：clangd 23 没有命令行开关（`--include-cleaner-stdlib` 已作废），只能靠用户或项目的 clangd 配置（`.clangd`、`config.yaml`）。
  mcppls 要替用户关，只能改写或遮住用户自己的配置，这本身就是副作用。

### 1.4 Zed / CLion 覆盖现状

- **CI**：release-checks 的 "zed and clion plugins" 构建两个插件并打包；每个平台用 devtools 安装（放文件、链接）、验证文件存在、
  验证服务端能回应项目、卸载干净。没有一步在真实 IDE 里加载插件；
- **CLion**：
  - `platformVersion = 2025.2`、`sinceBuild = 252`、IntelliJ Platform Gradle Plugin 2.2.1；

## 2. 设计：大项目补全（C-\*）

### C-1 prime unit 用完即关

- **做法**：`finish_prime_` 收到 prime unit 的诊断（或到期）后立即 `didClose`，不再进 `heldPrimeUnits_`。
  `release_prime_units_if_idle_` 与 `heldPrimeUnits_` 一并删掉；`close_prime_units_` 只剩关闭还在准备中的单元（重启、换数据库时用）；
- **为什么安全**：
  - BMI 在 clangd 的磁盘缓存里（E3），关掉 prime unit 不会让下一个文件从头构建；
  - 等数据库的文件交给 clangd 时，clangd 按需验证并复用缓存里的 BMI；
- **效果预期**：保存时要重建的只剩用户自己打开的文件。GalTranslPP 那一轮少 15 个，ux-xlings 少到 70 个；
- **门槛**：
  - ux-mcpp、ux-xlings 在 4 核上：U1 首次 ready、U15-cold prepared 不比现在差 10% 以上；
  - U16、U7a 回到预算内；
  - 新增 conformance 检查：准备期间保存一次模块源文件，断言 clangd 只重建用户打开的文件（从 clangd 日志数 "ASTWorker building file"）；
- **回退**：冷启动若变慢超过门槛，改为只保留"还有未准备的导入者需要它"的 prime unit，其余立即关。

### C-2 迟到的补全答案不浪费

- **做法**：
  - 预算到期时，mcppls 照旧先用文件里的词回答（`isIncomplete: true`），但**不取消** clangd 的请求，给它 10 s（`LATE_COMPLETION_KEEP`）；
  - clangd 的答案到了就存下，键是（文档，行号，当前词的起始列，该行在词前的文本）；
  - 同一个词的下一次补全请求（编辑器因 `isIncomplete` 会再问）若键相同，直接回这份答案，同时照常再问 clangd；
  - 只存一份（每个文档最新的一份）；文档在词前的内容一变就作废；
- **不改**：成员访问（`.`、`->`、`::`）之后文件里的词本来就是空的，仍回空的 `isIncomplete: true` 列表，让编辑器再问；那一次命中缓存就能出列表；
- **效果**：clangd 只要在用户打完一个词之前答上一次，列表就会出现，而不是永远拿词表；
- **测试**：
  - 单元测试：键的构造与作废（词前文本变、换行、换文档）；
  - conformance 的 typing 类型加一个"clangd 慢"的前置步骤（给 clangd 一个大文件把槽占满，或加一个延迟答复的测试开关），
    断言"一个词之内出现过 clangd 的列表"的比例 ≥ 90%；
  - ux 的 engineShare 预期上升。

### C-3（有条件）打字时 primer 让路

- 只在 C-1、C-2 之后 U16 / U7a 仍超预算时做：任一文档 2 s 内有过 `didChange` 时，`pump_primer_` 不开新的 prime unit，最多推迟 10 s；
- 已经在准备的不打断；推迟计入 M-3 的进度时钟，不会被误判成 stalled。

### C-4 诊断包说清"哪个文件慢、慢在哪"

- **clangd 构建耗时**：
  - 引擎的日志环（4000 行，现在只在事故里整份附成 `clangd.log`）里，挑出 "Built preamble of size … in X seconds"、"Built prerequisite modules for file … in X seconds"、
    "ASTWorker building file …"，按文件汇总成次数、p50、最慢；
  - 写进诊断包的 `engines[].details.buildTimes`，路径照常脱敏；
- **按文件的请求统计**：`requests` 之外加 `slowestFiles`，列 p95 最高的 10 个文件及其各方法的 p95，还有回退次数；
- 不改日志级别，不多写日志文件；
- **测试**：diagnostic-bundle fixture 断言这两个字段存在且结构正确。

## 3. 设计：xmake（X-\*）

原则（对应"自动识别、无感切换、不能有副作用"）：

1. **以 xmake 自己的回答为准**：xmake.lua、用户的 `xmake f` 一变，模型就跟着变，用户不需要做任何事；
2. **不写项目**：只在私有目录里运行 xmake，不生成、不改写、不删除项目里的任何文件，包括用户的 `compile_commands.json`；
3. **每个问题只报一次**：说清原因和一个动作，问题消失时自动清掉；一过即逝的状态（写到一半的文件、重启瞬间）不报。

### X-1 能运行 xmake 就私有运行它

- **来源顺序**（信任、`mcppls.buildTool` 开、找得到 xmake 时）：私有运行 xmake（`describe`）为唯一来源。
  项目根目录或 `.vscode/` 里的 `compile_commands.json` 不再优先；
- **只在 xmake 跑不了时读用户的文件**：`buildTool` 关了、PATH 上没有 xmake、私有运行失败。这时若该文件比任一 `xmake.lua`（或用户的 xmake.conf）旧，
  报一次 notice："`compile_commands.json` 比 xmake.lua 旧，改动不会反映出来；运行 `xmake project -k compile_commands` 更新它，或打开 `mcppls.buildTool`"；
- **监视**：
  - `**/xmake.lua`；
  - 用户的 `.xmake/*/*/xmake.conf`（X-2）；
  - 用户的 `compile_commands.json` 只在回退时监视；
- **无感升级**：0.0.7 时读用户文件的项目，升级后第一次启动先用缓存的模型，私有运行回来后替换。若两边命令相同，模型不变，不会重启；
  不同（例如用户的文件是另一种模式生成的），按现有流程最多重启一次；CHANGELOG 写明；
- **仍想用自己文件的人**：`mcppls.buildTool` 设为 `off`，mcppls 就不运行 xmake，只读项目里的 `compile_commands.json`（现有语义，即上面的回退路径），文档写明。

### X-2 私有配置沿用用户的 `xmake f`

- 读项目 `.xmake/<plat>/<arch>/xmake.conf`，只读。有多个时取最新修改的那个，即用户最近一次 `xmake f`；
- 格式是 Lua 表，只解析顶层 `key = "string"` 与 `key = true/false`，不执行 Lua；
- 取值：`plat`、`arch`、`mode`、`toolchain`、`sdk`、`runtimes`、`kind`，加上其余标量键（项目自己 `option()` 的值），
  但排除内部键：`builddir`、`host`、`theme`、`network`、`proxy_pac`、`ccache`、`policies`、`pkg_searchdirs`、`ndk_stdcxx`、`__*`；
- 组成 `xmake f -c -p <plat> -a <arch> -m <mode> --<key>=<value> … --builddir=<私有>`，再加现有的离线策略参数；
- 退出码非 0 且输出含 "unknown option"（E5：255）时，只用前 7 个标准键重试一次，并记一条 notice，说明哪些选项没带上；
- 配置键（`xmake_configuration_key`）加入用户 xmake.conf 的大小和时间：用户重新 `xmake f` 就会私有地重新配置一次；
- 没有 `.xmake/` 时行为与现在相同（`xmake f -c`，xmake 的默认值）。

### X-3 没写标准时按构建编译器的默认

- `translate_gnu` 在 GCC 命令没有 `-std` 时补上 GCC 这个版本自己的默认，只在它与 Clang 的默认不同时补：
  - C++：≥ 16 为 gnu++20；11–15 为 gnu++17，与 Clang 相同，不补，所以这些项目升级后命令不变、不会因此重启；6–10 为 gnu++14；更老的为 gnu++98；
  - C：≥ 15 为 gnu23（GCC 15 起的默认）；8–14 为 gnu17，与 Clang 相同，不补；更老的为 gnu11；
- 统一标准（`unify_language_standard`）随之能看到这个标准，模块单元和标准库单元用同一个；
- 模块单元的标准低于 C++20 时（构建也会失败），报一次项目 notice："这些模块单元按 C++17 编译，模块需要 C++20；在 xmake.lua 里 `set_languages("c++20")`"。
  这里按构建系统给出对应写法：mcpp 的 `mcpp.toml`、CMake 的 `CMAKE_CXX_STANDARD`；
- **测试**：`gnu.cpp` 的单元测试（gcc 16 无 `-std` → gnu++20；gcc 13 → 不补；有 `-std` → 不动；C 源 → 不动）；fixture `xmake-no-standard`（X-7）。

### X-4 标准库单元编不过是项目问题，不是"卡住"

- `note_scan_failure_`：失败的单元是标准库单元（计划里的 std 单元），或在工作区之外（工具链、包目录），就不可能是"正在打字"，
  和命令被拒一样记为 `module-scan-failed`。标准库单元的文案是："标准库模块 `std` 用这个项目的命令编不过：<clangd 的第一条错误>"；
- 准备本身照常结束：prime unit 收到带错误的诊断就算完成，不记为已构建。xmake 那次的 preparation-stalled 是主方案 M-3 修掉的旧时钟问题，不是准备真的卡住（§9）；
- 用户修好（例如 X-3 补上标准、换了工具链）后，新数据库按现有 `forget_scan_failures_` 清掉这个问题；
- **测试**：xmake-no-standard（X-7）在 X-3 之前正是这个场景；X-3 之后它不再出现，这一条靠代码审查，另见 §9。

### X-5 写到一半的 `compile_commands.json` 等它写完

- 模型重新载入时，解析失败且文件在 2 s 内改过：不报警，也不标 stale，1 s 后再读，最多 5 次；
- 5 次后仍不合法，或文件已稳定 2 s 仍不合法，才报 `compdb-invalid`（保留上一个模型，现有行为）；
- 对所有读用户文件的来源生效：CMake 构建目录、显式数据库，以及 X-1 回退时的 xmake；
- **测试**：fixture `compdb-midwrite`，场景先写入截断的 JSON，300 ms 后写入完整的，断言没有 `compdb-invalid` 事件、模型跟上。

### X-6 临时模型不说"未信任"

- `start_inferred_load` 的临时模型以不信任方式加载，只是为了不运行外部程序。载入后去掉 `untrusted-workspace` 这条 issue，
  真正的信任状态只由 orchestrator 报；
- **测试**：test_server 或 fixture 断言可信工作区启动时的事件里没有 `untrusted-workspace`。

### X-7 xmake 的 conformance（现在一个也没有）

| fixture | 场景 | 断言 |
|---|---|---|
| `xmake-basic` | xmake + 一个模块 + `import std`（gcc） | 模型来源 xmake、std 准备完成、跳转可用 |
| `xmake-late-config` | 起初没有 `set_languages`，根目录有一份旧的 `compile_commands.json`；场景里改 xmake.lua | 模型在 10 s 内跟上；全程没有 `compdb-invalid`、`preparation-stalled`；项目目录里的文件没被改动（前后哈希） |
| `xmake-user-mode` | 项目带 `.xmake/…/xmake.conf`（mode=debug） | 引擎命令里是 debug 的参数（无 `-DNDEBUG`）；项目目录未改动 |
| `xmake-no-standard` | xmake.lua 不写标准、gcc 16、`import std` | 引擎命令带 `-std=gnu++20`；std 准备完成 |

CI 里 xmake 用 xlings 安装、固定版本（与本机 v3.1.1 一致）。只在 Linux job 跑；Windows 的 xmake 留给 GalTranslPP 之外的下一个真实项目。

- **默认（建议，Q2）**：一个文件只由一个引擎回答。
  - CLion 已经建模的项目（有已加载的 CMake、compilation database、Makefile 工作区）由 CLion 自己回答，mcppls 不启动；
  - 其余项目由 mcppls 回答；
  - 判断用 CLion 的工作区 API，以可选依赖（`<depends optional="true">`）隔离；API 不可用时退回"根目录有 CMakeLists.txt 即视为 CLion 建模"；

## 7. 多角度检查

| 角度 | 本方案怎么做到 |
|---|---|
| 架构 | 不新增组件：C-1、X-4 改 primer 与扫描失败，C-2 在 orchestrator 的 R-7 路径上，X-1、X-2 在 xmake provider，X-3 在 normalize |
| 稳定性 | 关掉 prime unit 减少 clangd 的并发构建；X-4 让卡住的准备有明确结局；X-5 去掉一过即逝的报警 |
| 优雅简洁 | C-1 以删代码为主（`heldPrimeUnits_`、`release_prime_units_if_idle_`）；X-1 把两个来源收成一个 |
| 用户体验 | 慢文件里补全最终会出现；改 xmake.lua 或 `xmake f` 后自动跟上；每个问题只报一次、带一个动作 |
| 兼容性 | 用户仍可用 `mcppls.buildTool: off` 改读自己的文件；CLion 仍支持 2025.2；include cleaner 行为不变 |
| 跨平台 | X-2 解析的是 xmake 自己的配置文件，三平台同一格式；C-1、C-2 与平台无关；真实 IDE 冒烟先覆盖 Linux |
| 一致性 | X-3 让 mcppls 读命令的方式与构建编译器一致；CL-4、Z-3 与 VS Code、Neovim 的"一个文件一个引擎"一致 |

| 无副作用 | xmake 只在私有目录运行，fixture 断言项目目录前后不变；不改用户的 clangd 配置 |

## 8. 风险

| 风险 | 表现 | 应对 |
|---|---|---|
| C-1 让冷启动变慢 | 后面的 prime unit 要重新验证 BMI | 门槛里比较 U1、U15-cold；超过 10% 走 C-1 的回退 |
| C-2 给出过时的列表 | 词前的文本变了还用旧答案 | 键里含词前文本；编辑器按前缀过滤；只存最新一份 |
| X-2 解析不了用户的 xmake.conf | 格式变化、手写的复杂表达式 | 只取顶层标量；解析失败时按现在的 `xmake f -c` 并报一次 notice |
| X-1 与用户手工生成的文件不一致 | 用户用了 `xmake project` 的额外参数 | 文档写明 `mcppls.buildTool: off` 即改读用户的文件 |
| CLion 工作区 API 变化 | 判断"已建模"失效 | 可选依赖加退路；CL-2 在两个版本上验证 |
| Zed 在 CI 上渲染失败 | lavapipe 与 Zed 版本不兼容 | 先在 nightly 连跑 10 次，稳定后才进 PR 门槛；版本号固定 |
| 1.9 GB 的 CLion 下载 | CI 时间与缓存配额 | 按版本缓存；PR 上缓存命中时不下载；缓存配额不够时 verifier 只查 2026.2.3，2025.2 留给 nightly |

## 9. 实现记录

- **Q1–Q5**：按 §5 的建议执行，与主方案"Q1–Q5 取最合适和推荐的"的定法一致；review 若改变决定，再调整。
- **分工**：CLion（CL-1..CL-4）、Zed（Z-1..Z-3）、xmake 来源（X-1、X-2、X-5、X-6、X-7）各在独立的 worktree 里并行实现；
  C-1、C-2、C-4、X-3、X-4、I-1 在主工作树（f78d6c9）。
- **C-1**：实现前补了一个实验（E7，已验证）。clangd 23.1 在 didClose 之后只删掉带时间戳的"使用中"副本，
  `m.pcm` 本体留在模块缓存里；重新打开导入方 0.35 s 出诊断（第一次 1.66 s）。
  没有做 §2 说的"只重建用户打开的文件"的 fixture 断言：同一模块被重复准备时，prime unit 本来就会构建多次，日志里的次数分不开两种行为。
  C-1 的门槛只看 4 核上的 ux（U16、U7a、U1、U15）。
- **C-2**：
  - 预算到期时，只保留 core engine 的请求，其他引擎照常取消；
  - 等待中的请求（`waitsForLate`）没有自己的 clangd 请求，到了它的预算就拿文件里的词；
  - 空答案或错误不给任何人；
  - 报告的 `completion.late` 记 `arrived` 与 `served`。
- **C-4**：`slowestFiles` 按"最慢方法的 p95"排前 10 个文件；`buildTimes` 取日志环（4000 行）里 preamble、前置模块的秒数和 AST 构建次数，按总秒数排前 20。
- **X-3**：规则扩到 C（GCC 15 起默认 gnu23）；另加了模块单元低于 C++20 时的一次性 `module-standard-too-old`。
- **X-4**：没有改 primer（见 §3 X-4），只让标准库单元和工作区外单元的扫描失败进入 `module-scan-failed`，文案点名标准库模块。

  - 新检查类型 `diagnostic-code-lines`；
