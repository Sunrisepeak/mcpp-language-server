# 0.0.19：CLion 插件携带服务端，一个文件一个引擎，main 的代码模板

日期：2026-10-29。状态：**设计已定**（按平台分包由维护者选定；冲突处理由维护者提出）。基线：main `b807c3a`（0.0.18）。
涉及仓库：mcpp-language-server（0.0.19，一个 PR）、mcpp-ide（0.1.1，一个 PR）、xim-pkgindex（mcppls 0.0.19 与 mcpp-ide 0.1.1 两个条目）。

## 0. 结论

| 问题 | 结论 |
|---|---|
| CLion 插件不带服务端 | 0.0.19 起按平台分包：每个包带本平台的 payload，商店按 IDE 所在系统和架构下发对应的包，装上即可用，与 VS Code 的 VSIX 一致 |
| CLion 的引擎与 mcppls 同时回答同一文件 | 一个文件一个引擎。征得同意后，在 mcppls 回答的文件里关闭 CLion 自身引擎的语义诊断与补全；不经同意不改任何设置；可随时恢复 |
| mcpp-ide 找不到 0.0.18 的服务端 | 0.1.1 起候选项按 payload 解析（运行器 + 镜像），CLion 适配器把 mcppls 插件携带的 payload 交给后端 |
| 没有语义引擎会补全 `main` | 新模块 `mcppls.engine.native.templates` 持有一张固定模板表，文件作用域给出 `auto main() -> int { }` 与 `int main() { }`（§5） |

## 1. 证据

### 1.1 0.0.18 的 CLion 插件

- `mcppls-clion-0.0.18.zip` 共 25,992 字节，只含 `lib/mcppls-clion-0.0.18.jar` 与 searchableOptions；不含服务端。
- `plugin.xml` 的说明要求把 `payload/bin` 放到 PATH。0.0.18 的 `payload/bin` 只有 `okrun` 与 `mcppls.okb`，没有名为 `mcppls` 的程序，照做找不到服务端。
- 找不到服务端时，插件退回 `mcppls serve`，启动失败且不提示（`McpplsServerSupportProvider.createCommandLine`）。
- CI 的 CLion 测试把 `MCPPLS_PAYLOAD` 链接到用户数据目录（`build.gradle.kts` 的 `tasks.test`），因此未暴露上述缺失。
- mcpp-clion 强制依赖本插件；mcppls 缺失时，其 “Install mcppls” 打开插件设置与 GitHub release 页（`Dispatch.languageServiceAction`），插件已装时无路可走。

### 1.2 payload 的组成（v0.0.18 四个平台实测）

| | darwin-arm64 | linux-arm64 | linux-x64 | win32-x64 |
|---|---|---|---|---|
| 压缩后 | 27.7 MB | 29.9 MB | 31.0 MB | 37.1 MB |
| 本平台独有（解压后） | 69.8 MB | 73.0 MB | 77.7 MB | 146.0 MB |

四个平台逐字节相同的部分为 30.8 MB（含 `bin/mcppls.okb`）。差异集中在 `clangd/bin`（每平台约 52 MB）与 `kit/`（Windows 另含 97.6 MB 的 `generic-w64-mingw32`）。四平台合一的包压缩后约 100 MB、解压后约 400 MB，每个用户只用其中一份。

### 1.3 JetBrains Marketplace 的按平台分发

- JetBrains Marketplace 对 2026.1（since-build 261）及以上的 IDE 按 `plugin.xml` 中对 `com.intellij.modules.os.*` 与 `com.intellij.modules.arch.*` 的依赖选择版本。
- CLion 自身的 C/C++ 插件即按此方式分发：`org.jetbrains.plugins.clion.radler` 的版本为 `262.10968.117-linux-x86_64`，依赖 `com.intellij.modules.os.linux` 与 `com.intellij.modules.arch.x86_64`（CLion 2026.2.3 发行包）。
- 本仓库已用的 IntelliJ Platform Gradle Plugin 2.19.0 提供 `intellijPlatform.nativeVariants`：
  - 每个变体的文件按相对路径复制进插件目录；
  - 变体的 `plugin.xml` 版本加后缀 `-<os>-<arch>`，并补上 OS 与架构依赖；
  - since-build 低于 261 时拒绝构建（`PreparePluginVariantTask.validateSinceBuild`）；
  - `prepareSandbox` 复制当前主机的变体（`PrepareSandboxTask.copyNativeVariant`），因此测试沙箱即携带 payload 的插件。
- 单个插件文件上限 400 MB。

### 1.4 CLion 自身的引擎

- **引擎现状**：CLion 2025.3 起默认使用 Nova（ReSharper C++ 引擎）。2026.2 起发行包不再含 Classic 引擎，Classic 改为商店插件 `com.intellij.cidr.lang`（与 Nova 互斥）。
- **未配置目录也会分析**：项目未配置构建系统时，Nova 仍对文件做代码分析，状态为 “Project is not configured. Code insight uses '{0}' for name resolution”（`CLionOpenFolderBundle.properties`）。mcpp 项目即属此类：Nova 按默认编译器解析，`import` 与模块名在 Nova 看来无法解析。
- **按文件设置高亮级别**：平台把每个文件的高亮级别（`HighlightingSettingsPerFile`，即检查组件里的 None / Syntax / All Problems）经 `FileHighlightingSettingListener.SETTING_CHANGE` 广播。Nova 的前端订阅该主题，并把级别同步给后端（`com.jetbrains.rdclient.daemon.components.FrontendDaemonHost$MyListener` → `HighlightingSettingsModel`）。`HighlightingSettingsPerFile` 不带 `@ApiStatus.Internal`。
- **各级别关掉哪些平台 pass**（CLion 2026.2.3 字节码）：

  | pass | 判据 | None 时 | Syntax 时 |
  |---|---|---|---|
  | `GeneralHighlightingPass` | `shouldHighlight` | 停 | 保留 |
  | `LineMarkersPass` | `shouldHighlight` | 停 | 保留 |
  | `ExternalToolPass`、`InspectionRunner` | `shouldInspect` | 停 | 停 |
  | LSP 的 `LspHighlightingPass` | 不检查级别 | 保留 | 保留 |

  因此 Syntax 级别关掉 CLion 的语义诊断与检查，保留语法着色、行标记（mcpp-clion 的运行图标）与 mcppls 的诊断。
- **补全来源**：
  - Nova 的补全由前端的 `com.jetbrains.rider.completion.ProtocolCompletionContributor` 提供；
  - LSP 的补全由 `LspCompletionContributor`（`order="last, before wordCompletion"`）提供；
  - 公开的 `LspCompletionSupport.createLookupElement` 可以标记 mcppls 产生的条目。
- **无头测试的局限**：在 CI 的 CLion 无头测试里，Nova 后端不回答：只有 CLion 时高亮为空，补全在测试框架的 100 秒上限内无结果（CI run 40739365603 的 `CLION-ENGINE-EVIDENCE`）。Nova 在图形界面中的实际效果不能由该测试观察。

### 1.5 mcpp-ide 0.1.0 对 mcppls 的探测

- VS Code 适配器把 `<extension>/payload/<server.path>`，即 `bin/mcppls.okb`，作为候选程序交给后端（`vscode/src/backend/mcppls.ts`）。
- 后端直接执行该文件的 `--version`（`languageservice.cppm` 的 `probe`）。okb 不是可执行文件，因此对 0.0.18 的结果为 `unreadable`。
- 用户数据目录的候选为 `<data>/mcppls/payload/bin/mcppls`，0.0.18 的 payload 中没有这个文件。
- CLion 适配器只传 `MCPPLS_SERVER`。
- VS Code Marketplace 上 `sunrisepeak.mcpp-language-server` 为 0.0.17，低于 mcpp-ide 要求的 0.0.18（`kRequired`）；Open VSX 为 0.0.18。

## 2. CLion 插件携带服务端

### 2.1 变体

- **四个变体**：与 VS Code 同为 `linux-x64`、`linux-arm64`、`darwin-arm64`、`win32-x64`。每个变体在插件目录下携带本平台的 payload：`mcppls-clion/payload/`，内含 `payload.json`、`bin/okrun`、`bin/mcppls.okb`、`clangd/` 与 `kit/`。payload 与同版本的 `payload-<platform>.tar.gz` 逐字节相同。
- **另两个组合**：Gradle 插件同时构建的 `mac-x86_64` 与 `windows-arm64` 不携带 payload，不随 release 发布。
- **since-build 为 261**：Plugin Verifier 对 2026.1 与构建所用的 2026.2.3 各检查一次。
- **构建输入**：
  - payload 目录由 Gradle 属性 `mcppls.payload.<platform>` 指定；
  - 环境变量 `MCPPLS_PAYLOAD` 指定当前主机的 payload，供开发与测试使用；
  - 指定了任一 payload 即启用 `nativeVariants`；
  - 不指定时构建的插件不带服务端，仅用于开发。
- **发布资产**：`mcppls-clion-<version>-<platform>.zip`，按平台声明于 `packaging/release.manifest.json`。

### 2.2 启动服务端

依次查找：

1. `MCPPLS_SERVER`：开发与测试用的程序绝对路径，与 VS Code 扩展同名同义；
2. 插件携带的 payload：`<插件目录>/payload`，按 `payload.json` 的 `server.runner` 与 `server.path` 启动；
3. PATH 上的 `mcppls`：通用包、单文件或 xlings 安装的服务端，供不带 payload 的构建使用。

此外：

- payload 的 `platform` 与本机不符时，不启动，并说明应安装本系统的插件包。
- 商店与磁盘安装都可能丢失可执行位，启动前对 `server.runner` 与 `clangd.path` 补上可执行位，与 VS Code 扩展的 `ensureExecutable` 相同。
- 三处都找不到时，每个项目提示一次：说明本构建不带服务端，并给出两种办法——安装本系统的插件包，或把 `mcppls` 放到 PATH（`xlings install mcppls`）。
- 用户数据目录的 payload（`<user data>/mcppls/payload`）此后只由 Zed 使用；CLion 插件不再查找它。

### 2.3 devtools

- `extension --editor clion`：
  1. 把本机的 payload 准备在 `target/pack/clion-payload/`。`--payload` 给出时取它，否则按现有流程组装。
  2. 以 `-Pmcppls.payload.<本机平台>=<目录>` 运行 `buildPluginVariant_<os>_<arch>`，产物为本平台的变体包。
- `--install`：解包变体包；变体包携带 payload，不再在用户数据目录放服务端。
- `uninstall`：Zed 与 CLion 共用的服务端随最后一个使用者删除。携带 payload 的 CLion 不算使用者。

### 2.4 CI 与 release

- `release-checks.yml` 的 `plugins` 作业下载四个 payload 制品，去掉 `stage/`，以四个 `mcppls.payload.*` 运行 `buildPluginVariants`，并按 `mcppls-clion-<version>-<platform>.zip` 命名。
- `install` 作业在每个平台安装本平台的变体，从插件目录启动其服务端并回答 conformance 的 `inferred` 夹具，然后卸载。
- `clion-e2e` 不再链接用户数据目录：测试沙箱即携带 payload 的插件（§1.3）。PATH 中没有 `mcppls` 与 `mcpp`，`HOME` 为空目录，因此测试启动的必然是插件携带的服务端。
- `candidate` 作业按清单收集四个变体包。

## 3. 一个文件一个引擎

### 3.1 规则

既有的归属规则不变：CLion 建模的项目归 CLion，其余归 mcppls；“Also for projects CLion models” 让 mcppls 也回答前者。新增的只是：在 mcppls 回答的文件里，CLion 自身的引擎（Nova，或用户另装的 Classic）是否同时回答，由用户决定。

### 3.2 询问

- **何时问**：每个项目第一次有文件由 mcppls 回答时，询问一次：

  > CLion's own C/C++ engine also analyses the files mcppls answers in this project, so problems and completions come twice.
  > [Use mcppls only in this project] [Always use mcppls only] [Keep both]

- **答案存放**：项目级的答案存于项目的工作区文件，“Always” 存于应用级设置。询问只发生一次：通知被关闭而未作答时，该项目按 “Keep both” 处理，答案仍可在设置页与动作中给出。“Always” 之后，没有自身答案的项目直接按 “mcppls only” 处理。
- **之后修改**：Settings | Tools | mcppls 有三选一的 “CLion's engine in files mcppls answers”（本项目：跟随全局 / mcppls only / both），以及应用级默认（ask / mcppls only / both）。Tools | mcppls 下有两个动作：“Use mcppls Only in This Project” 与 “Restore CLion's Engine in This Project”。
- **同意原则**：不经回答或用户执行的动作，不改任何设置。这一点与 VS Code 扩展的冲突处理（design 2026-09-25 §10）相同。

### 3.3 “mcppls only” 做什么

对本项目中 mcppls 回答的每个文件：

1. **高亮级别设为 Syntax**（`FileHighlightingSetting.SKIP_INSPECTION`）。
   - **效果**：Nova 经 §1.4 的同步关闭该文件的语义诊断，平台的检查与外部工具同时关闭。
   - **保留**：语法着色、行标记与 mcppls 的诊断。
   - **记录与恢复**：设置前记下原级别。恢复时，只对仍为 Syntax 的文件写回原级别；用户事后亲手改过的文件不动。
2. **补全只留 mcppls 的条目**。
   - **做法**：
     1. 插件经 `lspCustomization` 提供 `LspCompletionSupport`，在 `createLookupElement` 中标记 mcppls 的条目。
     2. 一个 `order="first"` 的补全贡献者在该文件里运行其余贡献者。
     3. 结果中只保留带标记的条目（逐层解开 `LookupElementDecorator`）和平台的 Live Template。
   - **效果**：其余条目被丢弃，Nova 的条目与单词补全随之去掉。

“Keep both” 与恢复动作撤销以上两项。文件在打开时处理：平台只在启动服务器时调用 provider 的 `fileOpened`，因此插件另以 `EditorFactoryListener` 观察每个打开的编辑器。未打开的文件不涉及。

### 3.4 其他插件

- **Classic 引擎**（商店插件 `com.intellij.cidr.lang`）运行在前端，同样服从 §3.3 的高亮级别与补全过滤，不另作处理。
- **只指出、不处理**：另一个 LSP 客户端为 C/C++ 运行的语言服务器（如 LSP4IJ `com.redhat.devtools.lsp4ij` 中用户定义的 clangd）。它的补全与经平台检查报告的诊断已被 §3.3 排除，但其服务器仍在运行。
- **原因**：插件没有公开的接口去关闭另一个插件的语言服务器，也不按项目停用别的插件。
- **提示方式**：每个项目检测到时提示一次，写明插件名，并给出打开 Settings | Plugins 的动作。
- **候选清单**：集中声明在一处（`OneEngine.kt` 的 `OtherLanguageServices.CANDIDATES`）。

### 3.5 mcpp-clion

mcpp-clion 不注册语言服务，与 mcppls 不构成冲突；与 VS Code 一侧 mcpp-vscode 不在冲突清单中的理由相同。

## 4. mcpp-ide 0.1.1

1. **`languageservice`**：
   - 候选项可以是 payload 目录。后端读其 `payload.json`，以 `server.runner server.path`（或 `server.path` 单独）为命令执行 `--version`。
   - 其余候选（PATH、xlings、`<data>/mcppls/payload`）按程序或 payload 目录同样处理。
   - `Status` 记录完整命令。
2. **VS Code 适配器**：传 mcppls 扩展的 payload 目录（`MCPPLS_PAYLOAD` 或 `<extension>/payload`），以及 `MCPPLS_SERVER`。
3. **CLion 适配器**：
   - 传 mcppls 插件携带的 payload 目录（`PluginManagerCore.getPlugin("io.github.sunrisepeak.mcppls").pluginPath/payload`），以及 `MCPPLS_SERVER`；
   - mcpp-clion 的 since-build 改为 261，与其依赖一致；
   - “Install / Update mcppls” 打开 Settings | Plugins 的 Marketplace 页并搜索 mcppls。
4. **版本**：mcpp-ide 0.1.1、mcpp-vscode 1.0.1、mcpp-clion 0.1.1。`mcpplsPluginVersion` 为 0.0.19，构建与测试取本主机平台的 `mcppls-clion-0.0.19-<platform>.zip`。

## 5. main 的代码模板

- **依据**：clangd 的文件作用域代码模式只有 `namespace`、`using namespace`、`template`、`module`、`import` 等，没有 `main`（`SemaCodeComplete.cpp:2271-2354`）。mcppls 自身此前不产生 snippet 条目。
- **模块**：`src/engine/native/templates.cppm`（`mcppls.engine.native.templates`）。它与 `keywords` 并列，持有一张固定的模板表，首两项为 `auto main() -> int { }` 与 `int main() { }`。作用域判断复用 `keywords` 导出的 `read_before`；“已声明 `main`”的判断复用 `outline::declarations`。
- **规则**：S3-6.4-1 至 S3-6.4-5。
  - 只在文件作用域、且声明从本行开始时给出：前文以 `;` 或 `}` 结束，或没有前文；光标后无内容。
  - 已输入的是 `main` 的前缀，可以单独出现，也可以跟在该模板的类型（`int`、`auto`）之后。
  - 文件已声明 `main` 时不给出；命名模块单元中不给出（[basic.start.main]）。
  - 客户端支持 snippet 时，光标留在函数体内；否则按模板原文插入纯文本。
  - 排在语义条目之后，`detail` 标明为模板。
- **合并**：在 `finish_job` 中与模块语法关键字同样并入 clangd 的结果；空格触发的请求不给出。`cxxModules/report` 在关键字的计数旁另计 `templatesWithoutEngine`，R1 的含义不变。
- **测试**：单元测试 `tests/test_templates.cpp`；conformance 场景 `completion-templates` 开启 snippetSupport，并借新的检查种类 `completion-item` 读取单个条目的字段。

## 6. 测试

| 层 | 内容 |

| CLion 无头测试 | 沙箱插件携带 payload 并由其启动服务端；不带 payload 且 PATH 为空时提示一次；payload 平台不符时拒绝启动；询问的三种回答各自的存储；“mcppls only” 后打开的文件为 Syntax 级别，且 mcppls 的 `missing.module` 诊断仍在；恢复只写回仍为 Syntax 的文件；补全过滤只保留带标记的条目（对构造的条目判定，不经 Nova） |
