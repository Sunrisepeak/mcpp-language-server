# 0.0.13 设计方案：看得见、开得快、改得稳

日期：2026-10-12。

输入：
- issue #45 #47 #48 #50 #51 #52 #53；
- 两份用户诊断包：一个 Qt + `build.mcpp` 项目，以及 #53 的项目；
- 一个大型 Windows 模块项目上的临时验证探针（约 40 个模块，MSVC STL，重量级第三方头文件）的两轮完整运行（含稳态测量），日志摘要在 Actions 内提取（见 V1）。

0.0.12 解决了“崩溃、重启、误报”：在大型 Windows 项目上零退出、输入时零重启、诊断零误报。0.0.13 的主题有三个：

- **看得见**：出了问题，日志和概览就能说明是什么、为什么。
- **开得快**：第二次打开不重建、不久等；冷启动先让打开的文件可用。
- **改得稳**：局部失败（一个模块编不过、`build.mcpp` 写到一半、mcpp 自己失败）只影响局部。

重点平台是 Windows。CI 的 fixture 是门槛，大型项目探针只用来临时验证 Windows 上的性能和稳定性。

## 1. 目标与量化指标

| 场景（大型 Windows 模块项目，CI 4 vCPU） | 0.0.12 | 0.0.13 目标 |
|---|---|---|
| **第二次打开**（同一缓存，源码未变） | 188 s 才 ready，19/25 个模块重建 | 重建 **0** 个；打开的文件 **≤ 5 s** 给出首个语义回答；打开的文件全部 ready **≤ 30 s**；clangd 重启 0 次 |
| 第二次打开，但中间 `git checkout` 过（只有 mtime 变化） | 同上 | 与上一行相同 |
| 冷启动 | 486–608 s 才稳定；打开的文件第 71 s 才首次在 1 s 内作答 | 打开的文件 **≤ 10 s** 有语义回答（W1 的部分回答）；它的前置集合在现在一半的时间内就绪；clangd 重启 ≤ 1 次；全项目稳定 ≤ 350 s |
| 输入时的补全 | 18/24 为空（1 s 预算内没答上） | clangd 在 1 s 内作答的比例 ≥ 80% |
| 一个模块失败 / `build.mcpp` 坏了 / mcpp 失败 | 全部为空，或模型缺块、重启 | 其余部分照常；目标代码保留完整模型 |
| 出问题时 | 只看到 “stale” 和计数 | 日志里有每一个代价高昂或扰动性决策的原因（W6） |

Linux 上的门槛保持不变：ux-mcpp U2 暖启动重建 0 个模块。另外，ux-xlings 的 first-open 降到 1 s 以内。

不变的约束：mcppls-clangd 在任何方面都不弱于原版 clangd；发布前 CI 全绿，并用探针对比上一版。

## 2. 交付方式：单 PR，以 commit 为 checkpoint

- 产品只开**一个 PR**。引擎在另一个仓库，同样只开**一个 PR**，与 0.0.12 的流程相同：
  - 产品 PR 通过 `engine-candidate.json` 测试引擎 PR 的构建；
  - 引擎发布后做 lock switch。
- 每个 commit 都是 checkpoint：能编译、单元测试通过、相关 fixture 通过、可以单独回退；commit 信息写明对应的工作项。
- 每个 checkpoint 推送一次，让 CI 在四个平台上验证它。
- 涉及性能的 checkpoint，用 Windows 探针跑一轮。
- 引擎的每个工作项是一个独立补丁，记入 PATCHES.md。
- 探针本身的改造（V1）在临时验证 PR 上进行，它是验证工具，不属于产品 PR。

层：E = 引擎，P = 产品。

### 2.1 多角度拆分

| 角度 | 原则 | 落在哪些工作项 | 约束 / 检查 |
|---|---|---|---|
| 架构 | 引擎只做引擎能做好的事（模块构建、有限等待、重建原因）；产品负责策略（何时应用、何时重启、显示什么）。新行为都由引擎在 `engine.json` 中声明的特性开关，产品按特性启用 | W1、W2、W6(E3)、W8 → 特性 `bounded-module-wait`、`partial-prerequisites`、`rebuild-reasons` | 产品不解析引擎没有声明过的行为；没有声明特性的引擎，走 0.0.12 的路径 |
| 稳定性 | 局部失败只影响局部；任何不完整的输入（describe、模块、build.mcpp）都不能替换完整的状态；新增的每个等待都有上限 | W2、W3(b)、W4、W10 | 每一条都配有“失败注入” fixture：mock mcpp 失败、模块编不过、clangd 构建缓慢 |

### 2.2 任务依赖关系

```
                ┌────────────── 基础：看得见 ──────────────┐
                │ P-OBS  产品可观察性（W6 产品侧）            │
                │ P-VER  版本 / about / 概览（W7）            │
                │ E-WHY  引擎重建原因（W6 E3）                │
                └──────┬──────────────┬──────────────┬─────┘
                       │              │              │
      稳定性线          │      启动性能线 │       引擎线   │（与产品并行）
  P-SPIN  W4 ◀────────┤      P-FRESH W5.1-2 ◀──────┤      E-WAIT   W1
  P-HARD  W10         │      P-PROV  W5.6           │      E-PART   W2
  P-LKG   W3(b) ◀─────┤      P-READY W8 ◀── E-WHY   │      E-PRIO   W5.7
  P-APPLY W3(a) ◀ P-LKG      P-LOOP  W5.10          │      E-MEMO   W5.4
  P-GEN   W3(d)(e) ◀ P-VER                           │      E-WORKERS W5.8
                       │              │              │
                       └──────┬───────┴──────────────┘
                              ▼
                 P-ENGINE  接入候选引擎（engine-candidate.json），按特性启用：
                           W1 状态、W2 停止转交、W8 进度、W6 重建原因汇总
                              ▼
                 P-REL     版本号 0.0.13、CHANGELOG、规范与文档、lock switch
```

- 可以并行的：引擎线与产品的三条线并行；产品线内部，P-SPIN、P-HARD、P-FRESH 彼此独立。
- 必须串行的：P-APPLY 依赖 P-LKG（失败时需要兜底）；P-READY 和 P-ENGINE 依赖引擎特性；P-REL 在最后。
- 引擎补丁的顺序：E-WHY 最先，因为后面每一步的效果都要靠它来观察；E-WAIT、E-PART 接着做，它们解决的是用户最直接的感受；E-PRIO、E-MEMO、E-WORKERS 是性能项，最后做。
- 调查后再决定的：std 跨工作区共享（W5.9）、preamble 跨会话复用（W5.5）、W9 的深层 profile。它们风险高、收益要等数据证明，本版先产出调查结论和观测数据（借助 E-WHY 和启动时间线）。如果证据充分且改动可控，就纳入本版；否则写明原因，延到下一版。

## 3. 工作项

### P0

#### W1 补全对缺失模块和首个 preamble 只做有限等待（E；#52-1、#50）

**现状**（`CodeComplete.cpp`）：
- 只有依赖被编辑时有限等待 250 ms；
- 新出现的、项目能构建的 import（`NewModule`），同步构建，没有上限；
- `codeComplete` 在 modules 模式下以 `TUScheduler::Stale` 无限等待首个 preamble。

**方案**：
- `NewModule` 也改为 `buildPrerequisiteModulesWithin(Wait)`：超时就用已附带的模块作答，构建在后台继续。
- TUScheduler 增加一致性级别 `StaleWithin(Deadline)`：截止前没有 preamble，就按 `StaleOrAbsent` 走原版的 fallback。最坏情况下回答内容与原版相同，延迟最多多 600 ms，仍在 1 s 预算内。
- 回答不完整时带 `isIncomplete: true`，客户端下一次按键会重新请求。
- 默认预算：缺失模块 250 ms，首个 preamble 600 ms，可通过引擎参数调整。
- 引擎声明特性 `bounded-module-wait`；产品在状态中注明“模块仍在准备”。

**测试**：
- `ux-modules-cold`：冷缓存下每秒请求一次补全；从第 1 秒起在 1 s 内作答，且不止关键词；模块就绪后，回答包含导入的名字。
- 探针 E-typing：达到 §1 的比例。

#### W2 一个前置模块失败，其余照常加载（E + P；#47，以及探针中的同类现象）

**方案**：
- E：`getOrBuildModuleFiles` 返回已建成的子集和失败列表。新增 `PartialPrerequisiteModules`：失败模块及其下游视为未解析的 import，走 0011 的恢复路径。
- E：在失败模块的 import 处给出诊断 `module 'X' could not be built: <第一条 clang 错误>`，在 info 级别输出，不再需要 `--log=verbose`。
- P：引擎声明 `partial-prerequisites` 后，产品不再把依赖失败模块的文件转给 mcppls 自己的引擎（`apply_doom_diff_`），只在状态和 report 中列出原因。
- 根因调查：按 #47 的项目做 fixture `module-one-fails`。

**测试**：`module-one-fails` 中：
- `std::` 和其余模块的补全都有结果；
- 失败模块的 import 处有可读的诊断；
- 没有文件被转给 mcppls 的引擎；
- 修好后自动恢复。

#### W3 `build.mcpp` 的编辑体验，以及“描述失败时目标代码保留完整模型”（P；#52-2）

**本质**：`build.mcpp` 是构建流程的一部分，emit 需要编译并运行它，才知道目标代码的参数和生成单元。现状下：
- 每次保存，1.5 s 后就重新 describe，而且编辑推迟不了它；
- 描述失败时，部分描述照单全收；
- 打开文件的参数一变，就重启 clangd；
- 生成文件在构建之前，目标代码里只是 “file not found”。

探针证明，即使没人编辑，**mcpp 自己也会失败**，所以兜底不能只针对用户的编辑。

**原则**：
- 编辑不等于应用：编辑由 clangd 在 `:build` 上下文中服务；应用需要运行 mcpp，所以要有门控。
- 目标代码只采用完整描述（last-known-good）。
- 应用以最小代价生效。
- 状态可见，也可以手动控制。

**(a) 何时应用**
- 静默期：已保存且 2 s 内没有再变化；编辑可以推迟它。
- 预检：`build.mcpp` 打开时，clangd 对当前版本报 error 就不运行 mcpp。clangd 10 s 内没有诊断、文件没有打开、或 mcpp 太旧没有 `:build` 集合时，跳过预检。
- 单飞：每个根目录同时最多一个 emit。运行中又有变化，只记 dirty，结束后再跑一次；不杀正在运行的 emit，避免留下写了一半的生成物。
- 手动：命令 `mcppls: Apply build.mcpp`，设置 `mcppls.buildProgram.apply = auto | manual`。
- 只在受信任的工作区应用。

**(b) 失败时**：适用于任何一次 describe 得到不完整的结果，不论起因是用户的编辑还是 mcpp 自己出错。
- 触发条件：`MCPP_BUILD_DATABASE_PROGRAM_FAILED`、构建程序运行失败、或超时。
- 目标集合整体沿用 last-known-good，不改 plan、不重启；`*:build` 集合可以更新。
- last-known-good 随模型缓存持久化，并标记 “failing since …”。
- 错误作为诊断发布到对应的 `build.mcpp`，取用顺序：结构化诊断 > 解析 stderr 中的 `file:line:col` > 第 1 行加 stderr 尾部；与 clangd 的同类错误去重。
- 状态：`build.mcpp does not compile; the targets keep the description from HH:MM`。
- 这一条同时修复暖启动 degraded 的问题，也是暖启动重建模块的嫌疑之一：模型在“完整”和“缺块”之间来回切换，单元的参数随之变化，BMI 的键也跟着变（见 W5）。

**(c) 成功时**
- 只有 `:build` 集合变化，或只新增了单元：不重启。
- 打开文件的参数变化：由引擎就地重读命令并重建（`compilationDatabaseChanges`，或一个小的引擎补丁），不重启。
- 模块提供者移走：仍需重启，但合并为一次。
- 目标：一次编辑最多重启一次，常见修改不重启。

**(d) 生成代码**
- include 了尚未生成的声明输出时，诊断说明是哪个生成器、来自哪个输入，并提供 “Build in Terminal”。
- 生成文件出现或变化后重读，不重启。
- 生成文件在编辑器中设为只读。
- 不自动运行 `mcpp build`。

**(e) 版本**：提示中写明 mcpp 版本，以及 build.mcpp 支持所需的 ≥ 2026.10.11.1（依赖 W7）。

**(f) 向 mcpp 提的需求**：
1. 构建程序失败时给出结构化诊断；
2. 失败时沿用上次成功的产物；
3. 提供只编译、不运行的检查方式；
4. 查清引擎模块偶发 precompile 失败（`mcpp.deps` 等）的原因；
5. 输入未变时 emit 走 fast-path（现在每次启动 20–70 s）。

**测试**：
- `build-program-broken-autosave`；
- `build-program-typing`（30 s 内 emit ≤ 3 次，零重启）；
- `build-program-runtime-failure`；
- `build-program-flag-change`（零重启；引擎就地重读之前，允许一次）；
- `generated-header-missing`；
- `build.mcpp` 坏着时重启 server，目标代码仍是完整模型；
- `producer-fails-midway`：mock 一个先成功、后报 `PROGRAM_FAILED` 的 mcpp，要求模型不变、不重启、不 degraded。

#### W4 SpinWatch 按“同一个版本”计时（P；#53）

**现状**：只要 clangd 的状态一直带着 `parsing main file`，就算同一次构建。连续输入时，6 个版本的重建被记成一次 20.9 s 的构建，导致 set-aside 和重启。

**方案**：
- 以 clangd info 级别的 `ASTWorker building file <f> version <n>` 为准，每个新版本重新计时；
- 在日志限流之前解析这一行；
- 旧引擎没有这行日志时，构建期间送入了新版本就视为重新开始。

**测试**：
- guard 单元测试；
- `typing-slow-file`：mock 一个每次构建 3 s 的 clangd，10 Hz 输入 60 s，零 spin、零重启。

#### W5 冷启动与暖启动的性能（P + E；#52-3、#50，以及 §0.2 的探针证据）

**暖启动（第二次打开）应当几乎不花时间**：模型、BMI、校验结果都已经在磁盘上，需要做的只是确认它们仍然有效。

1. **只有 mtime 变化时，模型仍然 fresh**：
   - 模型指纹先比较 size + mtime；不一致时，再比较各 watch 输入的内容哈希。缓存里保存小文件的哈希；glob 只比较匹配到的文件列表。
   - 内容相同就算 fresh，处理 `git checkout`、切分支、恢复文件这些情况。
   - 日志写明是哪一个输入变了（W6）。
2. **fresh 的模型立即使用，producer 在后台确认**：
   - 确认结果相同：什么都不做；
   - 不完整或失败：保留缓存（W3(b)）；
   - 确认结果有差异：按 W3(c) 的最小代价应用。
   - ready 不再等待 producer。
3. **BMI 跨会话复用，并且要证明在复用**：
   - 用 W6 的“为什么重建”日志定位 19/25 和 14 个模块各自的重建原因。嫌疑依次是：模型来回切换导致参数变化（W3(b) 修复）；Windows 上非 owned cache 的 BMI 跨重启的保留情况；内容摘要（0.0.12 的 producerDigest）在 Windows 路径下是否稳定。
   - 门槛：探针中的第二次打开重建 0 个模块。
4. **第二次打开时，前置集合的校验结果持久化**（E）：模块校验 memo 落盘，键与进程内的 memo 相同，按精确输入。目标是把 Run.cpp 的 24.4 s 降到 1 s 以内。
5. **preamble 跨会话复用（调查后决定）**（E）：Run.cpp 的 53 MB preamble 每次会话都要 9.9 s。
   - 调查把 preamble 按“全部输入的精确摘要”（0.0.12 的 TextualPreambleProof 已经记录了这些输入）存盘，第二次打开时校验后直接加载。
   - 如果风险或体积不可接受，就退而依赖 W1 的有限等待加 W9 的体积优化。
6. **冷启动不再来回切换模型**：
   - 检测到 producer、但没有缓存时，临时模型只服务打开文件的非模块功能，不启动模块构建，也不启动 prime 和后台索引，等 producer 的模型到达再启动；
   - producer 失败或超时之后，临时模型转正，再开始构建。
   - 这样可以去掉冷启动的 3 次重启，以及在错误参数下的无效构建（GPPDefines 就是这样失败的）。
7. **优先级**（E）：正在编辑和已打开的文件的前置集合优先；prime 单元和后台索引排在 ready 之后。
8. **Windows 上的构建并发**：并发上限有 414 s 停在 2。查清上限是怎么定的，改为按内存准入决定（与 Linux worker 的内存预算一致），而不是固定值。
9. **std 模块在多个工作区之间共享**：std 和 std.compat 的 BMI 在 Windows 上要 96 s。按精确命令和工具链摘要在全局缓存中共享，打开第二个项目时直接复用；计入 `cache.totalBytes`。
10. **事件循环**：模型载入、plan、initialize 中的重活移出事件循环，消除 300–800 ms 的卡顿。

**测试**：
- Linux：ux-mcpp U2 保持 0 重建；新增 U2b：在 `touch` 了所有源文件之后再暖启动，仍然重建 0 个模块，模型保持 fresh。
- Windows：`ux-modules-windows` 增加第二次启动和 checkout 之后的启动，两次都重建 0 个模块。
- 探针：E-warm-pure、E-warm-checkout 达到 §1 的指标（V1）。

#### W6 可观察性：出问题时，日志里就有答案（P + E）

**原则**：
- 任何**代价高昂或带来扰动的决策**，都在 **info** 级别留下一行，说明“做了什么、为什么、代价多少”；
- 默认的 info 级别就足以分析问题，`debug` 只用于深挖；
- 格式稳定，可以被机器解析，探针摘要和 bundle 都依赖它。

1. **启动时间线**：每个阶段一行，ready 时再输出一行汇总：
   ```
   startup (root): model cache-fresh 0.2 s · engine up 0.4 s · first preamble Run.cpp 3.1 s · modules 25 reused / 0 rebuilt · first answer 3.4 s · ready 12.0 s
   ```
   - report 的 `startup` 中保存最近 5 次启动，便于对比冷启动和暖启动；
   - 阶段包括：initialize → 模型（来源、fresh/stale 及原因）→ 引擎启动 → 数据库写入 → 每个打开文件的首个 preamble 和前置集合 → 首个语义回答 → ready。
2. **每个决策都写明原因**：

   | 事件 | 现在 | 0.0.13 |
   |---|---|---|
   | 模型 stale | “older than its inputs” | 第一个变化的输入：路径、旧与新的 stamp、内容是否相同 |
   | 模型替换 | `engine database changed`（已有） | 再加上是否重启、为什么，以及触发它的 describe |
   | clangd 重启 | 有原因 | 修正错误的 cause 标签（冷启动的模型替换被标成了 `user`），并写明触发链 |
   | 模块重建 | 没有 | E：每个模块在 info 级别输出 `rebuilding module X: no BMI \| input changed <file> \| command changed <first arg> \| dependency Y rebuilt \| evicted \| validation failed <msg>`；每个前置集合一行汇总 |
   | 模块失败 | 要开 verbose | 直接带出第一条 clang 错误（W2） |
   | preamble 重建 | 只有 debug | `CanReuse` 的 Why 升为 info |
   | 回答由 mcppls 兜底 | 有 late reason | 每分钟汇总：各方法的兜底次数及原因分布 |
   | spin / set-aside | 有结论 | 附上证据：构建了哪些版本、每个版本用了多久 |
   | producer | 耗时 | 完整的部分描述诊断（多行），以及 mcpp 版本 |
3. **信噪比**：
   - clangd 每次 AST 构建都会回显两行命令（约 5 KB）。改为同一文件、同一命令只转发一次，之后降到 debug。
   - 限流器永远不丢 warning 及以上的行，也不丢 mcppls 自己的行；按类别记录丢弃的数量，并输出到日志。
4. **周期健康摘要**：有活动时每 10 分钟输出一行，状态变化时也输出一行。内容包括各方法的 p50/p95、clangd 作答的比例、重建与重启次数、clangd 内存、缓存大小。
5. **关联字段**：每行带上 root、引擎 generation、文件，慢请求带上请求 id。
6. **按需加深**：
   - `mcppls.logLevel = debug` 时，clangd 改用 `--log=verbose`，提示用户需要重启并自动安排；
   - bundle 中包含启动时间线、原因汇总、版本块和最近的 incidents。
7. **隐私**：沿用现有的路径脱敏（主目录写成 `~`）；新增字段不含源码文本，版本块不含路径。
8. **契约与测试**：
   - 行格式写进 `docs/50-troubleshooting.md`；
   - 每类原因行有单元测试；
   - conformance 检查暖启动日志中存在汇总行，且 `0 rebuilt`；
   - 探针摘要（V1）直接解析这些行。

#### W7 版本与运行状态一目了然（P；#53、#52-4）

1. **mcpp 版本**：`ProducerAnswers` 只缓存了“能否产出构建数据库”，改为同时缓存版本，每次 describe 都填入。
2. **server 统一提供 `about`**（`cxxModules/status` 的一部分，也可单独请求），内容包括：
   - server 版本，客户端扩展的版本（经 `initializationOptions` 传入）；
   - 引擎名称、版本、源码身份、已声明的特性；
   - kit、mcpp 的版本和来源、平台、payload 的短 ID。
3. **VS Code 快捷命令面板的“概览”组**，置顶两行：
   - `mcppls 0.0.13 · engine mcppls-clangd 0.0.13 (23.1.0-mcppls.1) · mcpp 2026.10.11.1`
   - `ready · modules 25/25 · up 12 min · restarts 0 · win32-x64`
   - 点击即复制一段 about 文本（版本、平台、编辑器，不含路径），方便提 issue。
4. **版本不一致时明确告警**：扩展版本 ≠ server 版本，或 payload 不是本扩展自带的，就在概览和状态栏 tooltip 中给出警告，日志写一条 warning。#53 中，用户以为在用 0.0.12，实际运行的是 0.0.11。
5. **日志开头的 banner 输出完整版本块**。其他编辑器可以通过 `mcppls version --json` 或 LSP 的 `serverInfo` 看到同样的信息，README 中写明查看方法。

**测试**：hub 的单元测试覆盖这两行和版本不一致时的告警；server 测试检查 `about` 的字段；mock 一个 mcpp，确认两次 describe 都带版本。

## 7. 自审记录

第一轮（单 PR 与 `build.mcpp`）：
- 单 PR 交付；
- W1 的延迟表述改为如实；
- W4 必须在日志限流之前解析；
- W8 不依赖 verbose 日志；
- W3 的预检加了超时和手动开关；
- 单飞不杀进程；
- last-known-good 持久化。

第二轮（可观察性、启动性能、Windows），在第一轮之上：
- **推翻了一个假设**：初稿认为“版本丢失会让模型指纹在两次之间变化”。实际上缓存读取和写入用的都是缓存里的版本，指纹不受影响。探针中 stale 的真正原因是 `git checkout` 改了 mtime。W5 改为“内容哈希判断 fresh”，W7 中的版本问题只影响提示，不影响缓存。（#52 第 4 项中“may also play a part in problem 3”的推断不成立。）
- **新发现的根因比原方案更大**：mcpp 自身失败导致模型缺块、暖启动 degraded，冷启动来回切换模型导致 3 次重启，这两点都是从日志摘要中挖出来的。W3(b) 的兜底因此扩展到任何不完整的 describe；W5 新增“冷启动不来回切换”。
- **“第二次打开慢”不只是重建模块**：即使一个模块都不重建，校验前置集合（24 s）加上 preamble（10 s）也要约 30 s。因此加入持久化校验 memo，并对 preamble 跨会话复用做调查。后者体积大、风险高，所以只做调查，并给出退路。
- **可观察性要先行**：重建了 19/25 和 14 个模块，却没有任何一行日志说明原因，所以 W6 和 E3 排在最前，否则 W5 无从验证。
- **探针本身的问题**：restart-clean 并不是纯暖启动（中间有 checkout）；稳态空闲轮次中 36/40 立即返回且无结果，原因不明。V1 修正这两点，否则指标会被误读。
- **日志量的风险**：“为什么重建”每个模块一行，冷启动约 40 行，可以接受；clangd 的命令回显同时降噪，总量反而下降。
- **冷启动不在临时模型下构建模块的风险**：没有构建工具的项目，临时模型就是最终模型。所以这一条只在检测到 producer 时生效，producer 失败或超时后立即开始构建。
- **std 共享的风险**：BMI 必须按精确命令和工具链摘要作键，任何参数不同都不共享；它占用 `cache.totalBytes`，由清理机制管理。
- **单 PR 的体量**：checkpoint 多达 13 个，每个都推送并在 CI 上验证；性能相关的 checkpoint 另跑探针，避免回归到最后才暴露。
- **隐私**：方案中的诊断包内容一律泛化描述，不含本地路径和用户信息；新增的 about 和日志字段不含源码与路径。

## 11. Windows 探针结论（0.0.13 候选对 0.0.12，同一大型模块项目，CI 4 vCPU）

稳定性：零崩溃；输入时零重启；编辑 `build.mcpp` 时只 describe 一次、零重启，并显示 `build-program-failed`；第二次启动重建 0 个模块（只有两个从未构建过的模块）。

性能：这一轮 0.0.13 所在的 runner 明显更慢——与 mcppls 无关的 `mcpp emit` 耗时是 0.0.12 那一轮的 1.5–2 倍（65→100 s、95→116 s、94→197 s），普通模块编译也慢了同样比例（std 80→122 s），所以两轮的绝对耗时不能直接比较。新日志给出的分解才是结论：

- **第二次打开慢在扫描，不在校验，也不在构建**：Run.cpp 的 25 个前置模块全部复用，共 28 s，其中复用检查 8.5 s，其余约 20 s 是依赖扫描与规划。下一步应持久化扫描 memo（W5.4 的方向随之修正）。
- **补全的每次请求在 Windows 上先花约 1.2 s 做 25 个模块的校验缓存检查**（逐个 stat 输入），稳态下一次补全需要 10–13 s；连续三次超出预算后，文件被暂时转给 mcppls 的引擎（规则与 0.0.12 相同，慢 runner 上越过了阈值）。下一步：减少补全路径上的模块检查，并处理 AST 被淘汰后重建的开销（53 MB preamble）。
- **缓存目录换了位置就全部重建**：探针把缓存复制到新目录后，24 个模块都报 “no BMI for this command (1 built with other commands)”，说明 BMI 的命令键里含有缓存位置相关的路径。下一步：把与缓存位置有关的参数从键中去掉。
- **冷启动**：clangd 在 101.9 s 时 ready（启动行），但模块构建一直持续到约 680 s；冷启动期间 clangd 的补全回复仍要数秒，因为补全路径上的依赖扫描没有被 W1 的有限等待覆盖。
